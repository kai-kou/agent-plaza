# Skill: agent-plaza 開発ワークフロー（1作業単位の進め方）

対象: agent-plaza の実装単位を担当するエージェント。正本は `REQUIREMENTS.md`、`docs/development-policy.md`、`AGENTS.md`、および `spec/`。本スキルはその実行手順を定めるもので、正本と矛盾する場合は正本が優先する。

## 手順

1. **単位の確定**: 目的、完了条件、対象外を1段落で書く。MVP の段階（M1〜M4）のどこに属するか、依存する検証（V 番号）や判断（D 番号）があるかを確認する。判断が未確定の事項に触れる場合は着手しない。
2. **spec の確認**: 触れる仕様を `spec/` で確認する。仕様変更が要る場合は、spec の差分とテストベクターの更新を先に用意する（実装はその後）。
3. **失敗するテストを書く（TDD）**: domain／application の振る舞いをテストで先に表す。適合ベクターに該当する場合はベクター側へ追加し、provider 横断で同じ期待値になることを確認する。
4. **最小実装**: ports の内側で実装する。core にフレームワークや基盤 SDK を持ち込まない。既存の用語（ユビキタス言語）を使い、新語は spec の用語集へ登録してから使う。
5. **テストを通す**: 単体 → 適合 → 統合の順に実行する。E2E L1（合成）に対象シナリオがある場合はそれも通す。E2E L2（実環境）は所有者の承認と上限の固定がある場合だけ手動で実行する。
6. **衛生スキャン**: 差分に秘密情報、実 ID、実会話、個人情報が混ざっていないかを確認する。フィクスチャは合成値のみ。
7. **Draft PR と専門チーム・セルフレビュー**: PR 本文に目的・完了条件・対象外・テスト結果・未検証の残りを書く。実装担当と別の担当で専門チーム（設計・QA・安全性の3観点）を組成してレビューし、各観点の判定（PASS / 要修正、指摘は重大度と根拠つき）とレビュー対象 head を PR コメントに記録する。必須指摘は修正後の head で再レビューを受け、解消を確認する（開発方針第5節）。
8. **Ready 化とマージ**: 全観点 PASS（または必須指摘の解消確認済み）、テストと型チェックの実測 pass、レビュー記録の head と最終 head の一致を確認してから Ready 化し、通常マージで取り込む。マージ後に merge commit と PR 状態を読み戻して検証する。
9. **報告**: 完了条件に対する合否、未検証の残り、次の一手を分けて報告する。「実装した」と「検証した」と「公開可能」を混同しない。

## 止まる条件

- 要件の判断（D 番号）が要るのに未確定である。
- 製品能力が `unknown` で、その確定に実アカウント・実環境の確認が要る。
- 承認境界の5区分に触れる操作（外部送信・公開、課金・契約、削除・不可逆変更、権利・個人情報、権限拡張）が必要になった。

この場合は作業を止め、不足している判断・確認を具体的に列挙して所有者へ上げる。
