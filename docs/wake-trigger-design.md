# 起床トリガーの形式非依存化 — 設計

状態: 設計・検証済み（2026-11-08、所有者承認 A）。実装は本書の提示後に別途行う。
関連: [VM 交換前提の運用方式](vm-resilient-operations.md)、[経緯・判断記録](vm-resilient-operations-history.md)

## 1. 背景と問題

起床フックは、観測ログ（JSONL）へ追記される `posted` 行の増加を検知して起床する。観測ログの書き手は2つある。

- ブリッジ: コンパクトな JSON（区切り文字に空白なし）で書く
- Socket Mode リスナー: 標準の JSON 出力（区切り文字に空白あり）で書く

フックの計数は固定文字列 `"action":"posted"` の一致で数えていたため、ブリッジ形式の行しか数えられなかった。リスナー形式の行だけが到着したイベントでは起床が発火しない。実例として、リスナー経由のみで到着したイベントが、ブリッジ側の echo 行が来ないまま数時間にわたり未処理（未 ack・試行 0 回）になった事例が発生した（2026-11-08 に検知・原因特定）。起床ログの全数照合でも、起床はすべてブリッジ行起点であり、リスナー行起点の起床は 0 件だった。

問題の本質は「対象経路の不足」ではなく「テキスト形式への依存」である。書き手が増える、または既存の書き手の出力形式が変わるたびに、同じ欠落が再発する。

## 2. 設計方針

計数をテキスト一致から JSON の意味（パース結果）へ移す。

- 述語: 行を JSON としてパースし、`action` フィールドが `"posted"` の行だけを対象とする。空白・キー順・その他のフィールドの有無に依存しない。
- 壊れた行（書き込み途中の切断行など）はパース失敗として読み飛ばし、計数全体を失敗させない。
- 件数の計数と、新着イベント ID の抽出は、同一のパース済みストリームから行う（片方だけ形式依存が残る状態を作らない）。
- 対象外の行（`post_failed`、`poll_failed`、`baseline` 等）は従来どおり数えない。`posted` は「配送先が受理した」行だけであり、受理が確認できない行で起床しない原則を維持する。

## 3. 方式比較

| 方式 | 内容 | 評価 |
|---|---|---|
| A1（採用） | フック側でパースベースの計数へ変更する | 変更点が1か所で、形式の揺れと将来の書き手追加に強い。フックは ID 抽出で既に JSON パーサ（jq）を使っているため新規依存はない。性能は 5 秒間隔のポーリングでファイル全行を読む現行方式と同等 |
| A2 | リスナー側の出力形式をブリッジ形式（コンパクト）に合わせる | 稼働中のリスナーと配布キットに触れるうえ、形式依存そのものが残り、別の書き手が現れれば再発する。不採用 |
| A3 | 起床条件を配送ストア（D1）の未 ack 有無のポーリングへ変える | 5 秒間隔のフックに資格情報と API 呼び出しが入り、遅延と障害点が増える。観測ログ自体の信頼性が疑われる事態が来たら再検討する余地はあるが、現時点では過剰。不採用 |

## 4. 状態移行と切替時の挙動

- 新しい計数意味論には新しい状態ファイルを使う（例: `posted-count-all.txt`）。従来の状態ファイルは変更せず、ロールバック時の基準として残す。
- 切替直後の最初のポーリングでは、過去のリスナー形式 `posted` 行の分だけ件数が跳ね上がり、1 回の起床が発火する。起床フローの回収は購読の未処理分を配送ストアから引く方式（合図の ID 一覧が正本ではない）ため、処理済みイベントの再処理は起きない。この起床で、その時点で滞留している未処理分が回収されることを、切替の受入条件とする。
- 静かに切り替えたい場合は、新状態ファイルを切替時点の件数で初期化すれば跳ね上がりは起きないが、滞留分の回収は次の到着まで遅れる。本書の推奨は、起床を発火させる形（受入確認を兼ねる）。

## 5. 検証（設計段階で実施済み）

試作述語（パースベース）を実ログとフィクスチャで検証した。実装時にも同じ観点で再検証する。

- 実ログ（読み取り専用）: 旧述語の件数 596 に対し、新述語は 677（ブリッジ形式 596 + リスナー形式 81）。新述語の末尾 ID は、滞留していた2件のイベント ID と一致した。
- フィクスチャ: ブリッジ形式 posted、リスナー形式 posted、post_failed、poll_failed、baseline、切断された壊れた行を混在させ、新述語の件数が posted 2 件のみを数えることを確認した。
- 疑似ポーリング列: (1) ベースライン初期化、(2) ブリッジ行の追記で増加と正しい新着 ID、(3) post_failed の追記では増加なし、(4) リスナー形式だけの追記（滞留事例の再現）で増加と正しい新着 ID、を確認した。
- 実装時の故障注入: 変更済みフックをサンドボックス（観測ログと状態のコピー）で動かし、リスナー形式の posted 行の追記で起床判断が出ること、post_failed では出ないことを確認してから本番へ適用する。

## 6. ロールバック

- 変更前のフックスクリプトへ戻すだけでよい。旧スクリプトは未変更の旧状態ファイル（切替時点のブリッジ形式件数）を読むため、切替後に到着したブリッジ行があればその分で起床が発火し、取りこぼしは生じない。
- 新状態ファイルは旧スクリプトからは参照されない。残置しても無害だが、混乱を避けるためロールバック時に退避する。

## 7. ゲート2（ブリッジ無効化）との関係

現行トリガーのままブリッジを無効化すると、起床が一切発火しなくなる。本変更はブリッジ無効化の前提条件であり、本変更の適用後は起床がブリッジ行に依存しなくなるため、ゲート2の判断は「二重配送の扱い」など本来の論点だけで評価できる。
