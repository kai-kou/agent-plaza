# 運用方式の経緯と判断記録（VM 交換前提の運用方式）

方式の正本は `docs/vm-resilient-operations.md`、導入手順は `docs/socket-mode-listener.md`、展開は Epic #59。本書は、方式がなぜ今の形になったかを引き継ぎ用に残す判断記録である。調査の生ログや詳細な実施記録（フェーズ別ログ、専門チームの調査メモ、議論ラウンドの全文）は先行導入者（mugi）の手元にあり、本書はその結論と根拠の要約である。実運用の URL・ID・資格情報は書かない。

## 1. 背景整理（2026-11-06）

- 応答遅延の内訳を層別に実測した。検知層（ブリッジ観測 420 件）は Slack 投稿→本体 ingress 完了が中央値 8.5 秒・p90 27.1 秒・最大 86.2 秒で、主因はハブ側の最新ポインタ更新の遅延と推定した。処理層（起床後の検討時間）が全体の大半を占めるが未計測だった。
- 方式の置き換え対象は検知段だけとし、起床以降（pull → 処理 → ack）は現行フローを維持する方針（推奨案 B：Socket Mode 常駐受信でハブ＋ブリッジのポーリング段を置換）を採用した。ドアベル（MCP Events）は配送方向と層が別であり、Tier の分類（受信形態の定義）とは別軸であることもこの時点で整理した。

## 2. 第 0 段（2026-11-07）：観測 0 件の根本原因と前提確認

Socket Mode リスナーを常駐化しても観測が 0 件だった問題を切り分けた。根本原因は 2 件とも VM 交換ではなかった。

1. 受信フィルタの取り違え：Events API の payload の `type` は `event_callback` だが、envelope の種別 `events_api` と比較していたため全件を無視していた。単体テストのフィクスチャも同じ誤前提で作られており、不具合を隠していた。教訓として、フィクスチャは実 payload の形から取ることをキットの README に明記した。
2. プロキシ設定の写しの失効：systemd サービスのプロキシドロップインが別セッションの環境の写しで、宛先によって黙って失効していた。対策として、プロキシは起動主体の環境から直接継承し、写しを作らない形へ改めた。

修正後、初の socket-mode 観測（検知約 0.85 秒、ブリッジ中央値の約 1/10）を確認。前提確認（フック実行環境の環境変数、flock の fd＋exec パターン、ingress 応答時間、Bot スコープ、配送量と自動無効化の関係）も同段で完了した。

## 3. 第 1 段（2026-11-07）：ホーム完結のスーパーバイザ方式

systemd の限界を踏まえ、段階ゲートで判断した。

- systemd ユニットを VM 交換後に自動復旧させる正規手段はランタイム文書上なく、systemd ユーザーサービス化もこのゲスト構成（ユーザーバスなし、到達ターゲットは default.target）では不成立と確定した。
- 採用したのは、poll 5 秒のスーパーバイザフックが flock で単一性を保ちながらホーム配下からリスナーを起動する構成（フックへの特権的な役割は所有者の例外承認を経た）。
- 故障注入は全件通過（systemd 停止からの切替、kill -9 からの復旧、SIGSTOP によるゾンビ再現での kill＋起床、フック停止時の無影響）。systemd リスナーは停止・無効化し、常駐確認 cron は 1 時間ごとの保険へ置き換えた。
- Events API → Cloudflare Worker は根本解決になりうるが、同一アプリで Socket Mode と併用できない一発切替になるため過剰投資と判断し、後の判断事項（ゲート 2 相当）へ送った。

## 4. 誤 kill の発生と対策（2026-11-08）

再起動直後、スーパーバイザが起動約 3 秒のリスナーを「heartbeat が古い」ことだけで kill した。構造的原因は、stale 判定が heartbeat ファイルの時刻だけに依存し、プロセス自身の起動時刻を見ていなかったこと（再起動直後は heartbeat ファイルが前 boot の残存でありうる）。実害は約 8 秒の遅れのみでイベント欠落はなかった。

対策は方式確立（次節）で実施した：stale 判定にプロセス起動時刻ガードを追加し、凍結注入と起動直後の擬似 stale の両方で検証した。この規則は方式ドキュメント §7 に正本として記載した。

## 5. VM 交換頻度の事実確認（2026-11-08）

所有者の求めで、公開公式を中心に事実確認した。

- 公開公式（Meta のニュースルーム、AI リサーチ、ヘルプ）には、デプロイ頻度・VM 置換・再起動の数値記述は一切ない。「頻繁な更新で VM が置き換わりうる」という定性表現がランタイム側の指示にあるのみで、頻度の根拠はローカル実測に求めるほかない。
- ローカル実測：約 38 時間に再起動 24 件（約 1.6 時間に 1 件）。内訳は boot_id 変化で証明できる再起動と、強い状況証拠によるもの。ゲスト内で証明できるのは OS／ランタイムセルの再起動までで、ハイパーバイザ側の VM 置換そのものとは切り分けできない。
- 再起動以外の停止要因も同期間に確認した：監視側の誤 kill（第 4 節）、Slack SDK のエンドポイント rotation（プロセスは無停止。Slack 公式も数時間ごとの接続 refresh が通常としている）、人為的な再起動・検証操作、プロキシ写しの失効。
- 未解明のまま残るもの：boot 前の沈黙（停止開始が boot 時刻より約 22〜24 分先行する事例 2 件）と、復旧時間の二峰性（高速な例は boot 後 12〜40 秒、長期の例は poll 途絶 475〜2,205 秒）。ホスト側の記録はゲスト内から参照できない。

## 6. 方式の確立（2026-11-08）

所有者が目標「各環境において Slack 投稿から 1 分以内に起床（起床後の LLM 検討時間は含めない）」を設定し、方式を確立した。60 秒目標と現行値の不整合を解消するため、次の変更を実施し故障注入で検証した（詳細は方式ドキュメント §4・§8）。

- スーパーバイザの stale 閾値を 180 秒 → 45 秒へ短縮し、プロセス起動時刻ガードを追加。
- リスナーのウォッチドッグ（接続断の継続で自己終了）を 300 秒 → 45 秒へ短縮。
- boot 履歴フックを新設（再起動の証跡をジャーナルに依存させない）。
- 起床遅延の計測と readiness チェックを整備し、ベースライン（72 時間、帰属できた起床 79 件で全件 60 秒以内）を確認。

なお、設計レビューの段階では stale 判定の変更は後の判断事項へ送る整理だったが、所有者の方式確立の指示と 60 秒目標（全環境）が旧値のままでは達成できないため、確立の範囲に含めて実施した経緯がある。主経路切替（ブリッジ無効化）・Events API・Tier 再相談は判断事項のまま変更していない。

## 7. 引き継ぎ時の注意

- 再起動のたびに /etc と前 boot のジャーナルは消える。証跡はホーム配下（boot 履歴、診断ログ、heartbeat）に寄せてある。
- 停止を見たら、まず boot 履歴で再起動かどうかを確認し、次に SDK の rotation や監視側の記録と突合してから原因を名指しする。証明できない機構（ハイパーバイザ側の置換など）を断定しない。
- 方式の変更は、方式ドキュメント §10 の変更管理（バックアップ、単体テスト、故障注入、readiness、記録）を揃えてから完了とする。

## 8. 起床トリガーの形式依存と設計決定（2026-11-08）

運用方式の適用後、起床フックがブリッジ行でしか起床しない構造が実事例で判明した。

- 症状: リスナー（Socket Mode）経由のみで到着したイベントが、ブリッジ側の echo 行が到着しないまま数時間にわたり未処理（未 ack・試行 0 回）になった。配送自体は受理されており、無言消失ではない。
- 原因: 観測ログの書き手が2つ（ブリッジとリスナー）あり、JSON の区切り形式が異なる。フックの計数は固定文字列の一致に依存していたため、片方の形式の行しか数えられず、リスナー形式だけの到着では起床が発火しなかった。起床ログの全数照合でも、起床はすべてブリッジ行起点で、リスナー行起点は 0 件だった。
- 寄与要因: 同時間帯の VM 再起動が起床セッションを中断した可能性はあるが、再起動後にフックのポーリングは再開しており、再起動だけでは数時間の無起床を説明できない。
- 未確定: ハブが当該イベントをブリッジへ出さなかった理由は、配送側の証跡だけでは切り分けできていない。
- ゲート2への影響: 現行トリガーのままブリッジを無効化すると起床が一切発火しないため、トリガーの形式非依存化はブリッジ無効化の前提条件になる。
- 決定: 2026-11-08、所有者が正式提示で選択肢 A（設計と検証を進める）を承認した。設計は [起床トリガーの形式非依存化 — 設計](wake-trigger-design.md) にまとめ、試作述語の検証（実ログでの読み取り専用照合とフィクスチャによる疑似ポーリング列）まで完了した。実装・適用は設計の提示後に別途判断する。
- 実施状態の追記（2026-11-09）: 上記の形式非依存化は、2026-11-08 夜に実装と本番適用まで完了した。計数は JSON のパースに基づく方式（`action` が `posted` の行を対象とし、壊れた行は読み飛ばす）へ変更し、サンドボックスでの故障注入検証を通過したうえで、実イベントでの起床と処理完了の成立を確認した。これにより、ゲート 2 の前提条件だった「トリガーの形式非依存化」は解消済みである（ゲート 2 本体の判断事項は変更していない）。
