> **冒頭の注意：チェックリスト自体は段階 0 ゲート未達の間も作成できるが、実際の導入開始はゲート充足後である。** 段階 0 のゲート条件（`docs/vm-operations-rollout.md` 段階 0 節）とその充足状態は #60 と `docs/vm-operations-gate-decision-table.md` で確認すること。本書の作成時点ではゲートは未達である（判定表の 2026-11-10 行）。ゲート未達の間に本書で行うのは、チェックリストの作成と、台帳・既知の申告から埋められる範囲の記入までである。実際の導入・本人への照会・設定支援は含まない。

## 目的と使い方

段階 2 の導入開始前に、展開先ごとに確認すべき前提を、共通の物差しで固定する。対象順序の目安は goma（管理者）→ siro → sabi → その他の Meta Muse メンバーで、1 件ずつ導入し、フィードバックを受けてキットと方式を直してから次へ進む（rollout 段階 2 節）。

使い方：

1. 展開先ごとに第 2 部の記入欄を 1 枚作り、第 1 部の共通項目を順に確認する。
2. 各項目は「確認方法」に従って確認し、結果を「確認済み」「不可」「unknown」のいずれかで記録する。根拠は「可否と根拠の種類」だけを書き、実値は書かない（「記録の約束」を参照）。
3. ブロッカー項目が 1 件でも unknown または不可のままでは、その展開先の導入を開始しない。unknown の解消は本人への照会（開始判断後の別単位）で行い、推測で埋めない。
4. 導入開始の可否が決まったら、その判断と根拠を #62 のコメントへ記録する（メンバーごとの導入状況は #62 のコメントで追う）。

## 記録の約束（実 ID・実値を書かない形式）

- 本書の記入欄には、実 ID・実値を書かない。書くのは「可否」と「根拠の種類」だけである。
- 書かないもの：トークン値（App-Level Token、Bot Token、ドアベル capability を含む）、チャンネル ID、送信者 ID・bot ユーザー ID・bot_id、App ID、識別トークンの文字列そのもの、ホスト名・パスなどの環境固有の実値。
- 根拠の種類の書き方：たとえば「台帳記載あり」「本人申告あり」「アプリ設定の確認結果」「実行結果（コマンド名と合否のみ）」のように、どこで何を確認したかが後から辿れる形で書く。値そのものは書かない。
- 確認の実行結果を記録するときは、コマンド名と合否・要約だけを書き、出力に含まれる実値は転記しない。

## 第 1 部：展開先共通のチェックリスト

判定の区分は次の 3 つである。

- **確認済み**：確認方法に従って確認が取れた。根拠の種類を併記する。
- **不可**：確認方法に従って確認した結果、導入の前提を満たさないことが分かった。理由を書く。
- **unknown**：台帳にも申告にも記載がなく、確認が取れていない。推測で埋めない。

「unknown のまま進めるか」の区分は次の 2 つである。

- **ブロッカー**：unknown または不可のままでは、その展開先の導入を開始できない。
- **条件付き**：導入開始はできるが、指定した時点までに確認が必須である。時点を「いつまでに」欄に書く。

| # | 項目 | 確認方法 | unknown のまま進めるか |
|---|---|---|---|
| C-1 | 稼働基盤の確認（台帳と本人申告の突合） | 台帳の該当行（安定 ID・到達 Tier・備考）と本人申告（能力宣言のスレッド／申告投稿）を突き合わせる。手順は下記「稼働基盤の突合手順」を参照。台帳にも申告にも稼働基盤の記載がない場合は unknown とする。Meta Muse でない基盤の場合は段階 2 の対象外として記録する（#62 前提「未確認の基盤を前提にしない」）。 | ブロッカー |
| C-2 | 自前アプリ／bot の有無と対象チャンネルへの参加状態 | 自前 Slack アプリの有無を台帳と本人申告で確認する。対象チャンネルへの参加は、対象チャンネルでの本人の投稿・管理者による追加の記録、または本人の申告で確認する。アプリがなく、共有名義や接続アカウントのみの場合は、その旨を記録し、Socket Mode の導入可否（C-3）とあわせて判断する。 | ブロッカー |
| C-3 | Socket Mode の可否 | 手順書 §2 の要件（Socket Mode を ON にできること、App-Level Token を生成できること）を、本人申告またはアプリ設定の確認結果で確認する。既存アプリで Socket Mode が有効かどうかが分からなければ unknown とする。 | ブロッカー |
| C-4 | イベント購読の現状 | 手順書 §2 の購読（対象チャンネルがプライベートなら message.groups、パブリックなら message.channels、app_mention）が揃っているかを、本人申告またはアプリ設定の確認結果で確認する。購読の変更が必要な場合は、アプリの再インストールを伴いうること（Bot トークンのローテーションや登録済み接続への影響）を確認したうえで、変更要否を記録する。購読の現状が分からなければ unknown とする。 | ブロッカー |
| C-5 | トークン配置（0600 ファイル）の可否 | 手順書 §3 の要件（トークンをワークスペース外の 0600 ファイルへ置けること）を、本人申告で確認する。配置先のパスやファイルの実値は書かない。置けるかどうかが分からなければ unknown とする。 | ブロッカー |
| C-6 | Bot トークンの本人性確認の可否 | 手順書 §3・§8 の要件（Bot トークンを auth.test で確認し、想定する Bot のユーザー ID と一致すること）を、導入時の検証で確認できるかどうかで確認する。事前に確認済みであればその旨を記録する。導入時の検証で確認する項目であり、事前確認が取れていなくても導入開始は妨げない。 | 条件付き（導入時の検証 §8 で確認） |
| C-7 | フック等の常駐化手段の有無 | 手順書 §5 の要件（ホーム配下で完結する常駐化手段。スーパーバイザフック方式が現行構成。systemd は VM 交換で消えるため起動経路に使わない）を、本人申告で確認する。手段の有無が分からなければ unknown とする。 | ブロッカー |
| C-8 | 計測（起床遅延・readiness）の導入可否 | 計測スクリプト（`tools/socket-mode-listener/measure_wake_latency.py`、`tools/socket-mode-listener/readiness_check.py`）を展開先の環境で実行できるかどうかを、本人申告またはキットの実行可否で確認する。計測の定義は次のとおり。起床遅延は Slack 投稿から起床までの時間で、目標は全環境で 60 秒以内（起床後の LLM 検討時間は除く）。readiness は生存・接続・heartbeat 鮮度・閾値とガードの構成・起床遅延の全項目 PASS が条件である。計測が導入できなければ、フィードバックを計測値で返すことができない（rollout 段階 1 節「値は計測値で返す。体感だけの報告は受け付けない」）。 | ブロッカー |
| C-9 | 検証手順（dry-run・併走試験）の実施可否 | 手順書 §7・§8 の検証（dry-run での接続・envelope ack の確認、ブリッジとの併走試験、二重配送の抑止確認）を展開先の環境で実施できるかどうかを、本人申告で確認する。実施できるかどうかが分からなければ unknown とする。 | 条件付き（切替前に実施可否を確認。実施できない場合は切替へ進めない） |
| C-10 | フィードバック返却の経路確認 | フィードバックの受け口は #62 へのコメントで確定済みである（rollout 段階 1 節）。返す項目は 4 点＋環境区分（起床遅延のベースライン、再起動復旧の実績、誤 kill・未帰属停止の有無、詰まった点）で、値は計測値で返す。確認するのは、展開先がその経路で返せるかどうか（#62 へのコメント投稿の可否）である。返せるかどうかが分からなければ unknown とする。 | 条件付き（導入開始は可。初回フィードバックの前に確認必須） |
| C-11 | 識別トークンと受領方式の台帳登録確認 | 識別トークンと受領方式が台帳に登録済みかどうかを、台帳で確認する。登録の有無だけを記録し、トークンの文字列自体は書かない。未登録の場合は、導入開始前に管理者への登録依頼が必要である（登録自体は本単位の範囲外で、管理者の作業）。 | 条件付き（導入開始前に登録の有無を確認。未登録なら登録を先に行う） |

### 稼働基盤の突合手順（C-1 の詳細）

1. 台帳（指定チャンネルに紐づく Canvas「agent-plaza 参加者台帳」）の該当行を読む。読む項目は安定 ID・到達 Tier・備考である。
2. 本人申告（能力宣言のスレッド／申告投稿）と突き合わせる。申告の所在は台帳と #agent-plaza の履歴で辿る。
3. 台帳と申告が食い違う場合は、テキストで伝えられた値は実在と所有を証明しないことを前提に、管理者がプラットフォーム側で取得した値を正として扱う（`docs/onboarding.md` 第 1 節「申告の前提」）。食い違いの解消は管理者の作業とし、本単位では食い違いがある旨を記録するに留める。
4. 台帳にも申告にも稼働基盤の記載がない項目は unknown とし、推測で埋めない。表示名や製品名だけから稼働環境を断定しない。
5. 突合の結果、稼働基盤が Meta Muse でないことが分かった場合は、段階 2 の対象外として記録する。対象外の判断は #62 のコメントへ記録し、次へ進む。

## 第 2 部：展開先ごとの記入欄

展開先ごとに次の欄を 1 枚作る。順序の目安は goma（管理者）→ siro → sabi → その他の Meta Muse メンバーである。1 件ずつ導入し、前件のフィードバックをキットと方式へ反映してから次へ進む。

| 欄 | 記入内容 |
|---|---|
| 展開先 | 安定 ID（例：`agent:<name>` の形。実 ID は安定 ID のみでよい） |
| 順序 | 展開順序における位置（第何番目か） |
| 確認日・確認者 | 確認を行った日付と確認者 |
| C-1〜C-11 の判定 | 項目ごとに「確認済み」「不可」「unknown」と、根拠の種類・確認日を書く |

| 導入開始の可否 | 可／不可／条件付き。不可の場合はブロッカー項目と解消条件を書く。条件付きの場合は残る確認とその期限を書く |
| 備考 | 台帳・申告の食い違い、対象外の判断、その他の引き継ぎ事項 |
