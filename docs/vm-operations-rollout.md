## 段階 0：安定稼働の確認（#60）

ゲート条件の全てを満たすこと。最短でも開始から 3 日間は観測する。

1. readiness チェックが連日 PASS する。
2. 起床遅延（24 時間ローリング、帰属分）が連日 100% 60 秒以内。
3. 実再起動が 3 回以上発生し、全て無人復旧する（boot 履歴に全 boot の記録が揃う）。
4. 誤 kill が 0 件、帰属できないリスナー停止が 0 件。
5. イベント欠落が 0 件。

確認は日次で行い、安定稼働ログへ記録する。異常が出たらゲートを止め、原因を直して観測を延長する。満たしたら所有者へ報告し、段階 2 へ進む。

## 段階 1：配布キットの整備（#61）

- 方式・手順・ロードマップの各ドキュメントと参照実装キットを本リポジトリへ保存する（本移管で実施）。
- 環境依存値（チャンネル ID、ベース URL、ホームパス）はパラメータ化し、実値を入れない。キットの単体テスト全件通過を前提とする。
- `docs/onboarding.md` から方式ドキュメントへリンクする（2026-11-08 に追加。導線の「VM 交換前提の運用方式」から方式・手順・ロードマップ・参照実装へ辿れる）。
- フィードバックの受け口（2026-11-08 に確定。委任ルールに基づく推奨判断。記録は #61 コメント）。
  - 受け口：段階 2 の Issue #62 へのコメント（メンバーごとに、導入完了時と追加の気づきがあったときに記録する）。記録の正本は #62 のコメントとし、#agent-plaza への投稿は記録を知らせる通知にとどめる。
  - 返す項目（4 点＋環境区分）：起床遅延のベースライン（中央値・最大・件数、環境区分つき）、再起動復旧の実績（実再起動の回数と全件の無人復旧可否）、誤 kill・未帰属停止の有無（件数と帰属）、詰まった点（手順のどこで、何が、どう詰まったか）。
  - 値は計測値で返す。体感だけの報告は受け付けない（再現・照合できないため）。
  - 反映：コーディネーターが集まったフィードバックを方式ドキュメントとキットへ反映し、版を上げる。反映内容は展開先全員へ共有する（段階 2 の進め方と同じ）。

## 段階 2：Meta Muse メンバーへの順次展開（#62）

- 対象は Meta Muse で稼働する参加者。稼働基盤は参加者台帳と本人申告で確認する。
- 順序の目安：goma（管理者）→ siro → sabi → その他の Meta Muse メンバー。1 件ずつ導入し、フィードバックを受けてキットと方式を直してから次へ進む。
- 各メンバーのトークンやアプリ設定は各人の領域。こちらは手順と検証方法を提供し、導入結果の読み戻しに協力する。
- フィードバックは方式ドキュメントとキットへ反映し、版を上げる。反映内容は展開先全員へ共有する。

## 段階 3：Grok Bot への横展開（#63）

- yuzu は box 常駐ポーラー＋webhook 起動の別構成のため、コードではなく原則と計測を移す：起床遅延の定義と 60 秒目標、投稿→起床の計測、存在と鮮度の二層判定と起動時刻照合、停止の帰属に必要な記録。
- 窓口は kai-kou/agent-doorbell-mcp フェーズ 4 の実機検証と同じ経路（yuzu の確実な窓は 07:00〜23:00 JST）。

## 段階 4：Dots への横展開（#64）

- Dots は MCP Events アダプター経由の別経路。移すのは計測定義、配送状態の突合、観測の型、帰属の型。
- siro が主担当。ステップ 2 (e) の整理状況と干渉しないよう、開始時期と範囲は siro と調整する。関連：本リポジトリ #28、kai-kou/agent-doorbell-mcp フェーズ 2。
