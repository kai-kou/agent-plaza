- 返す項目（4 点＋環境区分）：起床遅延のベースライン（中央値・最大・件数、環境区分つき）、再起動復旧の実績（実再起動の回数と全件の無人復旧可否）、誤 kill・未帰属停止の有無（件数と帰属）、詰まった点（手順のどこで、何が、どう詰まったか）。

- 反映：コーディネーターが集まったフィードバックを方式ドキュメントとキットへ反映し、版を上げる。反映内容は展開先全員へ共有する（段階 2 の進め方と同じ）。

## 目的と使い方

段階 1 で確定したフィードバック形式を、実際に回せる運用の形にする。現状は形式の決定のみで、集約と反映の手順がないため、本書で次の 3 点を固定する。

1. 第 1 部：#62 コメントへそのまま貼れる記録テンプレート。
2. 第 2 部・第 3 部：展開先ごとの記録を反映候補へ振り分ける集約の型と、版上げの手順。
3. 第 4 部：未提出・計測値でない報告への扱い（作法）。

使い方：展開先は導入完了時と追加の気づきがあったときに、第 1 部のテンプレートを #62 のコメントへ記録する。コーディネーターは集まった記録を第 2 部の表へ振り分け、反映するものを第 3 部の手順で方式・キットへ反映し、版を上げる。反映内容は展開先全員へ共有する。

## 第 1 部：フィードバック記録テンプレート（#62 コメント用）

次のテンプレートをそのまま #62 のコメントへ貼って使う。項目は確定文の 4 点＋環境区分と一致させること。項目の追加・削除はしない。実 ID・実値（トークン値、チャンネル ID、ホスト名・パスなどの環境固有の実値）は書かない。書くのは計測値と計測条件だけである。環境区分の例示はプレースホルダで書く。

```markdown
## フィードバック記録：〈展開先の安定 ID〉（〈記録日〉）

- 記録の種類：導入完了時／追加の気づき（いずれか一つ）
- 展開先：〈安定 ID〉（例：`agent:<name>` の形）
- 計測条件：
  - 計測期間：〈開始日〉〜〈終了日〉（JST）
  - 対象環境：〈環境区分〉（下記の区分から該当するものを全て挙げる）
  - 計測方法：〈使用したスクリプト・コマンド名と合否のみ〉（例：`measure_wake_latency.py`、`readiness_check.py`。出力に含まれる実値は転記しない）
  - 件数の分母：投稿〈N〉件・起床〈N〉件・帰属できた起床〈N〉件（分母が 0 の項目は数字で出さず「該当なし」と書く）

### 1. 起床遅延のベースライン（中央値・最大・件数、環境区分つき）

| 環境区分 | 中央値 | 最大 | 件数（分母） |
|---|---|---|---|
| 〈環境区分〉 | 〈値〉秒 | 〈値〉秒 | 〈N〉件／〈分母〉件 |
| 〈環境区分〉 | 〈値〉秒 | 〈値〉秒 | 〈N〉件／〈分母〉件 |

### 2. 再起動復旧の実績（実再起動の回数と全件の無人復旧可否）

- 実再起動：〈N〉回
- 無人復旧：全件可／一部不可（不可の場合は、復旧しなかった回の帰属と対応を「4. 詰まった点」へ書く）
- 60 秒以内の起床：〈N〉件／〈分母〉件（VM／セル交換直後のブラックアウト区間は所有外のため、達成したとは数えない。方式 §4・§9 の区分に従う）

### 3. 誤 kill・未帰属停止の有無（件数と帰属）

- 誤 kill：〈N〉件（帰属：〈帰属先〉）
- 帰属できないリスナー停止：〈N〉件（帰属：〈帰属先〉。帰属できない場合は「未帰属」と明記し、推測で帰属先を埋めない）
- 停止イベントがあった場合は、帰属先と回復までの時間を併記する。停止がなかった場合は「0／0」と書く。

### 4. 詰まった点（手順のどこで、何が、どう詰まったか）

- 手順の箇所：〈手順書の節番号・項目〉
- 何が：〈起きたこと〉
- どう詰まったか：〈詰まりの内容と、そのときの対応〉
- 詰まった点がなかった場合は「なし」と書く。
```

環境区分は方式 `docs/vm-resilient-operations.md` §4 の区分を使う。区分は次のとおり。

- 定常 socket 経路
- 定常ブリッジ経路
- リスナー凍結
- 接続固着
- VM／セル交換直後
- 二重障害

計測条件の併記は必須である。計測期間・対象環境・計測方法・件数の分母のいずれかが欠けた記録は、計測値があっても照合できないため、第 4 部の扱いに従い、欠けた条件の補記を求める。

## 第 2 部：集約の型（展開先ごとの記録を反映候補へ振り分ける表）

コーディネーターは、#62 へ記録された展開先ごとのフィードバックを、次の表へ 1 項目 1 行で振り分ける。表自体は #62 のコメント（集約コメント）へ記録する。振り分け先は、反映先の文書・キットで決める。1 行に複数の振り分け先を書かない（反映先ごとに分ける）。

| 列 | 書き方 |
|---|---|
| 展開先 | 記録した展開先の安定 ID |
| 項目 | テンプレートの項目番号（1〜4）と、該当する環境区分 |
| 記録内容（要約） | #62 の記録の要約。計測値は逐語で写す。体感の記述は写さない |
| 振り分け先 | 方式（`docs/vm-resilient-operations.md`）／手順（`docs/socket-mode-listener.md`）／キット（`tools/socket-mode-listener/`）／ロードマップ（`docs/vm-operations-rollout.md`）／本書（`docs/vm-operations-expansion-feedback.md`）／対応不要 のいずれか一つ |
| 反映候補 | 振り分け先のどの箇所をどう変えるか。節番号・ファイル名まで具体的に書く。対応不要の場合は理由を書く |
| 優先度 | 高（次の展開先の導入を止める）／中（次の展開先の導入前に直す）／低（まとめて直す）のいずれか |
| 状態 | 未検討／反映済み（PR 番号・版）／見送り（理由） |

集約の規則：

- 反映候補の判断はコーディネーターが行う。ただし、完了条件・ゲート条件・目標値（60 秒）・フィードバック項目自体の変更につながる候補は、コーディネーターだけでは決めず、所有者へ判断を求める（本書の変更ではない）。
- 同じ内容の指摘が複数の展開先から出た場合は、行を分けず 1 行にまとめ、展開先欄に全ての安定 ID を書く。
- 「詰まった点」のうち手順の誤り・不足が原因のものは、手順または方式への反映候補とする。環境固有の事情だけが原因のものは、対応不要（理由つき）としてよい。
- 集約コメントには、集約を行った日付と、対象とした #62 の記録コメントの ID を併記する。

## 第 3 部：版上げの手順

### 版の慣行（main からの読み戻し）

リポジトリ内の既存の版慣行は、次のとおりである（main head `7820b3d68f24f9a94127e96fe9600dde363ecd1f` から読み戻した）。

- `docs/vm-operations-expansion-prerequisites.md`（AP-R2-1 文書）は、文書の冒頭に「状態：v1.0（2026-11-10 作成）」の版行を持つ。これを本リポジトリの版表記の慣行とする。
- 方式 `docs/vm-resilient-operations.md` は「確立：2026-11-08」の日付のみで版行を持たない。手順 `docs/socket-mode-listener.md` は「状態：運用方式として確立済み（2026-11-08）」で版行を持たない。ロードマップ `docs/vm-operations-rollout.md` は段階ごとの状態と日付のみで版行を持たない。キット `tools/socket-mode-listener/` は、各ファイルに版を持たず、版の担い手は `tools/socket-mode-listener/README.md` である。

### 版を明記する文書と上げ方

版を上げる対象は次の 5 点である。各文書の版は、文書の冒頭の「状態：vX.Y（YYYY-MM-DD 作成／更新）」の行で明記する。版行を持たない文書に初めてフィードバック由来の変更が入るときは、その変更で版行を追加し、版は v1.0 とする（それまでの状態を v1.0 の基準とする）。2 回目以降の変更は下記の上げ方に従う。

| 対象 | 版の担い手 | 上げ方 |
|---|---|---|
| 方式 `docs/vm-resilient-operations.md` | 文書冒頭の「状態：vX.Y」行（なければ本手順で追加する） | 下記の上げ方に従う |
| 手順 `docs/socket-mode-listener.md` | 文書冒頭の「状態：vX.Y」行（なければ本手順で追加する） | 下記の上げ方に従う |
| ロードマップ `docs/vm-operations-rollout.md` | 文書冒頭の「状態：vX.Y」行（なければ本手順で追加する） | 下記の上げ方に従う |
| キット `tools/socket-mode-listener/` | `tools/socket-mode-listener/README.md` 冒頭の「状態：vX.Y」行（なければ本手順で追加する）。キット内の各ファイルには版を書かない | 下記の上げ方に従う |
| 本書 `docs/vm-operations-expansion-feedback.md` | 文書冒頭の「状態：vX.Y」行（作成時 v1.0） | 下記の上げ方に従う |

上げ方：

- 小版（+0.1。例：v1.0 → v1.1）：フィードバック由来の訂正・追記・明確化。完了条件・ゲート条件・目標値を変えない変更は全てここに当たる。
- 大版（+1.0。例：v1.2 → v2.0）：完了条件・ゲート条件・目標値（60 秒）・フィードバック項目自体の変更を伴う変更。所有者の判断を経た変更に限る。
- 版を上げるときは、版行の日付も変更日へ更新する。変更内容は、各文書の末尾の変更履歴（なければ本手順で追加する）に「日付・版・変更内容・PR 番号」の 1 行で残す。
- 一つのフィードバック反映で複数の文書・キットが変わる場合は、変わったもの全ての版を上げる。変わらなかったものの版は上げない。
- 版上げだけの変更（内容の変更を伴わない版行の追加・更新）は行わない。版は内容の変更とセットで上げる。

### 反映から共有までの手順

1. コーディネーターが第 2 部の表で反映候補を決める（優先度つき）。
2. 反映するものは、通常の手順（ブランチ、PR、セルフレビュー、マージ）で反映する。PR 本文には、反映元の #62 の記録コメントの ID と、第 2 部の振り分けを明記する。
3. マージ後、変わった文書・キットの版行と変更履歴を更新する（反映 PR に含めてよい）。
4. 反映内容を #62 のコメントへ記録する（どの展開先のどの記録から、どの文書・キットのどの版へ、何を反映したか）。記録の正本は #62 のコメントである。
5. #agent-plaza へ、記録を知らせる通知を投稿する（通知にとどめ、記録自体は #62 のコメントに置く）。通知には、変わった文書・キットの版と、変更の要約、次の展開先が使う版を書く。
6. 次の展開先の導入は、版上げ後の文書・キットで行う。導入開始前に、使う版が最新であることを確認する。

## 第 4 部：未提出・計測値でない報告への扱い（作法）

### 体感だけの報告は受け付けない

確定文のとおり、値は計測値で返す。体感だけの報告（例：「遅い気がする」「大体うまくいった」）は受け付けない。再現・照合ができないためである。体感だけの報告が #62 へ記録された場合、コーディネーターは次の定型文で返し、計測値での再提出を促す。報告を書き換えたり削除したりはしない（記録は残し、受け付けなかった旨を返す）。

> ご報告ありがとうございます。フィードバックは計測値でのみ受け付けています（体感だけの報告は再現・照合ができないため）。第 1 部のテンプレートの計測条件欄（計測期間・対象環境・計測方法・件数の分母）とあわせて、〈計測方法〉で計測した〈項目〉の値を再提出してください。計測方法は手順書 §8 とキットの計測スクリプト（`measure_wake_latency.py`、`readiness_check.py`）を参照してください。

計測値の一部だけが欠けている場合（例：中央値はあるが分母がない）は、報告全体を拒まず、欠けた条件の補記を求める。定型文の〈項目〉を欠けた条件に置き換えて使う。計測できなかった項目は「未計測」と明記し、体感で埋めない。

### 未提出への扱い

導入完了時または追加の気づきがあったときに記録がない場合（未提出）の扱いは、次のとおりである。

- コーディネーターは、導入完了から次の展開先の導入開始までに記録がない場合、#62 のコメントで 1 回だけ記録を促す。促すときは、テンプレート（第 1 部）へのリンクと、記録の種類（導入完了時／追加の気づき）を添える。繰り返しの催促はしない。
- 未提出のまま次の展開先へ進むかどうかは、コーディネーターが判断する。進む場合は、その旨と理由（例：導入完了時の記録は未提出だが、追加の気づきの記録はある）を #62 のコメントへ記録する。未提出を理由に段階の完了条件を緩めない。
- 未提出の展開先は、第 2 部の集約表で「未提出」として記録し、反映候補の検討対象から外す（記録がないため振り分けできない）。後から記録が提出された場合は、集約表へ追加し、反映候補の検討に含める。
