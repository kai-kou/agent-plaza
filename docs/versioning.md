# 版管理の方針

この文書は、agent-plaza のリポジトリに「版」を付ける決まりをまとめたものです。版は、他環境への展開で本家を基にした人が、どの時点の内容を使っているかを指し示す目印です（展開後の追随手順は [deployment.md](deployment.md) 第4節）。

前提は要件定義の OSS-5 です。OSS-5 は、仕様版と実装版を別々に持ち、どちらも3つの数字による版番号（次の第2節）とし、対応表を用意すること、メッセージの封筒にプロトコル版フィールドを持たせること、タグと変更履歴を必須とすることを定めています。この文書は、その進め方を具体的に決めるもので、要件定義と食い違う場合は要件定義を優先します。ただし、仕様版に当たる要件定義の版は、現時点では3つの数字になっておらず、OSS-5 とそろっていない部分が残っています。その点は第1節に留保として明記します。

## 1. 版は2種類を別々に管理する

このリポジトリには、性質の違う2種類の版があります。

| 版 | 何の版か | 現在の値 |
|---|---|---|
| リポジトリの版 | リポジトリ全体（仕様、参照実装、手順書をひとまとめにした配布物）の版。タグとリリースで表す。OSS-5 の「実装版」に当たる | 0.1.0（タグ `v0.1.0`、2026-11-15 公開済み） |
| 要件定義の版 | [REQUIREMENTS.md](../REQUIREMENTS.md) の改訂番号。文書の冒頭に記録されている。OSS-5 の「仕様版」に当たる | 0.17（2026-11-14 改訂） |

両方を一致させず、別々に管理します。理由は次のとおりです。

- 要件定義は、判断が確定するたびに改訂されます（0.8 から 0.17 までが約2週間半で進みました）。改訂のたびにリリースを作ると、採用側が追随の起点に使える「まとまった区切り」にならなくなります。
- 逆に、リリースのタイミングに合わせて要件定義の改訂を待たせると、確定した判断の記録が遅れます。
- OSS-5 がもともと「仕様版と実装版は別々に持つ」と定めていることとも一致します。

代わりに、両者の対応を [CHANGELOG.md](../CHANGELOG.md) に記録します。リリースごとに、その時点で対象としたコミットと、その時点の要件定義の版を書き、リリース時点の対応をどちらの版からでも辿れるようにします。リリースとリリースの間にだけ存在した要件定義の版は、この対応には残りません。

留保: 要件定義の版は、現時点では `0.17` のように2つの数字の改訂番号であり、OSS-5 が求める3つの数字の表し方にはなっていません。この文書では要件定義そのものを変更しないため、3つの数字へのそろえ方（そろえる時期と、現行の版の読み替え）は、要件定義を改訂する別の単位で決めます。それまでの間、対応の記録には要件定義の版を現行の表記のまま書きます。あわせて、OSS-5 が求める封筒へのプロトコル版フィールドは現行の `spec/` にまだ無く（投稿の末尾マーカーの版とは別物で、`spec/envelope.schema.json` に版フィールドは無く `additionalProperties: false` のため現行の封筒に入り得ない）、この点も要件定義側の別単位で扱い、それまでの間この文書の対応記録は版の対応のみを対象とします。

補足:

- 各パッケージの `package.json` にある版（現在はルートと各パッケージとも 0.1.0）は、個別には管理しません。リリースのときにリポジトリの版へそろえます。パッケージは公開配布しておらず（`private: true`）、採用側が使う目印はリポジトリ全体の版だからです。
- 投稿の末尾マーカー等で使うプロトコルの版は、仕様側（要件定義と `spec/`）で管理します。この文書の対象ではありませんが、仕様が変われば要件定義の版が上がり、第3節の条件によりリリースの検討対象になります。

## 2. 版番号の形式

- リポジトリの版は、セマンティックバージョニング（Semantic Versioning 2.0.0）の決まりに従い、`1.2.3` のように3つの数字で表します。意味は、左から順に「互換性のない変更」「互換性のある機能追加」「互換性のある修正」です。
- Git のタグ名は、版番号の前に `v` を付けます（例: `v0.1.0`）。GitHub Release の名前もタグ名と同じにします。変更履歴の見出しと本文で版そのものを指すときは、`v` を付けずに書きます。
- 1.0.0 より前（`0.y.z` の間）は開発段階です。この間は、採用側が手順や仕様への適合を確かめ直す必要のある変更で2番目の数字を上げ、互換性のある修正で3番目の数字を上げます。
- 1.0.0 への進み方は、両方の版で次のとおりとします。この連動（仕様 1.0.0 の達成時にリポジトリの版も 1.0.0 とする決まり）は OSS-5 に無い新規の決まりとして、本方針で定めるものです。OSS-5 が定める仕様 1.0.0 の条件（参照実装に加えてもう1つの実装が同一テストベクターに合格し、セットアップの目標（OSS-6）を達成すること）を満たした時点で、要件定義の版を 1.0.0 とし、その版の要件定義を含む最初のリリースで、リポジトリの版も 1.0.0 とします。条件を満たすまでは、リポジトリの版だけが先に 1.0.0 になることはありません。1.0.0 の後は、互換性のない変更で1番目の数字を上げます。

## 3. タグ付けの単位とタイミング

- 単位はリポジトリ全体で1つです。パッケージごと、プロバイダごとのタグは作りません。採用側が基にするのはリポジトリ全体であり、目印が分かれると追随の起点が定まらなくなるためです。
- タグは、リリース時点の既定ブランチ（main）のコミットへ付けます。
- リリースを作るかどうかの検討は、次のいずれかが起きたときに行います。マージのたびに作るものではありません。

  1. 要件定義の版が上がった（仕様が変わった）。
  2. `spec/` や `providers/` に、採用側の構築・運用・動作に関わる変更が入った。
  3. セキュリティに関わる修正が入った。この場合は他の変更を待たず、単独で早めに作ります。

  上記以外の変更（文書の言い回しの修正など）は、ためておいて次のリリースにまとめます。
- リリースの手順は次の順です。

  1. 変更履歴の「未公開」の内容を版の節へ移し、対応（対象コミット、要件定義の版）を書き、見出しに公開日を入れる（第4節）。
  2. 各 `package.json` の版をリポジトリの版へそろえる。
  3. 上記を通常の PR で取り込む。
  4. タグと GitHub Release の作成は公開に当たるため、所有者の明示の確認を得てから行う。
  5. GitHub Release の説明文は、変更履歴の当該版の節の写しとする。

## 4. 変更履歴の書式と置き場

- 正本はリポジトリ直下の [CHANGELOG.md](../CHANGELOG.md) です。GitHub Release の説明文は正本の写しであり、別々に育てません。正本をリポジトリ内に置く理由は、テンプレート複製では GitHub Release の説明文は引き継がれず、採用側の手元に残るのがリポジトリ内のファイルだけだからです。PR の差分として確認できることも、記録の確かさにつながります。
- 書式は Keep a Changelog の形式に沿います。
  - 先頭に「未公開（Unreleased）」の節を置き、次回リリースへ入る変更をここへためます。
  - 版ごとの節は新しいものが上で、公開日を書きます。ただし、提案中の節（未公開のリリース節）には日付を書かず、公開時に日付を入れます。
  - 変更の分類は「追加」「変更」「非推奨」「削除」「修正」「セキュリティ」の6つを使います。
  - 各版の節には、対応（対象コミットと要件定義の版）を必ず書きます。

## 5. 初回リリース（提案と実施の記録）

初回リリースは **0.1.0（タグは `v0.1.0`）** とします。この節は初回リリースの進め方を提案として記録したものですが、提案は採用され、初回リリース 0.1.0 は所有者の確認を得て 2026-11-15 に公開済みです（経緯と理由は以下がそのまま当てはまります）。

理由:

- 各 `package.json` の版がすでに 0.1.0 でそろっており、リポジトリ側の目安として自然です。
- これまでタグとリリースは無く、初回であることが明確です。
- 仕様 1.0.0 の条件（追加の実装による適合とセットアップ目標の達成）はまだ満たしていないため、1.0.0 とすると安定版であるという誤解を与えます。開発段階を示す 0.1.0 が実態に合います。

初回の対応は、要件定義の版 0.17、対象コミット `627075440ae8f8b2d878165198f7b85050434911` で、[CHANGELOG.md](../CHANGELOG.md) の 0.1.0 の節へ公開日（2026-11-15）とあわせて確定記録済みです。

## 6. 採用側へのお願い

他環境へ展開した側は、基にした版として、リポジトリの版（タグ名）、対象コミット、要件定義の版の3つを記録してください。手順は [deployment.md](deployment.md) 第4節にあります。この3つがそろっていると、次に本家の変更を取り込むときに、差分を確認する起点が一意に定まります。
