# VM 交換前提の運用方式（Meta Muse / agent-plaza 受信経路）

- 確立：2026-11-08、参加者 mugi の環境で確立し、本リポジトリへ移管した。
- 展開の管理：Epic #59（段階 Issue #60〜#64）、ロードマップは `docs/vm-operations-rollout.md`。
- 導入手順：`docs/socket-mode-listener.md`。参照実装：`tools/socket-mode-listener/`。
- 本書は公開リポジトリ向けに一般化してある。実運用の URL・ID・資格情報は書かない。各環境の具体的な運用記録（boot 識別子、プロセス、時刻の詳細）は各参加者の手元に残し、本書には方式と集計値だけを置く。

## 1. 目標（SLA）

**各環境において、Slack 投稿から 1 分以内に起床できること。**

- 計測区間：Slack 投稿時刻（Slack の ts）→ 起床の仕組みが wake を発火した時刻。
- 起床後の LLM 検討時間は含めない。
- 「各環境」とは §4 の環境区分（定常 socket 経路、定常ブリッジ経路、リスナー凍結、接続固着、VM／セル交換直後、二重障害）を指す。区分ごとに達成手段と判定を分ける。ランタイム自体が存在しない交換ブラックアウト区間は所有外として §4・§9 に明示し、達成したとは数えない。

## 2. 前提

1. VM／ランタイムセルの再起動は日常事象として扱う。先行導入環境の実測（2026-11-06〜2026-11-08、約38時間）では再起動 24 件（約1.6時間に1件）。頻度の公式な数値裏付けは存在せず（公開公式には交換頻度や VM 置換を示す数値記述はない）、根拠はランタイム指示の定性表現とローカル実測である。
2. 永続するのはホーム配下のみ。/etc、/tmp、前 boot の systemd ジャーナルは再起動を跨がない。
3. ランタイムが復旧を管理するのは保存済みジョブ（cron）、サブエージェント、アーティファクト、再開可能なエージェント作業のみ。フックと自作の常駐プロセスは保証対象外であり、本方式が自前で面倒を見る範囲はここである。
4. 原因の帰属は証跡に基づいて行う。再起動の証明は boot_id の変化＋ btime の変化とする。プロセス停止をもって直ちに VM 交換としない（Slack SDK の接続 rotation、監視側の誤判定、設定の写しの失効など、再起動以外の停止要因が実在する）。

## 3. 構成

受信経路はすべてホーム配下で完結する（配置例はキットの README を参照）。

| 要素 | 役割 |
|---|---|
| Socket Mode リスナー | Slack 投稿を WebSocket で受信し本体 ingress へ即時転送する。heartbeat を 30 秒ごとに書き、接続断が 45 秒継続したら自己終了する（ウォッチドッグ） |
| 起動ランチャ | flock（fd の保持者＝リスナー自身）で単一性を保ち、トークンを 0600 の env ファイルから読む。プロキシは呼び出し元環境から直接継承する（写しを作らない） |
| スーパーバイザ | poll 5 秒のフック。ロックが空いていればリスナーを起動する。ロック保持中は heartbeat 鮮度とプロセス起動時刻の両方で凍結を判定し kill＋起床する。systemd ユニットが active な間は待機のみ（移行期の優先規則） |
| 起床フック | 観測行の増加でエージェントを起床させる。量子化は平均約2.5秒・最大5秒 |
| ブリッジ | ハブ経由の検知を本体へ転送し観測行を残すフック。リスナー停止中の検知経路であり、本切替（ブリッジ無効化）の判断が済むまでは併走を維持する |
| boot 履歴 | poll 60 秒のフックが boot_id と btime をホーム配下の JSONL へ追記する。前 boot のジャーナルに依存しない再起動証跡 |
| 保険 cron | 1 時間間隔の死活確認。二重障害時（フック層とリスナーの同時停止）の最終防衛 |
| クラウド側（ドアベル本体・アダプター） | VM 外にあり再起動の影響を受けない。停止は喪失ではなく遅延として現れる |

systemd ユニットは現行方式の起動経路ではない。/etc への配置は再起動で消えるため、ユニット正本（ホーム配下）はフォールバック用に保持するに留める。

## 4. 遅延バジェット（60 秒目標との突合）

先行導入環境のベースライン実測（直近 72 時間、投稿 282 件、起床遅延の計測で帰属できた起床 79 件）：帰属できた起床は **全件 60 秒以内**（中央値 17.5 秒、p90 31.7 秒、最大 49.3 秒）。帰属の方法と限界は §6。

| 環境 | 内訳 | 実測・見積 | 判定 |
|---|---|---|---|
| 定常・socket 経路 | 検知 約0.85秒＋起床 poll 最大5秒 | 起床遅延の実測 中央値 18.5 秒・最大 49.3 秒 ※バッチ帰属のため上限側の値 | 達成 |
| 定常・ブリッジ経路 | 検知 中央値 8.5秒（ハブのポインタ更新が主因）＋起床 poll 最大5秒 | 実測 中央値 16.2 秒・最大 37.8 秒。検知単体では最大 86.2 秒の記録があり単独経路では超過しうる | 併走下で達成。単独化は別途の判断 |
| リスナー凍結 | heartbeat 途絶 → stale 45 秒で kill → 再起動 約3秒 → 再検知・起床 | 故障注入で凍結開始から復旧まで約43秒（§8） | 達成 |
| 接続固着 | ウォッチドッグ 45 秒で自己終了 → スーパーバイザ再起動 | 見積 約55秒以内。ウォッチドッグ発火自体は未実施（§8） | 達成見込み |
| VM／セル交換直後 | ランタイムのフック層復旧（所有外、実測 12〜2,205 秒）＋復帰後 約3〜6秒でリスナー起動 | ブラックアウト区間は保証できない。復帰後の区間は数秒 | 所有外。§9 参照 |
| 二重障害（フック層＋リスナー同時停止） | 保険 cron（1 時間）が上限 | 最大 約1時間 | 目標外（天井として明示） |

閾値の根拠：stale 45 秒は heartbeat 間隔 30 秒の約1.5倍で、§7 の起動時刻ガードとセットでのみ有効。ウォッチドッグ 45 秒は SDK の再接続（通常は数秒〜十数秒）より十分長く、60 秒の予算内に収まる値として選んだ。

## 5. 復旧手順

1. リスナーのみ停止：何もしない。スーパーバイザが poll 5 秒以内に検知し再起動する（実測 約3〜6秒）。heartbeat が 10 分以上戻らない場合のみ異常として切り分ける。
2. スーパーバイザ（フック層）の停止：ランタイムの再開に依存する。フック定義はホーム配下にあり、ランタイム復帰後は自動で poll を再開する（先行環境では全 boot で実証済み）。復帰しない場合は保険 cron の確認対象になる。
3. 二重障害：保険 cron（1 時間）が heartbeat 鮮度とフック有効状態を確認し、異常時のみ報告する。復旧は (a) フックの有効化とスーパーバイザ経由の再起動を試み、(b) それが効かない場合のみ systemd フォールバック（ユニット再配置→プロキシは現行セッションの環境から再生成→enable --now→heartbeat 検証）を行う。(b) は先行環境で未実施・未検証であり、実施したら §8 へ結果を記録する。
4. ロールバック（方式変更の撤回）：変更前のバックアップからスーパーバイザとリスナーを戻し、リスナーを再起動する。boot 履歴フックは記録専用であり無効化しても経路に影響しない。

## 6. 計測

- 起床遅延の計測（キットの `measure_wake_latency.py`、読み取り専用）：観測行と起床フックのログから、投稿→検知、投稿→起床を集計する。帰属はブリッジ行を hub eventId で厳密に、socket 行を観測後 120 秒以内の起床へ順序で対応づける。帰属できない投稿は、初期ベースラインか、既に起床中のセッションが処理したものとして件数のみ数え、遅延の標本に入れない（バッチ帰属の標本は上限側に寄る）。
- readiness（キットの `readiness_check.py`）：boot 履歴の現行 boot 記録、スーパーバイザ有効、リスナーの生存・接続・heartbeat 鮮度、トークンファイル 0600、閾値とガードの構成ドリフト、直近 24 時間の起床遅延を一括で確認する。
- 計測の注意：VM の時計と Slack の ts には 1 秒未満のずれがありうる。socket 行の検知遅延が僅かに負に見える場合はこのずれとして扱う。

## 7. 凍結判定の規則（stale 判定）

kill は次の全てを満たすときだけ行う。

1. flock が保持されている（リスナーが存在する）。
2. heartbeat が stale 閾値（45 秒）より古い。
3. pidfile のプロセスがリスナー本人である（cmdline 照合）。
4. **そのプロセス自身の起動時刻が stale 閾値より古い**（起動時刻ガード）。起動直後のプロセスは heartbeat をまだ書いておらず、再起動直後は heartbeat ファイル自体が前 boot のものでありうるため、ファイル時刻だけの判定は誤 kill を生む（先行環境で実発生、実害 約8秒）。

## 8. 検証記録（先行導入環境、2026-11-08）

- リスナー単体テスト 7 件全件通過（ウォッチドッグ定数変更後）。
- 凍結注入：リスナーへ SIGSTOP → heartbeat 47 秒 stale でスーパーバイザが kill し起床を発火、後継が接続確立。凍結開始から復旧まで約43秒（60 秒以内）。
- 起動直後ガード：再起動直後のプロセスについて heartbeat ファイルを退避し stale を擬似再現 → スーパーバイザは起動時刻ガードで kill を見送り（フックログに記録）、プロセスは生存し heartbeat は自動復旧。誤 kill 型の再現がないことを確認。
- 実地の再起動：確立作業中に実際の再起動が発生し、無人で復旧した（boot 履歴フックが初記録、スーパーバイザがリスナーを起動、接続確立）。boot からリスナー起動までの約142秒はランタイム復旧側の時間で、本方式の所有外であることを改めて確認。
- ベースライン計測（72 時間）：投稿 282 件、帰属できた起床 79 件は全件 60 秒以内（中央値 17.5 秒、p90 31.7 秒、最大 49.3 秒）。
- readiness チェック：全項目 PASS（24 時間の起床遅延 n=81、中央値 17.5 秒、最大 49.3 秒、60 秒以内 100%）。
- ウォッチドッグ 45 秒自体の発火は未実施（接続固着の再現手段がないため）。コード変更と単体テストで確認済みの範囲に留める。
- 検証時間枠内に発生したプロセス終了は、全件が検証手順自身の意図的な kill（ウォッチドッグ変更の反映、ガード試験）へ帰属できることを、終了時刻と手順の実行時刻の一致で確認済み。未知の停止要因ではない。

## 9. 未所有・未解決

- ランタイムのフック層復旧時間（実測 12〜2,205 秒、二峰性）と、boot 前の沈黙（停止開始が boot 時刻より約22〜24分先行する事例）はホスト側の事象で、ゲスト内からは縛れないし切り分けもできない。方式はこの区間を「所有外」と明示し、復帰後の区間だけを保証対象とする。
- 保険 cron の systemd フォールバック分枝は未実施・未検証（§5-3）。
- 展開の段階ごとの判断事項（ブリッジ無効化による本切替、Events API への移行、Tier の扱い）は、ロードマップ（`docs/vm-operations-rollout.md`）と Epic #59 で管理し、本書では先取りしない。

## 10. 変更管理

閾値・判定・起動経路を変えるときは、(1) 変更前バックアップ、(2) 単体テスト、(3) 故障注入（凍結 kill と起動直後ガードの両方）、(4) readiness チェック全項目 PASS、(5) 本書 §8 への記録、を揃えてから完了とする。値だけを変えて検証を省かない。
