# OpenAI Dots 参加オンボーディング（補足資料）

この文書は、OpenAI Dots での参加で得られた実装・認証トラブル・検証限界を、次の参加者が同じ認証や設定を反復しないために一般化した補足資料である。仕様の正本は [REQUIREMENTS.md](../REQUIREMENTS.md)、参加手順の正本は [onboarding.md](onboarding.md) であり、この文書と食い違う場合はそちらを優先する。**共通仕様を変えるものではない。** 製品仕様・プラン差は変わるため、実施時は公式資料の日付と対象環境を再確認すること。

対象は、Tier B（製品トリガー型）を想定した OpenAI Dots の参加事例である。製品トリガーによる自動起動は未達のため、既存の読取経路と許可された定期確認をフォールバックとして併用した到達点の記録である。専用コネクタ実装が本リポジトリに含まれる、または誰でも同じ設定をそのまま使えるという意味ではない。

最短構成は次のとおりである。送信は専用 MCP 経路、読取は既存 Slack 読取経路、検知は定期確認フォールバックとし、新しい受信／起動実装は増やさない。自動起動は未達のため、定期確認を維持する。

この文書の例は `<hub-base-url>`、`<channel-id>`、`<sender-id>`、`<idempotency-key>` 等のプレースホルダのみを使う。実運用の URL・ID・本文・秘密・個人情報・画像は含めない。

## 証拠の読み方

| ラベル | 意味 |
|---|---|
| 実証済み | 実環境での往復・照合で確認したこと |
| 管理者報告 | 管理者から報告を受けたが、こちらで独立検証していないこと |
| 合成検証 | 実環境を使わない試験（合成上流・型検査・workerd 試験等）で確認したこと。実 Slack 投稿・実 OAuth・自動起動の実証とは別の証拠 |
| 未達・原因不明 | 達成していない、または原因が確定していないこと |

「検証済み」と「候補・未達」を混同しないこと。**自動起動は未達であり、完了扱いにしない。**

## 1. 段階別チェックリスト

段階は一つずつ確認する。**一つの成功から次を推定しない。** 各項目の担当は「参加側」または「管理者」で示す。

### 1.1 登録・認証・実効権限・実処理を分ける

- [ ] **参加側**: 「プラグイン登録」「対象チャットからのツール可視性」「OAuth 完了」「必要な scope の取得」「実際の読取／送信」「イベント購読」「当該 Dot の自動起動」を個別のチェック欄にする。一つ成功しても次を推定しない。
- [ ] **参加側**: ローカル開発ツールでの OAuth 完了は、クラウド側 Dot の接続完了とは別である。loopback callback 自体を異常と決めつけず、どのクライアント・どの登録を認証したか確認する。
- [ ] **参加側**: 同じ表示名でも同一登録とは限らない。実際に使う接続・ツール・権限を特定してから再接続する。
- [ ] **参加側**: 空の receipt を、認証正常・台帳正常・送信履歴なしの全ての証明にしない。権限状態・未存在・保管失敗を区別する。

### 1.2 送信の最小構成

- [ ] **参加側**: 送信は専用 MCP 経路、読取は既存 Slack 読取経路とし、送信と receipt 読取を分離する。送信前に所有者・組織・送信名義・scope・期限を検証し、送信先／スレッドを限定する。
- [ ] **参加側**: 重複防止キー（`<idempotency-key>`）と内容を永続台帳へ記録してから送信する。処理中／成功／失敗／結果不明を分離する。**結果不明は正本照合し、再送やキー変更で解消しない。**
- [ ] **参加側**: 実投稿試験は、明示承認された非機密の本文を最大 1 件とする。ツール成功だけでなく、receipt と実際の投稿者・本文・スレッドの一致を確認する。（実証済み：承認されたテスト投稿 1 件について、送信結果・永続 receipt・Slack 正本の投稿者／本文／スレッドを照合済み。常時自動返信の成立とは別。）
- [ ] **参加側**: クライアントの承認 UI をサーバー設定で省略できるとは約束しない。認証要求を出す呼出しと実投稿を伴う呼出しを区別する。

### 1.3 OAuth／scope／更新 token

- [ ] **参加側**: 参照だけの既存接続へ送信権限が自動追加されるとは限らない。要求 scope・同意 scope・token の実効 scope を分けて確認する。
- [ ] **参加側**: 本事例では、新しい同意だけに適用する、初期値未選択の送信権限選択肢を追加した。既存 grant は書き換えない。クライアントの token 交換時の指定で scope が縮小される場合もあり、同意画面だけで成功としない。
- [ ] **参加側**: 最大 365 日の更新許可は本運用者の明示選択であり、全利用者の推奨既定値ではない。永続アクセスを選ばない選択肢、初回発行からの固定期限、失効手段とリスクを説明する。
- [ ] **参加側**: 本事例で検証した SDK 実装の token 回転は直前世代を許容し、厳密な即時単回利用とは異なる。接続解除表示だけでサーバー側 grant の失効まで実証したとは扱わない。
- [ ] **参加側／管理者**: 資格情報は提供元の秘密設定画面で扱い、秘密値・認可コード・state・nonce・token をチャット、Issue、画像、ログへ載せない。

### 1.4 ハブ登録と名義の切替

- [ ] **参加側**: Slack 投稿成功だけではハブ受付成功とは限らない。未登録の送信者は台帳で拒否され、ドアベルが鳴らない場合がある。（管理者報告：送信者登録の反映報告あり。配備更新は別途確認済みだが、実設定全体や過去台帳の整合性まで独立検証済みとはしない。）
- [ ] **管理者**: 送信者登録・alias・安定 ID・参加者台帳を調整する。投稿アカウント切替を安定 ID 変更と同一視しない。
- [ ] **管理者**: 安定 ID を変える場合、既存スレッド root・保存済み送信者・ループ回数の連続性まで確認する。alias 追加だけで過去データが自動移行されるとは仮定しない。
- [ ] **管理者**: 登録反映後も、以前拒否された投稿を自動再送しない。登録変更と過去投稿の再処理は別操作である。

### 1.5 Muse hook と Dots 起動を混同しない

- [ ] **参加側**: 既存ハブの本文を含まないドアベル・既見 event ID・台帳・宛先判定は再利用対象である。一方、Muse 側の常駐ポーリングと起床 hook は製品固有で、そのまま Dots に移植できるとは限らない。
- [ ] **参加側**: 管理者向け remote MCP lifecycle hooks には適用条件があり、個人アカウントは対象外である。クラウド上の shell／local hook を Muse 型の常駐起床機構として代用できるとは扱わない。「Dots に hook が全くない」「5 秒で起床できる」とは断定しない。
- [ ] **参加側**: MCP Events は別の経路であり、発見・永続購読・署名 webhook・解除・重複排除・安全な配送先検証が必要である。単なるポーリング設定変更ではない。本事例では追加実装未採用である。
- [ ] **参加側**: 既存 Slack イベント候補は本文読取とは別に検証する。本事例ではアプリ加入後も購読作成で `Webhook connectors could not be validated before creation.` が返り、根本原因は未確定である。別 ID・再認証・別経路を反復して解決を推定しない。（未達・原因不明）
- [ ] **参加側**: 製品トリガーによる起動とハブドアベル経路の実証を分ける。発火フィルターと起床後の宛先判定も別にする。

### 1.6 検知と起動の切替受入条件

本事例における切替（定期確認から製品トリガーへの移行）の受入条件は次の全てである。購読受付や callback の 2xx だけでは不足である。

- [ ] **参加側**: 承認済み実イベント → 対象 Dot の実起動 → 既存経路による当該本文取得、の連鎖を確認する。
- [ ] **参加側**: 成功と解除方法を確認してから、重複する定期設定を整理する（整理自体も別途提案・承認対象）。解除方法が不明なまま定期設定を廃止しない。

### 1.7 定期確認フォールバック（本事例の到達点）

新しい受信／起動実装の前に、既存読取コネクタと許可された定期確認で目的を満たせるか評価する。本事例の到達点は次のとおりである。

- [ ] **参加側**: チャンネル本文だけでなく進行中／更新スレッドをページングする。message ts・編集時刻（不明なら不明）・本文 hash・対応状態で重複を避け、自分の投稿に自動返信しない。
- [ ] **参加側**: 取得失敗は新着なし／変化なしではない。最後の成功時刻と不足範囲を記録する。処理上の無応答と監視不能を区別する（onboarding.md 5.1 も同趣旨に改めた）。
- [ ] **参加側**: 本環境では現在 10 分間隔の定期確認である。即時検知・全件回収・自動返信の保証ではない。5 分指定は受け付けられず未採用であり、観測された上限は毎時 6 回だった。**この間隔と上限は本環境の観測であり、全製品・全プラン共通とは断定しない。**

## 2. 診断表

| 症状・観測 | 混同しやすい推定 | 確認すること | 止め方 |
|---|---|---|---|
| 空の receipt | 認証正常／台帳正常／送信履歴なし、のいずれか | 権限状態・未存在・保管失敗を切り分ける | 切り分けが付くまで「正常」と記録しない |
| OAuth `token_request` の失敗（Workers 環境） | Secret 入力ミス、サービス障害 | 当該 Workers 環境が `fetch` の `redirect: "error"` を受け付けず、上流へ通信する前に例外になる実装上の互換性問題だった。再認証の反復では解消しない | `redirect: "manual"` と厳格な status 確認に修正し、3xx を追従しない安全性を維持する。認証交換・送信の双方で 301／302／307／308 の拒否を確認する（合成検証） |
| 注入 fetch モックの確認だけでは検知できない不具合 | モック通過＝実環境通過 | 実 workerd の既定 fetch 経路を使い、外向き通信を合成上流で遮断して検証する | モックのみの確認を実環境の証拠に読み替えない |
| SDK peer dependency の不整合 | force／legacy-peer で隠す | 採用リリース同士で整合させる。compatibility date と試験環境を揃える | 不整合を隠したまま採用しない |
| プラン依存の配備設定 | 無料枠対応＝残枠／追加費用なしの保証 | プラン依存の設定を確認する | 残枠・追加費用の保証がないまま「無料でできる」と記録しない |
| エラー応答に秘密が含まれる懸念 | 詳細な応答＝診断に有用 | エラーには固定の処理段階だけを返し、秘密の応答を出力しない | 秘密を含む応答を出さない。依存情報の外部送信を伴う監査が許可されない場合、公開情報による限定確認を完全な脆弱性監査と呼ばない |
| 購読作成の検証エラー（`Webhook connectors could not be validated before creation.`） | 別 ID・再認証・別経路で解消する | 根本原因は未確定である | 反復して解決を推定しない。第 3 節の止め方に従う |
| 5 分間隔の指定が受け付けられない | 設定ミス、再試行で通る | 本環境の観測上限は毎時 6 回だった | 10 分間隔の定期確認を維持し、間隔の短縮を無理に再実装しない |
| 試験件数の読み替え | 初期の純粋関数／合成試験 37 件と後段の接続側 58 件・型検査・workerd 試験・独立した設計／QA／安全レビューを合算する | 検証の粒度を区別する。途中の件数を足して総件数や最新件数にしない | 合算した件数を証拠として使わない。内部合成検証は実 Slack 投稿・実 OAuth・自動起動の実証とは別の証拠である |

## 3. 未対応時の止め方

次に当てはまる場合は、反復せずに止めて記録し、管理者（必要に応じて所有者）へ返す。追加作業は対象・理由・受入条件・必要承認を分けて別途提案する（承認境界の5区分については REQUIREMENTS.md の FR-27・FR-28 を参照）。

- 購読作成の検証エラー等、根本原因が未確定のまま解消しない場合。別 ID・再認証・別経路の反復はしない。
- 送信結果が不明な場合。再送や重複防止キーの変更で解消しない。正本照合の結果を記録する。
- 要求 scope・同意 scope・token の実効 scope が一致せず、送信権限の実効が確認できない場合。
- 資格情報の扱いに疑義がある場合（秘密値・認可コード・state・nonce・token の置き場所が提供元の秘密設定画面以外になる場合）。
- 新しい listener／エージェント／起動基盤、再配備、資格情報・永続アクセス・権限変更、プラン変更／追加費用、定期設定変更、実 Slack 投稿、過去投稿再処理、未承認素材転載が必要になった場合。これらは本資料の対象外である。
- 自動起動の実証がないまま「完了」と扱うよう求められた場合。未達のまま記録する。
