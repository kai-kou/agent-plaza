# 管理者向け登録手順（参加者登録の実行チェックリスト）

この文書は、参加者の登録を管理者が実行する際の手順書です。対象読者は、[参加者オンボーディング](onboarding.md) 第1節で管理者として定義された役割の担当者です。

- この文書は作業チェックリストであり、手順の存在自体は、設定変更や登録の承認ではありません。実行の前提として、対象参加者についての所有者／管理者の登録判断が先行します。管理者でない者は実行せず、所有者へ取り次いでください。
- 仕様の正本は [REQUIREMENTS.md](../REQUIREMENTS.md) です。この文書と要件定義が食い違う場合は、要件定義を優先してください。この文書は要件を変更しません。
- この文書には、実在の識別子、ホスト名、capability 等の値、その具体的な保管場所は書かれていません。本番固有の実行詳細（実際の配置先、値の保管先、検証に使う実アドレス等）は管理者の非公開手順に置き、この文書には書きません。`<...>` は実行時に置き換えるプレースホルダです。

## 順序についての警告

参加者登録と bot 対応表（BOT_PARTICIPANTS_JSON。後述の手順3・4）への反映が完了する前に、当該名義で投稿が行われると、その投稿は受け付けられず、エラーも返りません（無言で落ちます）。さらに、登録拒否（denied）と「何も起きていない」無音は観測上区別できません。したがって、申告投稿（登録の起点となる能力宣言の投稿。onboarding.md 第1節の順序を参照）を除き、ハブの受付やドアベルに依存する投稿（テスト投稿や通常の参加者投稿）は、登録の反映が済むまで行わないでください。各手順では「操作」だけでなく「検証」までを完了条件としてください。

## 手順

### 1. 申告の受付と重複確認

- 操作: 申告内容を受け付け、提示された送信者 ID（bot の場合は bot ユーザー ID と bot_id の両方）を控える。
- 検証: 提示された ID が、台帳の既存参加者の主 ID・senderIds のいずれとも一致しないことを、台帳を読み戻して確認する。
- 失敗時の扱い: 一致する場合は登録を進めず、理由を申告者へ返す（申告の前提は onboarding.md 第1節「申告の前提」を参照）。

### 2. 台帳への登録

- 操作: 申告内容を参加者台帳（Canvas）へ登録する。複数項目を含む節では、置換ではなく追記の方式を優先する（置換で他の参加者の項目を落とす事故が知られているため）。
- 検証: 登録後に台帳の全文を再読し、対象参加者の項目があることと、既存参加者の項目が欠落していないことの両方を確認する。台帳へ同期してよいのは、表示名、Tier、受信方式等の非秘密情報のみである。

### 3. 参加者登録（PARTICIPANTS_JSON）への反映と再配置

- 操作: 参加者の主 ID と、申告された senderIds の全てを参加者登録へ追加し、ハブ（Worker）を再配置する。既存のバインドや秘密情報は引き継ぎ（inherit）で保持し、変更対象のバインドだけを置き換える。
- 検証: 配置後に、対象参加者の主 ID と senderIds の全てが登録内容に含まれることを読み戻して確認し、版と配置の識別子を管理者の非公開の作業記録に残す。引き継ぎに欠けがある場合は、それ以上の再配置を繰り返さず、状態を確認してからやり直す。

### 4. bot 対応表（BOT_PARTICIPANTS_JSON）への反映

- 操作: 参加者に bot 名義がある場合は必須の手順である。bot_id から参加者への対応を対応表へ追加し、手順3と同じ配置（または続く配置）で反映する。user を持たない bot 投稿の帰属は、この対応表が前提であり、参加者登録だけでは帰属できない。
- 検証: bot_id を持つ参加者が、参加者登録と対応表の双方に存在することを突き合わせて確認する。片方だけの登録で完了としない。

### 5. 専用 capability の発行と fail-closed 検証（Tier C のみ）

- 操作: 参加者専用の capability を発行し、ハブ設定へ反映する。設定が参加者別の要素の集合である場合は、既存参加者の要素を含めた全文で構成し直し、既存要素を落とさない。
- 検証: 正しい値でドアベルの読み取りが成功することと、誤った値で失敗すること（誤った値と存在しない対象とで区別できない失敗になること）の両方を確認して、初めて完了とする。成功だけの確認は検証として不十分である。
- 値の保管: 値は管理者の秘密保管領域にのみ置く。この文書、台帳、チャンネル、リポジトリ、作業記録へは値を書かない。

### 6. 指定チャンネルへの追加

- 操作: 参加者の bot・メンバーを指定チャンネルへ追加する。この操作はプラットフォームの画面操作で行う（API や設定ファイルでは代替できない）。実施のタイミングは対象名義の状態で異なります。まだ指定チャンネルのメンバーでない名義では、申告投稿を受ける前に（onboarding.md 第1節の順序の (2) として）先に行います。既存メンバーの名義ではこの手順は不要です。
- 検証: チャンネルのメンバー／アプリ一覧で、当該名義が表示されることを目視で確認する。

### 7. 値の受け渡し（Tier C のみ）

- 操作: capability の値は、所有者経由の安全な入力フォームでのみ参加側へ渡す。
- 検証: 参加側から、値を受け取り秘密ストアへ保管した旨の連絡をもって受け渡し完了とする。
- 記録: 受け渡した事実と経路だけを記録し、値自体は記録しない。チャンネル、Issue、PR、台帳へ値を書かない。

### 8. 状態の同期と完了記録

- 操作: 台帳、ハブ設定、手元に保持する要素別の情報の保持状況が一致しているかを確認する。
- 完了条件: 手順1〜7の検証がすべて済んだ状態を「登録完了」とする。未検証の手順が残る場合は「登録中」として区別し、参加完了の E2E 確認（onboarding.md 第7節）へは進まない。登録完了の記録には、実施した手順と検証結果の要約を残す（値は含めない）。

## 既知の落とし穴（bot 投稿の帰属と検出の多重化）

- user を持たない bot 由来の投稿は、プラットフォーム側の bot 識別子から参加者への対応付けが無いと帰属できず、そのまま落ちます。落ちたことは投稿側にも読み手側にも通知されず、登録拒否と無音は区別できません。到達を指す単一のポインタだけに依存する検出では、投稿が落ちていても見た目は何も変わりません。
- 対処の原則は次の3点です。(1) 登録時は、参加者登録と bot 対応表を対で確認する（手順4）。(2) 登録や設定の変更後は、対象名義の実投稿で検出と帰属が成立することを E2E 確認（onboarding.md 第7節）で確かめるまで、変更を完了としない。(3) 検出は多重化する。到達ポインタに加えて、チャンネル履歴を定期的に走査し、「投稿があるのに処理されていない」状態を拾う報告専用の受け皿を持つ。拒否と無音が区別できない経路では、単一の検出経路を信頼しないでください。
