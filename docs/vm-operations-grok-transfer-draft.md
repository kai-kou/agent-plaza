## 1. この文書の範囲

本書は、mugi 側で確立した運用方式の「原則と計測」を、Grok Bot（yuzu）の別構成へ翻訳したドラフトである。コードの移転ではない。

- 含むもの：移転対象 4 点の対応表（§3）、相手側の採用／不採用の判断欄と知見を方式ドキュメントへ戻す欄（§4）、#63 の受入条件との対応づけ（§5）。
- 含まないもの：相手への送信・依頼、段階 3 の実施そのもの（移転の送信・計測開始の依頼）、段階の逐次前提の変更。
- 逐次前提について：#63 本文の前提「段階 2 のフィードバック反映が済んでいること」は実施・送信の前提であり、本ドラフトはその前提を変更しない。ドラフト作成は、定義と計測の読み替えに限ることで分離している。実際の移転・送信は本単位の範囲外であり、別途判断する。

## 2. 前提となる相手側の構成

yuzu 側の構成は、mugi 側の Socket Mode リスナー常駐とは異なる。正式記録（kai-kou/agent-doorbell-mcp #33・#34）に基づく範囲のみを記す。

- box 常駐ポーラー（5 秒間隔、Bearer 付き HTTPS GET）→ webhook → ルーティン起動。
- G1 adapter 契約：利用者側ポーラーが本体の pull（購読）を監視し、新規イベントでルーティンの webhook を叩いて起動する。起動したルーティンが MCP ツール（list_events / read_event / ack_event）で回収し、処理後に ack_event で確定 ack する。本体は無変更。
- 上記以外の yuzu 側の詳細（ポーラーのログ形式、webhook 発火時刻の記録方法、箱のスリープ検知の手段など）は未確認であり、本書では値を定めない。§3 の「最小項目」は、yuzu 側で記録が可能かどうかの確認を前提とした項目一覧である。

## 3. 対応表（移転対象 4 点）

### 3.1 起床遅延の定義と 60 秒目標

| mugi 側の定義 | 相手側の構成への読み替え | 相手側で計測・記録に必要な最小項目 |
|---|---|---|
| 各環境において、Slack 投稿から 1 分以内に起床できること（方式ドキュメント §1）。計測区間は Slack 投稿時刻（Slack の ts）→起床の仕組みが wake を発火した時刻。起床後の LLM 検討時間は含めない。環境区分は §4 の 6 区分。ランタイム自体が存在しない交換ブラックアウト区間は所有外とし、達成したとは数えない。 | 目標と計測区間はそのまま移す。起床の発火点は、yuzu 側では「ルーティンの webhook を叩いた時刻」または「ルーティンが起動した時刻」のいずれかとし、どちらを発火点とするかは yuzu 側で決める（未確認）。Slack 投稿時刻は Slack の ts を使う。起床後の LLM 検討時間は含めない点も同じ。箱のスリープによる検出遅れは、§6 の窓の扱いとあわせて、遅延の帰属として分けて記録する。 | Slack 投稿の ts。ポーラーが新規イベントを検知した時刻。webhook を叩いた時刻。ルーティンが起動した時刻。発火点として採用した時刻の定義。夜間のスリープ影響があったかどうかの区別（分かる範囲で）。 |

### 3.2 投稿→起床の計測方法

| mugi 側の定義 | 相手側の構成への読み替え | 相手側で計測・記録に必要な最小項目 |
|---|---|---|
| 方式ドキュメント §6。観測行と起床フックのログから、投稿→検知、投稿→起床を集計する（キットの `measure_wake_latency.py`、読み取り専用）。帰属はブリッジ行を hub eventId で厳密に、socket 行を観測後 120 秒以内の起床へ順序で対応づける。帰属できない投稿は件数のみ数え、遅延の標本に入れない。readiness は `readiness_check.py` で一括確認する。計測の注意：VM の時計と Slack の ts には 1 秒未満のずれがありうる。 | yuzu 側は自環境のログから集計できる形にする。ポーラーの検知ログとルーティンの起動ログを突き合わせ、投稿→検知、投稿→起床を集計する。mugi 側の hub eventId による厳密な帰属は yuzu 側の構成にはないため、帰属の方法は yuzu 側で決める（未確認）。帰属できない投稿は件数のみ数え、遅延の標本に入れない扱いは同じにする。集計の道具（スクリプトの有無・形式）は未確認であり、本書では定めない。 | 投稿ごとの Slack ts。検知時刻・起床時刻（3.1 と同じ）。帰属できた件数と帰属できなかった件数。集計期間。中央値・最大値など、共有する集計値の定義（ベースライン共有時に決める）。 |

### 3.3 監視の考え方（存在と鮮度の二層判定、起動時刻の照合）

| mugi 側の定義 | 相手側の構成への読み替え | 相手側で計測・記録に必要な最小項目 |
|---|---|---|
| プロセスの存在と接続・鮮度の二層判定。凍結判定は方式ドキュメント §7 の 4 条件をすべて満たすときだけ kill する。(1) flock が保持されている（リスナーが存在する）。(2) heartbeat が stale 閾値（45 秒）より古い。(3) pidfile のプロセスがリスナー本人である（cmdline 照合）。(4) そのプロセス自身の起動時刻が stale 閾値より古い（起動時刻ガード）。起動直後のプロセスは heartbeat をまだ書いておらず、再起動直後は heartbeat ファイル自体が前 boot のものでありうるため、ファイル時刻だけの判定は誤 kill を生む（先行環境で実発生、実害約 8 秒）。heartbeat 間隔は 30 秒、stale 閾値 45 秒は heartbeat 間隔の約 1.5 倍で、起動時刻ガードとセットでのみ有効。 | 「存在」と「鮮度」を分けて判定する考え方と、「起動直後のプロセスを凍結と誤判定しないために起動時刻を照合する」考え方を移す。対象は yuzu 側の常駐ポーラーと webhook 経路に読み替える。mugi 側の数値（heartbeat 間隔 30 秒、stale 閾値 45 秒、kill の 4 条件）は mugi 側の構成の値であり、yuzu 側へそのまま適用しない。yuzu 側の判定条件・閾値・kill／再起動の要否は yuzu 側で決める（未確認）。 | ポーラーの生存確認の方法と確認間隔。ポーラーの最終活動時刻（heartbeat 相当の記録がある場合）。ポーラー自身の起動時刻。凍結と判定した事例の記録（判定に使った値を含む）。誤判定があった場合の記録。 |

### 3.4 停止・失敗の帰属に必要な記録

| mugi 側の定義 | 相手側の構成への読み替え | 相手側で計測・記録に必要な最小項目 |
|---|---|---|
| 再起動の証跡を永続領域へ残す。方式ドキュメント §2・§3：永続するのはホーム配下のみ。boot 履歴は poll 60 秒のフックが boot_id と btime をホーム配下の JSONL へ追記する。再起動の証明は boot_id の変化＋ btime の変化とする。プロセス停止をもって直ちに VM 交換としない（Slack SDK の接続 rotation、監視側の誤判定、設定の写しの失効など、再起動以外の停止要因が実在する）。 | 停止・失敗の原因を証跡で帰属させる考え方を移す。yuzu 側では、箱の再起動・スリープ、ポーラーの停止、webhook の不達、ルーティンの未起動を区別できる記録を、再起動・スリープを跨いで残る場所へ置く。記録先・形式・保存期間は yuzu 側で決める（未確認）。mugi 側の boot_id・btime という具体的な証跡は、yuzu 側の環境に同じものがあるとは限らないため、そのままの転用はしない。 | 停止・失敗の発生時刻。箱の再起動・スリープがあったかどうかの記録。ポーラーの停止・再開の時刻。webhook の発火・不達の記録。ルーティンの起動・未起動の記録。帰属の結論とその根拠となった証跡。 |

## 6. 窓（yuzu の起床・実施の時間帯）

yuzu 本人の訂正（2026-11-09、kai-kou/agent-doorbell-mcp #33 コメント 6731751690 に記録された yuzu の訂正発言）に基づく内容のみを用いる。

- yuzu は 24 時間いつでも起床・実施できる。
- 07:00〜23:00 JST は、スリープ防止ルーチンが毎時動く時間帯で、検出が遅れにくい目安に過ぎない。
- 夜間は箱のスリープで検出が数十分遅れることがある。
- 上記の扱いは、本書のすべての工程に適用する。時間帯を前提とした工程（特定の時間帯にしか実施できないとする手順、夜間の実施を除外する手順）は本書に置かない。計測のベースラインを共有する際は、夜間の遅れを帰属として分けて扱う（§3.1・§3.4 参照）。
