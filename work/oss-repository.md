# OSS 化要件とリポジトリ名候補 — OSS／リポジトリ担当メモ

- 担当範囲: ライセンス、リポジトリ構成、公開前提の衛生、バージョニングと配布、セットアップ UX、リポジトリ名候補
- 対象プロジェクト: 異なるプラットフォームの AI エージェント同士が Slack の指定チャンネルでリアルタイムに近い形でコミュニケーションできる仕組み。構成要素は共通インフラ仕様、Cloudflare Workers 参照実装、エージェント別アダプター
- 前提: 最終的に public リポジトリとして公開する。利用者が自分のインフラ（Cloudflare 以外を含む）で立てられることを目指す。本メモは要件定義フェーズの提案であり、リポジトリ作成、商標・ドメインの確定調査、法的助言の取得は含まない
- 表記: 本メモの「推奨」は担当提案であり、プロジェクト所有者の決定ではない。未確定事項は第 7 章に集約する

## 1. ライセンス候補の比較と推奨

### 1.1 比較表

| 観点 | MIT | Apache-2.0 | BSD-3-Clause（参考） | MPL-2.0（参考） |
|---|---|---|---|---|
| 概要 | 最も短く単純な寛容型ライセンス。著作権表示と免責の保持を条件に、利用・改変・再配布・商用利用を広く許可 | 寛容型だが条文が精密。表現・特許・商標・免責・コントリビューションの扱いを明記 | MIT に近く、3 条項目は組織名等を宣伝に無断使用することを禁じる条項 | ファイル単位のコピーレフト。MPL 対象ファイルの改変は MPL で公開するが、別ファイルの自社コードと組み合わせやすい |
| 特許条項 | 明示的な特許許諾なし。特許リスクの扱いが黙示的で、企業法務が追加確認を求める場合がある | 明示的な特許許諾あり。各コントリビューターが寄稿に含まれる自らの特許請求項を許諾する。特許訴訟を起こした場合に当該特許に関する許諾が終了する条項（いわゆる報復・終了条項）あり | 明示的な特許許諾なし。MIT と同じ論点がある | 特許許諾あり。ただし対象範囲と終了条項の解釈が Apache-2.0 より複雑になりやすい |
| 商標 | 商標に関する明示規定はほぼなし | 商標を許諾しないことを明記。プロジェクト名・ロゴをライセンスと切り離して管理しやすい | 組織名等の無断使用禁止に触れるが、商標ポリシーそのものではない | 商標を許諾しない旨を含むが、運用の分かりやすさでは Apache-2.0 に劣る |
| コントリビューションのしやすさ | 条文が短く心理的障壁が最も低い。DCO（Developer Certificate of Origin）や CLA（Contributor License Agreement）と組み合わせても説明しやすい | 寄稿が原則として同一ライセンスで入ることが条文上明確（inbound = outbound が読み取りやすい）。企業コントリビューターにとって手続きが予測可能 | MIT と同程度に容易 | 改変ファイルの公開義務を寄稿者が理解する必要があり、アダプターを寄稿する外部開発者に説明コストがかかる |
| 企業利用のされやすさ | 非常に高い。ただし特許の明示がない点を厳格に見る企業では採用審査が長引くことがある | 非常に高い。特許・商標・免責が明示され、大規模 OSS やインフラ系プロジェクトでの採用実績が多い。企業法務が審査しやすい | 高い。MIT とほぼ同等で、特許の明示がない論点も同じ | 中程度。コピーレフトの範囲確認が必要なため、組み込み先の法務審査が MIT／Apache-2.0 より重くなる場合がある |
| 依存ライブラリとの相性 | MIT／BSD／Apache-2.0 など寛容型の依存と衝突しにくい。強いコピーレフト依存を組み込む場合は本プロジェクト側ではなく依存側の条件が支配的になる | 寛容型依存と相性が良い。GPL 系依存とは版ごとに相性が異なるため、依存追加時に個別確認が必要（特に参照実装に直接バンドルする場合） | 寛容型依存と相性が良い。論点は MIT とほぼ同じ | MPL 依存とは自然に合うが、全体を MPL にすると「どのファイルが MPL か」の境界管理が発生する。アダプターを別ライセンスで持ちたい寄稿者との整合が課題になる |
| 仕様文書への適合 | 文書にも適用できるが、仕様の改変・抜粋・翻訳・相互運用実装を作る際の条件が最小限で済む反面、帰属表示の運用を別途文書化したい場合がある | 文書にも適用可能。帰属と変更表示（NOTICE 等）の運用と相性が良い。仕様を実装する行為と特許の関係をコードと一貫して扱える | 文書にも適用可能。MIT とほぼ同じ | 仕様文書をファイル単位コピーレフトで管理する必然性が低く、仕様の抜粋利用や他言語への移植仕様書を作る利用者に負担をかける |
| 本プロジェクトでの弱点 | 特許が明示されない。仕様＋実装の複合体で、他者が仕様を実装する場面でも特許の扱いが曖昧に残る | 条文が長く、個人寄稿者には MIT より重く見える。NOTICE 管理の運用が必要 | MIT に対する明確な優位が本プロジェクトでは小さい | ファイル単位とはいえコピーレフトであり、「仕様に沿った別実装」「独自アダプター」を作る利用者・企業に公開義務の範囲を誤解させる恐れがある |

出典の扱い: 各ライセンスの条文そのものが一次情報である。本メモは条文の要約であり、公開前に必ずライセンス全文と照合する。法的判断が必要な論点（特許、商標、雇用先の職務著作等）は専門家の確認対象として残す。

### 1.2 推奨: Apache-2.0 を第一候補とする

推奨は Apache-2.0 を単独の主ライセンスとする案である。理由は次の 4 点である。

1. 仕様が中核資産であること: 本プロジェクトの価値は実装そのものより「仕様に沿えば異なる実装同士がつながる」点にある。仕様の採用者が企業の場合、特許許諾が明示されているかどうかが採用審査に直結する。Apache-2.0 はこの点を条文で解消できる。
2. 商標と切り離せること: プロジェクト名はライセンスで許諾せず、別途の名称・ロゴ利用方針で管理する設計と相性が良い。フォークが同一名称で公式を名乗る混乱を、ライセンスではなく商標・運用ルールで抑える前提にできる。
3. 企業コントリビューターの予測可能性: 寄稿が同一条件で取り込まれることが読み取りやすく、企業所属の開発者が社内手続きを通しやすい。アダプター寄稿を外部に期待するプロジェクトでは重要である。
4. MPL-2.0 を避ける理由が明確であること: 独自アダプターや別インフラ実装をクローズドに保ちたい利用者を排除しないことが普及条件になる。ファイル単位コピーレフトでも、その境界説明のコストと誤解のリスクは普及初期には見合わない。

MIT が劣るわけではない。個人中心で特許論点が小さい小規模ツールなら MIT の単純さが勝る。本プロジェクトは「共通仕様＋相互運用」を掲げ、企業利用と企業からの寄稿を最初から想定するため、Apache-2.0 の明示性に分がある、という条件付きの推奨である。

### 1.3 仕様文書とコードでライセンスを分けるべきか

結論: 公開初期は分けない。コード、仕様、ドキュメントを Apache-2.0 で統一し、例外を増やさない。

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A. 統一（推奨） | 全体を Apache-2.0 とし、ルートに `LICENSE`、必要に応じて `NOTICE` を置く | 利用者・寄稿者が覚える条件が 1 つ。ディレクトリをまたぐ移動・複製で条件が混ざらない。審査が最速 | 文書専用ライセンスに比べ、仕様の自由な抜粋・再編集に関する慣行との細かな違いが残る場合がある |
| B. 分離 | コードは Apache-2.0、仕様・ドキュメントは CC BY 4.0（帰属表示付きの文書向けライセンス） | 文書の翻訳・抜粋・教材化の条件が文書慣行に合う。仕様だけを参照する人にソフトウェア特許条項を読ませずに済む | 二重管理になる。仕様中のサンプルコード、スキーマ、テストベクターがどちらの条件かで境界争いが起きやすい。寄稿時に同意すべき条件が増える |
| C. 仕様を最も寛容に分離 | コードは Apache-2.0、機械可読なスキーマ・テストベクターのみ CC0 等で切り出す | 相互運用に必須の素材を他実装が取り込みやすい | 対象ファイルの列挙と維持が必須になり、運用を誤ると意図しないファイルまで権利放棄的に扱われる恐れがある |

分離を再検討する条件を先に決めておく。仕様が本リポジトリ外の標準化・他プロジェクトでの逐語採用の対象になった時点で、案 B の導入を改めて判断する。その場合でも、サンプルコードとスキーマはコード側ライセンスに寄せる境界定義を先に書く。

付随する決定事項:

- CLA は初期は導入せず、DCO（コミットへの `Signed-off-by`）で寄稿の出所表明を運用する案を基本とする。CLA は企業寄稿者の手続きを重くし、初期の寄稿障壁になるためである。所有者の所属組織等で CLA が必須になる事情が判明した場合は未確定事項として再判断する。
- ルートに `NOTICE` を置く場合は、帰属表示が必要な外部素材を持ち込んだときだけ更新する運用とし、空の体裁だけのファイルは置かない。
- 依存ライブラリ追加時は、ライセンス名とスキャン結果を CI で確認できる状態にする（第 3 章のスキャンと同列に扱う）。強いコピーレフトの依存を参照実装へ直接組み込む変更は、通常の依存追加より一段高いレビュー対象とする。

## 2. リポジトリ構成案（モノレポ前提）

### 2.1 切り分けの原則

- 仕様（spec）が正本であり、実装は仕様に従う。仕様と実装のディレクトリを分け、仕様変更と実装変更のレビュー観点を分離できるようにする。
- インフラ差分とエージェント差分は別の軸である。`infra/` は「どこで中継基盤を動かすか」、`adapters/` は「どのエージェントをどう接続するか」を担い、互いに直接依存しない。両者は仕様が定義するインターフェースでのみ接続する。
- 利用者が最小構成だけを読むときに不要な部分を丸ごと飛ばせること。最小構成に必要なのは仕様の要約、参照実装 1 つ、アダプター 1 つ、セットアップスクリプトだけであり、構成はその導線を妨げない。
- 生成物（ビルド成果物、生成された型、ロックファイル以外のキャッシュ）はコミットしない。スキーマから生成する型等がある場合は生成手順を `scripts/` に置く。

### 2.2 ディレクトリ構成案

```text
.
├── README.md                  # 概要、最短セットアップへの導線、ライセンス表示
├── LICENSE                    # Apache-2.0 全文
├── NOTICE                     # 必要な場合のみ
├── CONTRIBUTING.md
├── CODE_OF_CONDUCT.md
├── SECURITY.md
├── CHANGELOG.md               # リリースノートの正本（第4章）
├── spec/                      # 共通仕様（言語・インフラ非依存）
│   ├── README.md              # 仕様の読み方、版の対応表への導線
│   ├── protocol.md            # メッセージ交換、順序、再送、重複排除等の本体仕様
│   ├── envelope.schema.json   # 機械可読スキーマ（例: JSON Schema）
│   ├── identity-and-trust.md  # エージェント識別、相関 ID、信頼境界
│   ├── slack-binding.md       # Slack チャンネルを輸送路とする場合の対応付け仕様
│   ├── conformance.md         # 適合の定義、必須／任意項目の区別
│   └── test-vectors/          # 正常系・異常系の入出力例（個人情報を含まない合成データのみ）
├── adapters/                  # エージェント別アダプター
│   ├── README.md              # アダプターの作り方、共通インターフェースへの導線
│   ├── _template/             # 新規アダプターの雛形（最小実装とテスト付き）
│   ├── <agent-a>/             # 具体名は実装対象が決まってから。汎用的な識別子で命名する
│   └── <agent-b>/
├── infra/                     # インフラ別の中継基盤実装
│   ├── README.md              # 実装の選び方、仕様適合状況の一覧
│   ├── cloudflare-workers/    # 参照実装（第一の正本実装）
│   │   ├── src/
│   │   ├── wrangler.toml.example
│   │   └── README.md          # この実装固有の前提とデプロイ手順
│   ├── generic-node/          # 例: 任意の Node.js 実行環境向け実装（将来枠）
│   └── container/             # 例: コンテナで動かす実装・配布物の定義（将来枠）
├── packages/                  # （任意）複数実装で共有するライブラリ
│   └── core/                  # 例: 封筒の検証、署名検証、再送制御など仕様中核の共有実装
├── examples/                  # 最小構成と応用例
│   ├── minimal/               # 第5章の最短手順が対象とする構成
│   └── echo-agent/            # 外部資格情報なしで動作確認できるダミーエージェント
├── scripts/                   # 構築・運用スクリプト
│   ├── setup.sh               # 前提チェックから初期設定までの冪等なセットアップ
│   ├── doctor.sh              # 環境診断（バージョン、未設定項目、疎通の切り分け）
│   ├── dev.sh                 # ローカル開発用エミュレーター起動
│   └── check-secrets.sh       # 公開衛生チェックのローカル実行（第3章）
├── docs/                      # 利用者・運用者向けドキュメント
│   ├── getting-started.md     # 最短手順の本文
│   ├── concepts.md            # 概念と全体像
│   ├── deploy/                # インフラ別デプロイガイド
│   ├── operations.md          # 運用、監視、障害時の切り分け
│   ├── security-model.md      # 脅威モデル、信頼境界、資格情報の扱い
│   └── troubleshooting.md     # 症状別の対処（セットアップのつまずきを含む）
└── .github/
    ├── ISSUE_TEMPLATE/
    ├── PULL_REQUEST_TEMPLATE.md
    └── workflows/             # CI: テスト、秘密情報スキャン、ライセンススキャン、リンクチェック
```

置くものの例と注意:

- `spec/test-vectors/` のデータはすべて合成データとし、実在のメッセージ、実在の識別子、実在のチャンネルの断片を転用しない。
- `adapters/` の各アダプターは、単体テストと「モック輸送路で動く確認手順」を必須とし、実サービスへの接続なしにレビュー可能にする。
- `infra/` の各実装は、対応する仕様版と適合状況（必須項目の実装有無）を各 `README.md` の冒頭に明記する。
- `examples/` は教育用ではなく動作確認用と位置付ける。最小例が古くなって動かない状態を CI で検出できるようにする。

### 2.3 言語・ランタイム方針の論点

利用者の再現しやすさを最優先とし、次の論点として整理する。最終決定は実装担当と所有者の判断事項であり、本メモでは推奨の方向だけを示す。

| 論点 | 選択肢 | 再現しやすさの観点 | 担当所見 |
|---|---|---|---|
| 参照実装の言語 | TypeScript／JavaScript、Python、Go 等 | Cloudflare Workers の参照実装は TypeScript／JavaScript が公式ツールと最も自然に合う。利用者層（Web 開発者）に普及している | 参照実装は TypeScript を第一候補とする。型は仕様のスキーマと対応付けしやすい利点もある |
| 仕様の記述形式 | Markdown＋機械可読スキーマ（JSON Schema 等）を正本にする／特定言語の型定義を正本にする | 前者は言語非依存で他実装が追随しやすい。後者は実装は速いが仕様が言語に引きずられる | 前者を推奨。型定義はスキーマから生成する側に回す |
| アダプターの言語 | 各エージェントの実行環境に合わせる（複数言語を許容）／単一言語に統一 | 接続先エージェントの SDK や起床手段が言語を事実上決めるため、統一は利用者の障壁になる | 複数言語を許容し、統一するのはインターフェースとテストベクターのみとする |
| モノレポ管理ツール | ワークスペース機能のみ（例: パッケージマネージャーの標準機能）／専用モノレポツール導入 | 専用ツールは学習コストとバージョン固定の負担を増やす。初期規模では過剰になりやすい | 初期は導入しない。ビルド・テストは言語標準の手段と `scripts/` の薄いラッパーで揃える |
| バージョン固定 | ランタイム版をファイルで固定（例: `.tool-versions`、`.nvmrc` 相当、ロックファイル必須）／README の文章のみで案内 | ファイル固定は再現性と診断（`doctor`）の両方に効く | ファイル固定を必須とする。ロックファイルは常にコミットする |
| 依存の量 | 参照実装の依存を最小にする／機能豊富なフレームワークを採用する | 依存が少ないほど供給網リスク、ライセンス審査、長期保守の負担が減る | 中核（`packages/core/` 相当）と参照実装は依存最小を方針とする。周辺ツールはこの限りではない |
| テストの実行方法 | 言語横断の適合テスト（テストベクター駆動）／実装ごとの単体テストのみ | 前者は「仕様に合っている」ことを実装横断で示せる。本プロジェクトの存在意義に直結する | テストベクターによる適合テストを必須の仕組みとして設計する |

## 3. 公開前提の衛生ルール

公開後に直すのが最も高コストな領域であるため、private な開発期間中から public 前提で運用する。

### 3.1 秘密情報スキャン

| 層 | 候補 | 役割 |
|---|---|---|
| コミット前（ローカル） | pre-commit フレームワーク＋gitleaks | 秘密情報のパターンをコミット時点で検出する。フック回避（`--no-verify`）を前提にせず、次層と多重化する |
| プッシュ／PR（CI） | gitleaks（履歴全体スキャンを含む）、TruffleHog | ローカルで漏れた場合の最後の防衛線。検出時はマージをブロックする必須チェックとする |
| ホスティング側 | GitHub の secret scanning と push protection（公開後に有効化可能な機能を含む） | プラットフォーム側の検出とアラート。CI スキャンの代替ではなく補完として併用する |
| 補助 | detect-secrets（ベースライン管理） | 誤検出をベースラインで管理したい場合の選択肢。gitleaks との二重運用は初期は不要 |

運用ルール:

- 検出された秘密情報は「削除して再コミット」では不十分とする。履歴に残るため、当該資格情報の失効・再発行を先に行い、履歴の書き換え要否を別途判断する手順を `docs/` の運用手順に明記する。
- サンプルやテストに使うダミーの資格情報は、スキャナが誤検出しない形式（第 3.2 節のプレースホルダ形式）で書き、正規表現の例外リストで誤魔化さない。例外登録が必要な場合は、対象ファイルと理由をレビュー必須とする。
- スキャン対象はコードだけでなく、Issue、PR、ドキュメント、設定例、テストベクター、コミットメッセージを含む。公開直前には履歴全体の再スキャンを必須ゲートとする。

### 3.2 サンプル設定の匿名化ルール

- 実在の値を使わない。実在のワークスペース、チャンネル、アカウント、URL、識別子、メールアドレス、電話番号等をサンプル、スクリーンショット説明、テストデータに転用しない。実物を見ながら書いたサンプルは、値が似ていても転用とみなして作り直す。
- プレースホルダ形式を統一する。例は次のとおりとし、`docs/` と各 `.example` ファイルで同じ形式を使う。

| 対象 | プレースホルダの例 | 備考 |
|---|---|---|
| 汎用の差し替え値 | `REPLACE_ME` | 未設定のまま実行すると検証で失敗する形式にする |
| 環境変数形式の例 | `<your-workspace-id>` のように山括弧＋小文字ハイフン区切り | 実値の書式（桁数、接頭辞）を模さない。実フォーマットに似せると実値と誤認され、スキャナの誤検出も増える |
| トークン類 | `xoxb-EXAMPLE-TOKEN` のように接頭辞の後に `EXAMPLE` を含める | 実際に発行され得る形式と完全には一致させず、コピーしたままでは認証が通らないことを保証する |
| チャンネル等の識別子 | `C-EXAMPLE-CHANNEL` | 実在の ID 体系の桁数を再現しない |
| ドメイン・URL | `example.com`、`example.invalid` | 予約済みドメインのみを使う。実在し得る架空名ドメインは使わない |
| 人名・アカウント名 | 「利用者」「運用者」「エージェント A／B」等の役割名 | ハンドル形式の文字列自体をサンプルに書かない |

- 設定ファイルは実ファイルをコミットせず、`.example` ファイルのみをコミットする。実ファイルは `.gitignore` で除外し、`doctor` スクリプトが「実ファイルが追跡対象になっていないか」も確認する。
- ログ出力の設計にも適用する。デバッグログに資格情報や実識別子を出さないことをアダプター・参照実装のレビュー観点に含める。

### 3.3 実在の名称を持ち込まないためのチェック観点

次を PR レビューと公開前チェックの共通観点とする。

- 実在の Slack ワークスペース名、チャンネル名、チャンネル ID、ユーザー ID、Bot 名が、コード、ドキュメント、コメント、テストデータ、画像の代替テキストに含まれていないか。
- 実在のクラウドアカウント ID、サブドメイン、バケット名、キュー名、デプロイ先 URL が含まれていないか（特に `wrangler.toml` 等の実設定の複写）。
- 特定個人のアカウント名、メールアドレス、実名が、謝辞・サンプル・コミット例等に含まれていないか。コントリビューター表示はホスティングサービスの標準機能に任せ、手書きの一覧で実名・ハンドルを列挙しない。
- 非公開プロジェクトの名称、社内・家庭内等の私的な文脈の固有名詞が、比喩や経緯説明として紛れ込んでいないか。経緯は「要件定義の過程で判明した」のような汎用表現で書く。
- 画像・スクリーンショットを使う場合は、撮影データそのものではなく図版として作り直すことを原則とし、識別子の写り込みを目視でも確認する。

自動化できる部分（既知パターンの grep、スキャナのカスタムルール）は `scripts/check-secrets.sh` と CI に寄せ、自動化できない部分（文脈上の固有名詞）は PR テンプレートのチェック項目で担保する。

### 3.4 ガバナンス文書の要否と内容方針

| 文書 | 要否 | 内容方針 |
|---|---|---|
| `CONTRIBUTING.md` | 必須 | 開発環境の作り方、テストの実行方法、DCO の付け方、仕様変更は通常の PR と分けて提案すること、アダプター追加の手順、匿名化ルール（第 3.2・3.3 節）への同意を含める |
| `CODE_OF_CONDUCT.md` | 必須 | Contributor Covenant 2.1 の採用を第一候補とする。独自文を作成しない。執行の連絡先は公開前提で使える窓口が確定してから記入し、個人の連絡先を書かない |
| `SECURITY.md` | 必須 | 脆弱性の報告方法（公開 Issue ではなく非公開の報告経路を使うこと）、対応範囲、サポート対象バージョン（第 4 章と整合させる）、秘密情報が漏洩した利用者への初動案内（失効が先、履歴削除は後）を含める |
| `LICENSE`／`NOTICE` | 必須 | 第 1 章の決定に従う |
| Issue テンプレート | 必須 | 下記の 4 種を用意する。自由記述のみの運用は初期から避ける |
| PR テンプレート | 必須 | 変更種別（仕様／実装／アダプター／文書）、仕様との互換性への影響、衛生チェック（秘密情報なし、サンプル匿名化、実名なし）、テスト結果の記入欄を含める |

3. 仕様変更提案（RFC 的位置付け）: 動機、変更内容、互換性への影響、移行方法。実装 PR と分けて議論する入口とする
4. 新規アダプター提案: 対象エージェントの公開情報、接続方式、保守の担い手

## 4. バージョニングと配布形態

### 4.1 仕様版と実装版の関係

- 仕様（プロトコル）と実装は別々に版を持つ。仕様が安定資産であり、実装は仕様の改訂速度と独立に直せるためである。
- 各実装のリリースは「対応する仕様版」を明記する義務を持つ。対応表の正本は `spec/README.md` と各実装の `README.md` に置き、利用者が互換性を一目で確認できるようにする。
- 通信上の封筒（envelope）には、仕様のメジャーバージョンに対応するプロトコル版フィールドを含める設計とする（詳細は仕様担当の領域）。これにより、異なる版の実装同士が混在する期間でも、受信側が受理・拒否・変換を判断できる。

### 4.2 セマンティックバージョニングの適用方針

| 対象 | 方針 |
|---|---|
| 仕様 | セマンティックバージョニング（SemVer）を適用する。MAJOR: 互換性を壊す変更（必須フィールドの意味変更、削除等）。MINOR: 後方互換な追加（任意フィールド、任意機能の追加）。PATCH: 誤記の修正、明確化など意味を変えない変更 |
| 参照実装・各 infra 実装 | SemVer を適用する。MAJOR の引き上げ要因には「対応仕様の MAJOR 変更への追随」と「利用者から見た設定・インターフェースの破壊的変更」の両方を含める |
| アダプター | SemVer を適用する。対象エージェント側の仕様変更による追随は、利用者影響に応じて MINOR／MAJOR を判断する |
| 1.0.0 の条件 | 仕様 1.0.0 は、参照実装と少なくとも 1 つの追加実装（別インフラまたは別実装者）で同一テストベクターに合格し、最小構成のセットアップが第 5 章の目標を満たした時点で宣言する。それまでは 0.x とし、0.x の間は MINOR で破壊的変更があり得ることを明記する。ただし 0.x でも封筒のプロトコル版フィールドによる混在動作の扱いは仕様で定義する |
| 廃止（deprecation） | 項目の削除は、少なくとも 1 つの MINOR リリースで廃止予告をしてから次の MAJOR で行う。予告は `CHANGELOG.md` と仕様本文の両方に書く |
| リリース単位 | モノレポのタグは対象を接頭辞で分ける。例: 仕様は `spec/v1.0.0`、参照実装は `workers/v1.2.0`、全体を束ねた節目の配布は `v1.0.0` のような全体タグを別に切る。全体タグと個別タグの二重管理が負担になる場合は、初期は全体タグ＋変更履歴での内訳明記に寄せる案も残す（未確定事項） |

### 4.3 リリース形態

| 形態 | 要否 | 方針 |
|---|---|---|
| Git タグ＋リリースノート | 必須 | タグは前項の規則に従う。リリースノートは `CHANGELOG.md` を正本とし、ホスティングサービスのリリース機能にはその転記または要約を置く。分類は「仕様変更／互換性に影響する変更／追加／修正／セキュリティ」とする |
| テンプレート配布 | 推奨（初期から） | 利用者が自分のリポジトリへ取り込むための最小構成テンプレート（`examples/minimal/` の独立利用が可能な形）を用意する。デプロイ支援ボタンのようなホスティング固有の導線は、特定事業者への依存度を所有者が許容できる範囲で後から追加する |
| コンテナイメージ | 条件付きで推奨 | コンテナで動かす実装（`infra/container/`）を提供する場合のみ、レジストリで版付きイメージを配布する。タグは実装版と一致させ、`latest` のみの利用を推奨しない。イメージには SBOM の添付と署名を将来の検討対象とする。Workers 参照実装そのものはコンテナ配布の対象ではない |
| パッケージレジストリ配布 | 後回し可 | 共有ライブラリ（`packages/core/`）を npm 等で単体配布するのは、外部利用者が現れてからでよい。初期はリポジトリ内参照で足りる |
|  IaC モジュール | 後回し可 | Terraform 等のモジュール化は、対象インフラの実装が安定してから判断する。初期は `wrangler` 等の公式 CLI と手順書で足りる構成を優先する |

## 5. セットアップ UX 目標（要件）

### 5.1 目標値

| 項目 | 目標 |
|---|---|
| 最小構成の定義 | エージェント 2 つが 1 つの Slack チャンネル相当の場で往復のメッセージを交換できること（うち 1 つは資格情報不要の echo 用ダミーで可） |
| 所要時間 | リポジトリのクローンから最小構成の動作確認まで、中央値 15 分以内。初回（前提アカウントの作成を含む）でも 30 分以内を目標とする |
| コマンド数 | ローカルでの試行（ダミー構成）は 5 コマンド以内。実サービス接続まで含めても、手順書上のターミナル操作は 10 コマンド以内に収める |
| 成功の判定 | 手順の最後に自動確認（ヘルスチェックと往復テスト）が用意され、利用者が目視ではなくコマンドの成否で完了を判断できること |
| 失敗時の復帰 | 失敗した手順を最初からやり直さず、`doctor` の指摘に従って不足分だけを直して再開できること。セットアップスクリプトは冪等とし、再実行で壊れないこと |

### 5.2 最短手順の流れ（要件としての骨子）

前提（手順書冒頭に明記する）:

- Git、固定された版のランタイム（第 2.3 節の固定ファイルに従う）
- ローカル試行のみなら外部アカウント不要。実接続には、利用者自身の Slack ワークスペースでアプリを作成できる権限と、選択したインフラ（参照実装では Cloudflare）のアカウント

流れ:

1. クローンと移動（1 コマンド相当）
2. サンプル設定のコピーと、利用者自身の値への差し替え（`.example` から実ファイルを作成。差し替える項目は最小構成で 5 項目以内に抑えることを要件とする）
3. 依存のインストール（ロックファイルに基づく 1 コマンド）
4. 資格情報なしのローカル試行（エミュレーター＋echo アダプターで往復を確認し、ここまでを 5 分以内の到達目標とする）
5. 実インフラへのデプロイ（公式 CLI の 1〜2 コマンド）と、資格情報の設定（シークレット登録は対話的コマンドまたはダッシュボード手順で案内）
6. 実チャンネルでの往復テスト（用意されたテスト送信コマンドで確認）

資格情報の発行・アプリ作成のようなダッシュボード操作は、手順書では「1 ステップ＝1 画面」を原則にスクリーンショットなしの文章で完結させ、値のコピー先（環境変数名）をその場で明示する。

### 5.3 つまずきポイントと回避策

| つまずきポイント | 回避策（要件） |
|---|---|
| Slack 側アプリの権限（スコープ）不足で接続できない | 必要スコープを最小限に絞った一覧を手順書に固定し、不足時に API エラーから不足スコープを特定できる対照表をトラブルシューティングに置く |
| Bot をチャンネルへ招待し忘れてメッセージが流れない | 往復テストが失敗したときの確認順序の筆頭に置き、`doctor` が可能な範囲で未招待を検出・案内する |
| 署名検証用の秘密情報と Bot トークンの取り違え | 設定項目名を用途が分かる名前にし、検証スクリプトが「形式は合っているが用途が違う」ケースを可能な範囲で指摘する。サンプルは第 3.2 節の形式で取り違えを誘発しない |
| イベント受信 URL の検証（チャレンジ応答）が通らない | 参照実装が検証応答を仕様どおり返すことを適合テストに含め、手順ではデプロイ直後に検証用 URL の疎通確認を独立ステップとして置く |
| インフラ側のアカウント識別子やデプロイ先設定の誤り | `doctor` が設定ファイルと環境変数の不整合（未設定、書式、実ファイルの誤コミット）を実行前に洗い出す |
| ランタイム版の差異でインストールや実行が失敗する | 版固定ファイルと `doctor` の版チェックで、手順の早い段階で失敗させる（インストール途中での失敗にしない） |
| 時計のずれや再送・重複でメッセージが二重に流れる | 仕様側の重複排除（相関 ID 等）の実装を利用者が意識しなくてよいことを最小構成の確認項目に入れ、往復テストで重複がないことまで確認する |
| 費用が発生するインフラ操作への不安で手が止まる | 手順書の冒頭に「最小構成で課金が発生するか」をインフラ別に明記し、無料枠の範囲に収まる構成を最小構成の既定とする |

### 6.3 推奨: `agent-plaza`

推奨は `agent-plaza` である。根拠は次のとおりである。

1. 衝突の観点で最も素直である。軽い確認の範囲で完全一致の目立つ先行プロジェクトがなく、語自体の混雑も `agora` や `relay` の系統より低い。
2. 概念との一致が「場」の軸で最も正確である。本プロジェクトはメッセージを運ぶだけの機構ではなく、複数のエージェントが同じチャンネルに集まって対話する場を提供するものであり、広場の比喩は仕様（場と対話の規定）まで含めた全体像と矛盾しない。
3. 汎用性が高い。Slack という固有名も、Workers 等の実装技術も、特定のエージェント名も含まず、将来の輸送路やインフラの追加で名前が陳腐化しない。
4. 実務的な扱いやすさ。綴りが安定し、タイプミスが起きにくく、ハイフン区切りの 2 語でリポジトリ名、パッケージ名、コマンド名への展開もしやすい。

次点は `agent-ferry` とする。中継の動作が名前から伝わる点は `agent-plaza` より優れ、最終決定で「場」より「中継」を前面に出す方針になればこちらが逆転し得る。`agent-relay` は説明力が高いが先行衝突のため除外し、`relayroom` は短さが魅力だが完全一致の先行例があるため次点にも置かない。

採用前の必須確認（本メモの調査では未実施）: GitHub 上での完全一致の再確認、主要パッケージレジストリ（npm、PyPI 等）での同名確認、商標データベースでの同一・類似分野の確認、ドメインの要否判断。これらが済むまで名前は候補として扱う。
