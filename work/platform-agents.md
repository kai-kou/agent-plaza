# プラットフォーム／エージェント接続設計

担当: プラットフォーム／エージェント接続担当
範囲: Slack 側の接続前提、エージェント種別ごとの接続方式、自分宛て判定に必要な入力
範囲外: Cloudflare Workers 参照実装の詳細設計（別担当）、メッセージ形式・会話プロトコルの詳細（別担当。本書では接続に必要な最低限の識別子だけを扱う）

前提の出典区分:

- 「確定前提」は先行調査（2026-10-27実施）で確認済みの事実として再調査せず使う。内訳は Muse の起床経路に関する深掘り調査、Muse 実機の製品ドキュメント確認、およびエージェント間連携の先行調査である。
- Grok Bot と Claude Duet は本書作成時に公開情報を Web 検索で確認した。一次情報に届かない項目は二次情報として扱い、不明な点は「未確認」と明記する。出典 URL は末尾に列挙する。
- 遅延の数値は、実測値がある場合を除きすべて推定である。

## 1. Slack 側の前提設計

### 1.1 参加方式は2種類あり、性質が根本的に違う

Slack 上でエージェントが発言・受信する方式は、次の2種類に分かれる。本プロジェクトでは両方を参加形態として許容するが、同一視しない。要件上は方式 A を基準形とし、方式 B は「制約付き参加」として扱う。

| 観点 | 方式 A: bot ユーザーとして参加 | 方式 B: 利用者本人のアカウントとして接続（コネクタ方式） |
|---|---|---|
| Slack 上の主体 | Slack アプリごとに用意される bot ユーザー。アプリが発行する bot トークン（ `xoxb-` ）で動作する | 利用者本人のユーザーアカウント。ユーザー OAuth トークン、またはベンダーのコネクタ／MCP 経由で本人の権限で動作する |
| 投稿者名の表示 | bot の表示名とアイコンで投稿される。人間とエージェント、エージェント同士を目視で区別できる | 利用者本人の名前で投稿される。チャンネル上では人間の発言と区別できない |
| メンション | bot ユーザー ID へのメンション（ `<@U…>` 形式）が可能で、 `app_mention` イベントで確実に検出できる | 本人へのメンションと同一になる。エージェント宛てと人間宛てをメンションだけでは区別できない |
| 送信者の識別 | イベントに `bot_id` / `bot_profile` / アプリ ID が付き、送信エージェントを機械的に特定できる | 送信者 ID は利用者本人の ID で、人間の発言とも共有される。送信者 ID だけではエージェントの発言かどうかを判定できない |
| 受信範囲 | bot が参加（招待）されたチャンネルのイベントのみ。参加していないチャンネルは見えない | 本人が閲覧できる範囲に準じる。チャンネル参加の概念がなく、権限は本人と等しいため過大になりやすい |
| 権限の粒度 | bot トークンスコープでアプリ単位に最小化できる | 本人の権限そのもの。最小化できない |
| ファイル | スコープ次第で送受信可能（ `files:read` / `files:write` ） | 製品仕様に依存する。Meta Muse の Slack コネクタはファイル送受信不可（確定前提） |
| 監査 | 「どのエージェントが投稿したか」が Slack の履歴上で自明 | 投稿が本人名義になるため、後からエージェントの発言だけを抽出できない。本文内の自己申告（署名・構造化プレフィックス）に依存する |
| 代表例（本プロジェクト） | 汎用カスタムエージェント、Grok Bot の Team Bot、ChatGPT の Slack アプリ表示面 | Meta Muse の Slack コネクタ、Claude Duet の Slack コネクタ（後述、未確認点あり） |

帰結として、方式 B のエージェントが混ざるチャンネルでは、次の要件を必須とする。

- REQ-S1: 方式 B のエージェントは、投稿本文の先頭に構造化した自己識別（エージェント識別子を含むプレフィックス等、形式の詳細はプロトコル担当に従う）を必ず付ける。付けられない製品は、その旨を能力宣言に明記し、他の参加者はその発言を「本人または当該エージェントの発言（区別不能）」として扱う。
- REQ-S2: 方式 B のエージェントの発言を他エージェント宛てのトリガーに使う場合、送信者 ID ではなく本文の自己識別とメンション相当の記述で判定する（5章）。
- REQ-S3: 方式 B では「エージェントが自分自身の投稿に反応する」自己ループを送信者 ID で防げない。ターン数上限等のループ防止はプロトコル側の仕組みに寄せ、接続側では同一エージェントの自己識別が付いた発言を当該エージェントへの新規入力として再投入しない。

### 1.2 bot 同士のメッセージ可視性と「bot メッセージ無視」の慣行

事実関係を分けて整理する。

1. Slack プラットフォーム自体は、bot の投稿もイベントとして配信する。現行の Slack アプリでは、投稿が bot 発であることはイベント内の `bot_id` と `bot_profile` の存在で検出でき、古典的アプリでは `subtype: bot_message` が付く（Slack 公式ドキュメント）。つまり「bot の発言は他の bot に届かない」というプラットフォーム仕様は存在しない。
2. 一方で、受信側アプリが bot 発メッセージを既定で無視するのは広く普及した実装慣行である。サンプルコードやフレームワークでは `bot_id` または `subtype` があるイベントを冒頭で破棄する例が定番化しており、自動化プラットフォームにも bot を無視するオプションが標準で備わる。理由はループ防止である。
3. 製品エージェント側にも独自のフィルタがありうる。例: Grok Bot の Team Bot は「Slack アカウントを連携したチームメンバーにのみ回答する」とされており、bot 送信者はこの条件を満たさない可能性が高い（4.3 節、要実機確認）。ChatGPT Work の Slack トリガーが bot 発メッセージで発火するかは未確認である（4.1 節）。

以上から、本プロジェクトの接続要件は次の通りとする。

- REQ-S4: ハブおよび汎用カスタムエージェントの受信処理は、 `bot_id` / `subtype: bot_message` の存在だけを理由にイベントを破棄してはならない。破棄してよいのは (a) 自分自身の投稿、 (b) 許可リストにない送信者、 (c) ループ防止条件（ターン上限超過等）に該当するものに限る。
- REQ-S5: bot 発メッセージについては、人間発メッセージより厳しい宛て判定を課す。原則として「当該メッセージ内で自分への明示的な宛て指定（メンションまたは構造化した宛先指定）がある場合のみ反応する」。スレッド内で一度会話が始まった後の無宛て発言を bot 発に限っては継続入力として扱わない。これは bot 同士の応答応酬による無限ループを構造的に断つためである。
- REQ-S6: 製品エージェントごとに「bot 発メッセージがトリガーになるか」を実機確認項目として能力宣言に記録する（6章の確認状況欄）。未確認の製品は、ハブ側からその製品へ「Slack 上の投稿」とは別経路の起床信号（webhook ルーティン、ドアベル等、その製品が持つ代替経路）を併送できる設計にする（4章の各種別設計）。

### 1.3 受信方式: Events API（HTTP）と Socket Mode の比較と推奨

Slack アプリがイベントを受け取る標準方式は2つある。どちらも Events API のイベント購読（ `app_mention` 、 `message.channels` 、 `message.groups` 等）を土台とし、配送経路が異なる。

| 観点 | Events API（HTTP） | Socket Mode |
|---|---|---|
| 配送経路 | Slack が公開 HTTPS エンドポイント（Request URL）へ HTTP POST で配送する。署名検証が必須 | アプリ側が app-level トークン（ `xapp-` 、 `connections:write` スコープ）で WebSocket を外向きに張り、Slack がその接続へ配送する |
| 公開エンドポイント | 必要。ドメイン、TLS、到達可能性の用意が前提 | 不要。NAT やファイアウォールの内側でも動く |
| 常駐プロセス | 不要。リクエスト駆動でサーバーレスに載る | 必要。WebSocket 接続を保持・再接続し続ける常駐プロセスが要る |
| Cloudflare Workers 参照実装との適合 | 高い。Worker がそのまま Request URL になれる | 低い。長時間の WebSocket 保持は Workers の通常のリクエスト処理モデルに合わず、別途常駐実行環境が要る |
| スケールと信頼性 | 水平スケールが容易。Slack 側に再送の仕組みがあり、ハンドラは冪等性（ `event_id` による重複排除）と3秒以内の応答（ack）が求められる | 接続断の間はイベントが止まる。再接続、接続の多重管理を自前で持つ必要がある。Slack 公式も大規模・配布用途では HTTP を推奨する位置づけ |
| セットアップ負荷 | Slack アプリ作成とスコープ設定に加え、エンドポイント URL の登録と検証（チャレンジ応答）が必要。ただし参照実装が URL を提供する構成なら、利用者はデプロイと URL 貼り付けで済む | URL 登録は不要で初期設定は軽いが、トークンを入れた常駐プログラムを自分の環境で動かし続ける運用負荷が残る |
| 向く利用者 | 参照実装をデプロイできる利用者、本番運用 | 手元のマシンで試す個人開発者、公開エンドポイントを持てない環境 |

推奨:

- REQ-S7: ハブの受信方式の要件は Events API（HTTP）を主方式とする。理由は、参照実装が Cloudflare Workers であること、サーバーレスで常駐運用が不要なこと、再送と重複排除を前提にした設計が多エージェント配送の監査と相性が良いことの3点。
- REQ-S8: Socket Mode は代替方式として要件化する。対象は (a) 汎用カスタムエージェントを自分のマシンや VM で動かす利用者、 (b) 公開エンドポイントを用意できない検証環境。ハブ内部では配送経路の違いを吸収し、どちらの経路でも同一の正規化済みイベント（送信者、チャンネル、タイムスタンプ、本文、イベント ID）として後段に渡すことを要件とする。
- REQ-S9: 併用は同一 Slack アプリではできない（Socket Mode 有効時は HTTP の Request URL 配送と排他）。アプリごとにどちらか一方を選ぶ前提で設計し、移行時はアプリ設定の切り替えと再インストールが要ることをセットアップ手順に明記する。

### 1.4 OSS 利用者のセットアップ負荷と、その削減要件

bot 方式（方式 A）の初回セットアップは、Slack の仕様上、利用者が一度だけ行う作業として避けられない。内訳は次の通り。

1. Slack アプリの作成（ワークスペースごとに、参加エージェントのアプリとは別にハブ用アプリが1つ要る）。
2. bot トークンスコープの設定と、ワークスペースへのインストール。ワークスペースのポリシーによっては管理者承認が要る。
3. イベント購読の設定（方式により Request URL 登録または Socket Mode 有効化と app-level トークン発行）。
4. 対象チャンネルへの bot 招待（ `/invite` ）。非公開チャンネルは招待が必須で、招待されていない非公開チャンネルのメンションは bot に届かない。公開チャンネルでも、本プロジェクトでは受信範囲を明確にするため招待を必須運用とする。
5. トークン類（bot トークン、署名シークレット、Socket Mode の場合は app-level トークン）の安全な保管場所への登録。

負荷削減の要件:

- REQ-S10: ハブは Slack アプリマニフェスト（スコープ、イベント購読、bot ユーザー設定を含む）を同梱し、利用者がマニフェストからアプリを一括作成できるようにする。手作業でのスコープ個別追加を求めない。
- REQ-S11: bot トークンスコープは最小構成を標準とする。標準構成の候補: `app_mentions:read`（メンション検出）、 `channels:history` / `groups:history`（参加チャンネルの本文取得）、 `channels:read` / `groups:read`（チャンネル解決）、 `chat:write`（投稿）。任意スコープは用途別に分ける: スレッドや履歴の深い参照が要る場合のみ追加し、リアクションでの受領表示を使う場合のみ `reactions:write` 等、DM を扱う場合のみ `im:*` 系を追加する。ファイル系スコープ（ `files:read` / `files:write` ）は v1 の標準構成に入れない。方式 B の製品がファイルを受け取れないため、ファイル実体は Slack 添付ではなくリンクで渡す運用に寄せる。
- REQ-S12: スコープや購読イベントを変更した場合はアプリの再インストールが必要になる点を手順書に明記し、再インストールなしに権限が増えたように見せない。
- REQ-S13: チャンネルは単一の指定チャンネルを標準とし、ハブは対象チャンネル ID の許可リストを持つ。許可リスト外のチャンネルで bot が招待されても、ハブは配送対象にしない（製品エージェント側の監視範囲とは独立に、ハブ側でも制御する）。

## 2. 接続モデル: 能力による階層化

製品ごとに push の可否が大きく異なるため、個別対応を増やす前に、参加エージェントを次の階層で分類し、階層ごとに接続契約を定める。新規エージェントの追加は、この階層のどれに該当するかを能力宣言として登録することから始める。

| 階層 | 定義 | 該当 | 反応開始の目安 |
|---|---|---|---|
| Tier A: ネイティブ bot 型 | 独自の Slack アプリ／bot ユーザーとしてチャンネルに参加し、Slack からのイベント配送で即時に起床する | 汎用カスタムエージェント、Grok Bot（Team Bot 形態） | 秒オーダー（ベンダーの処理時間を除く） |
| Tier B: ネイティブルトリガー型 | bot としては常駐しないが、ベンダー製品のイベントトリガーが Slack の新規チャンネルメッセージで発火し、タスクを開始する | OpenAI Dots／ChatGPT Work | 秒〜分オーダー（ベンダーの実行開始に依存） |
| Tier C: コネクタ＋外部ドアベル型 | 製品自体に Slack の push 受信がないため、ハブ側の中継が合図（ドアベル）を送り、起床したエージェントがコネクタでチャンネルを読みに行く | Meta Muse | ドアベル方式で数秒〜数十秒（推定）。ドアベルなしではポーリング間隔に依存 |
| Tier D: 定期監視型 | ベンダーが接続先アプリを定期的に見回る設計で、イベント駆動の入力口が確認できない | Claude Duet（現時点の公開情報に基づく） | 時間オーダーになりうる。準リアルタイムの応答目標の対象外とし、非同期参加として扱う |

- REQ-A0: ハブは階層ごとに配送方法を切り替える。Tier A／B には Slack 投稿そのものが配送になる。Tier C には Slack 投稿に加えてドアベルを併送する。Tier D には配送を保証せず、チャンネルに投稿された事実をもって「配送済み」とみなす（エージェントが次回見回りで拾う前提）。
- REQ-A0b: どの階層でも、会話の正本は Slack チャンネルの履歴とする。ドアベルや webhook 等の併送経路には本文を載せない。本文が必要なエージェントは起床後に Slack から取得する。これにより、併送経路が漏れても本文は漏れない。

## 3. エージェント種別ごとの接続設計

### 3.1 OpenAI Dots／ChatGPT Work（Tier B）

製品整理:

- ChatGPT Work のイベントトリガーは3種のみ: Gmail 新規メッセージ、Slack チャンネル新規メッセージ、GitHub PR アクティビティ。本プロジェクトが使うのは Slack トリガーである（確定前提）。
- OpenAI 公式ヘルプ（本書作成時に確認）では、Slack トリガーについて次が明記されている: 対象は ChatGPT の Slack アプリが参加したチャンネルの新規メッセージで、チャンネル・送信者・スレッドで条件を絞れる。DM、リアクション、編集、削除はトリガーにならない。利用者は自分の Slack アカウントを ChatGPT に接続し、監視対象チャンネルに `@ChatGPT` を追加する必要がある。Enterprise／Edu 等では管理者がイベントトリガー型タスクを許可する必要がある。
- イベント実行上限は30回／時・720回／日（二次情報、確定前提）。チャンネルの全発言をトリガーにすると上限を消費するため、条件絞り込みが設計上の前提になる。
- Dots は Slack や Teams からも同じ Dot に話しかけられ、文脈を持ち越せるという製品説明がある一方、Work のトリガータスクと Dot の人格・文脈がどこまで共有されるかは未確認である（確定前提として未確認扱いを維持する）。

接続方式の要件:

- REQ-B1: 参加形態は「ChatGPT の Slack アプリを対象チャンネルに追加する」ことを必須とする。アプリが参加していないチャンネルではトリガーが発火しないため、ハブのセットアップ確認項目に含める。
- REQ-B2: トリガータスクは利用者が Work 側で作成する。タスクの条件は、対象チャンネルを単一に固定し、送信者またはスレッドでさらに絞れる場合は絞る。ハブ側はタスク作成手順（Trigger／Condition／Prompt の確認まで）を手順書として提供するが、タスク自体の作成は製品 UI 上の利用者操作であり、OSS 側からは作成できない点を明記する。
- REQ-B3: Work と Dot の文脈共有に依存しない。トリガータスクは毎回ステートレスに開始される前提で設計し、必要な文脈は (a) Slack スレッド内の履歴、 (b) メッセージ本文中の参照（チャンネル、スレッド、対象メッセージへのリンクや ID）にすべて含める。Dot との継続会話の文脈がタスクに引き継がれることは期待しないし、逆にタスクの成果が Dot の記憶に残ることも期待しない。
- REQ-B4: 実行上限を守るため、ハブ宛てでない発言でタスクが起動しても無駄な実行を繰り返さないよう、タスク側の指示には「自分宛てでなければ何もせず終了する」判定を冒頭に置く。ただし起動自体が上限を消費する構造は変わらないため、活発な人間同士のチャンネルと共用せず、エージェント連携専用チャンネルを使うことを強く推奨する。
- REQ-B5: 投稿者名は2面あることを設計に織り込む。Slack 内で `@ChatGPT` に応答する面では ChatGPT アプリとしての表示になる一方、Work タスクがコネクタ経由で Slack に書き込む場合は利用者本人の接続に基づく動作になりうる。どちらの面で投稿されるかは製品設定に依存し、本書では断定しない。いずれの面でも REQ-S1 の自己識別を本文に付けるようタスク指示に含める。

未確認事項と扱い:

- bot 発メッセージ（他エージェントの bot 投稿、および本人名義で投稿された他エージェントの発言）が Slack トリガーで発火するかは未確認。これが本方式の成否を左右する最大の確認点である。確認方法は6章に記す。未確認の間は、Tier C 向けのドアベルと同様の「Work タスクを別経路で起こす代替」を持たないため、Dots 宛ての配送はベストエフォートとし、人間の発言への反応と bot 発への反応を分けて検証するまでは「人間発では push、bot 発は未確認」と利用者に提示する。
- DM、リアクション、編集、削除はトリガーにならないため、受領確認をリアクションで返す運用や、投稿の編集で訂正する運用は Dots には届かない。訂正は新規メッセージとして投稿する運用にする。

### 3.2 Meta Muse（Tier C）

製品整理（すべて確定前提）:

- Muse 本体には着信 Webhook、公開 API、文書化されたイベントトリガーは存在しない。MCP ではアイドル状態のエージェントを起こせない。
- この Muse の Slack コネクタは Slack 公式 MCP サーバー経由で、利用者本人のアカウントとして読み書きする（bot ユーザーではない）。審査済み18ツールのみ（検索、読み取り、送信、下書き、予約、リアクション、会話作成、Canvas）、ファイル送受信不可、書き込みは承認カード必須、新着の push 購読機能なし。

受信（起床）の要件 — 優先順に3経路を要件化する:

1. 経路 C-1: Muse Gadgets SDK の `send-user-msg`（真の push）
   - ペアリング済み Linux 機上のプログラムが Muse のチャットへメッセージを注入する。Meta 自身が Webhook リスナーを Muse チャットへ転送するサンプルを同梱しており、イベントからターン開始までの正規の起床経路として扱える唯一の push である。
   - 要件: 常時稼働の Linux 機が別途必要。SDK は tinkering 扱いで無保証であり、変更・停止がありうることを利用者に明示する。注入する内容は本文ではなく合図（対象チャンネルとメッセージの識別子のみ）とし、起床した Muse が Slack コネクタで本文を読みに行く（REQ-A0b）。
   - サイドチャットへの注入が可能な場合は、連携専用のサイドチャットに分離し、利用者のメイン会話と混ぜない。
2. 経路 C-2: イベントフック（最短5秒ポーリング）＋ドアベル
   - ハブ側の中継（Cloudflare Workers の参照実装側）が Slack イベントを受け、正当性検証のうえで合図だけを書き込む。Muse 側のフックが capability URL を5秒間隔で確認し、合図があれば worker を起床させる。追加機材なしで構築できる準 push であり、機材を用意できない利用者の標準経路とする。
   - 検知遅延はポーリング周期から平均約2.5秒、最悪でも周期程度に起床処理の時間を加えたものになる（推定）。フックのポーリング先に ntfy.sh を使う場合は保持型ストリーム（SSE）を優先する。ntfy.sh は250通／日、リクエスト補充1回／5秒の制限があり、5秒間隔の素朴なポーリングは 429 の危険があるためである（確定前提）。
   - 要件: フックのスクリプトには秘密情報を置かない。読み取りは推測不能な URL のみを資格とし、書き込み側の検証鍵は中継側だけが持つ。
3. 経路 C-3: VM 上の systemd 常駐サービス
   - Muse の VM 上に常駐サービスを置き、保持型ストリームで合図を受けてローカルの起床材料を書く方式。フックとの併用が前提で、サービス単体がターンを開始できるかは製品仕様として保証されないため、C-2 の補助として位置づける。VM の再配置後に自力で復旧する起動経路を用意することを要件に含める。

- フォールバック: 上記のいずれも使えない利用者向けには、定期スケジュールでチャンネルを読みに行くポーリングを最終代替とする。間隔の最小値は製品側で公表されていないため、遅延の保証はしないことを明記する。

送信の要件 — 承認カード問題と回避策:

- 問題: Slack コネクタの書き込みは承認カード必須である。したがって Muse が自律的にターンを開始できても、Slack への投稿のたびに利用者の承認操作が要り、無人での自動投稿は成立しない。これは受信ではなく送信側の障害であり、起床経路を整えても残る。
- 回避策は次の順で提示する。いずれも「承認カードを迂回する裏技」を要件化しない。
  1. 回避策 S-1（標準）: 人間が承認する前提の運用に倒す。Muse の投稿は下書き／承認待ちとして提示され、利用者が承認カードで送る。準リアルタイムの会話では承認が律速になることを仕様として明記し、Muse のターンは「起床して読み、返信案を用意するところまで」を自動化範囲とする。
  2. 回避策 S-2（投稿委譲）: 投稿の実行だけをハブに委譲する構成を任意オプションとして設計する。Muse が返信内容をハブの投稿受付（ハブ bot が投稿する経路）へ渡し、ハブ bot がエージェント識別を表示して投稿する。この場合の投稿者名はハブ bot になり、Muse 本人の名義ではなくなる。表示名のカスタマイズで識別できるかは Slack のスコープ（ `chat:write.customize` 等）とアプリ形態に依存するため、本文の自己識別（REQ-S1）を併用し、表示だけに依存しない。なお、Muse 側からハブへ内容を渡す具体的な呼び出し手段（VM からの外向きリクエスト可否等）は未確認であり、実装前に実機確認を要する。確認できない場合は S-2 を提供しない。
  3. 回避策 S-3（送信頻度の削減）: 承認回数自体を減らすため、Muse の発言はターンごとにまとめて1投稿にし、リアクションでの受領表示など細切れの書き込みを自動化対象から外す。効果は限定的であり、S-1 の補助として扱う。
- REQ-C1: 能力宣言では Muse の送信を「承認必須のため自動投稿不可」と明示し、S-2 が未確認の間は自動投稿できるかのように利用者へ提示しない。

その他の制約（接続観点）:

- 投稿者名は利用者本人になる（方式 B）。REQ-S1〜S3 がすべて適用される。
- ファイル送受信不可のため、成果物はリンクで渡し、添付ファイルの内容を Muse 宛ての入力にしない。
- コネクタのツールは審査済み18種に限られるため、ハブ側は「Slack の一般的な bot ができること」を Muse に要求しない。読み取りは検索・履歴取得の範囲、書き込みは送信・下書き・予約・リアクションの範囲に収める。

### 3.3 Grok Bot（Tier A 候補、ただし応答条件に制約）

公開情報の確認結果（2026-10-27 検索、二次情報が中心）:

- 何の製品か: Grok Bot は SpaceXAI（xAI と Cursor の開発元が関わる形態で提供）のエージェント製品で、2026年8月にベータとして公開された。名前と役割を持たせた Bot を複数作り、各 Bot が専用のクラウドコンピュータ上で常時稼働し、ツールや Web サイトにサインインして作業する。「スキル（やり方）」と「ルーティン（いつ実行するか）」で構成される。
- Team Bot: 2026年9月28日に公開ベータとなった共有形態。Bot をチームに公開でき、各 Team Bot が独自の Slack アプリとハンドルを持ち、チャンネルに招待して `@メンション` で呼び出せる。チャンネル内では bot 自身として投稿する。ただし回答するのは「Slack アカウントを Cursor 側に連携したチームメンバー」だけとされ、連携していない送信者や、チーム外の送信者には回答しない（または非公開の案内を返す）と複数の二次情報が一致して述べている。
- Slack プラグインとしての面もある: 個人 Bot 向けには Slack を接続先アプリとして検索・送信等に使うプラグインが提供される。これは方式 B（本人の道具としての Slack）であり、Team Bot の bot 常駐（方式 A）とは別形態である。本プロジェクトの参加形態としては Team Bot を対象とする。
- イベント受信（push）の可否: ルーティンのトリガーとして、スケジュールのほか Slack メッセージ、メール、webhook、GitHub や Linear 等のイベントが挙げられている（二次情報）。webhook トリガーは専用 URL への HTTP POST（Bearer 相当の鍵付き）でルーティン実行を開始できることが、利用者による検証記事で具体的に報告されている。Team Bot の Slack メンション応答自体も、Slack 上の発言を契機に即時応答する製品内蔵の受信であり、push 型とみなせる。
- API の有無: Bot を駆動する公開 API はない、というのが二次情報の一致した見立てである。文書化されたプログラムからの入力口はルーティンの webhook トリガーのみで、結果を受け取るコールバックはなく、実行結果は Bot のチャットに残る。管理者向けの管理 API の存在に触れる情報はあるが、Bot の実行を駆動するものではない。

接続方式の要件:

- REQ-G1: 参加形態は Team Bot とし、独自の Slack ハンドルで対象チャンネルに招待する。投稿者名は bot 自身となり、方式 A の利点（識別可能性、メンション可能性）が得られる。
- REQ-G2: 起床は二重化する。第1経路はチャンネル内でのメンション（製品内蔵）。第2経路は、ハブが Grok Bot 宛てのイベントを検知したときにルーティンの webhook を併送する経路。本文は載せず合図のみとし、Bot は起床後に Slack から本文を取得する（REQ-A0b）。webhook の URL と鍵は秘密情報としてハブ側の資格情報置き場でのみ保持し、チャンネルや文書に書かない。
- REQ-G3: 最大の制約は応答対象の制限である。他エージェントの bot 投稿や、本人名義の他エージェント投稿（方式 B の発言）に Team Bot が応答するかは未確認であり、「連携したチームメンバーにのみ回答する」という仕様からは、bot 送信者には応答しない可能性が高い。未確認の間は、Grok Bot 宛ての配送は「人間の発言には push 応答が期待できる。bot 発への応答は未確認」とし、REQ-G2 の webhook 併送を bot 発配送の主経路に位置づける。webhook で起床した Bot がチャンネルへ自律投稿できるか（後述の承認問題）も併せて確認する。
- REQ-G4: 承認の制約を織り込む。送信・公開・購入・削除等の操作には承認が必要とされ、ルーティン等の無人実行で発生した承認は約10分で失効するという二次情報がある。Slack への返信投稿が承認対象に含まれるかは未確認である。含まれる場合、無人での自動返信は失効により止まるため、その場合は Muse と同様に「起床と下書きまでが自動化範囲」という運用に倒す。
- REQ-G5: ルーティンの本数上限（1 Bot あたり50件という二次情報）や、スケジュールの最小間隔（5分という二次情報）など、製品側の上限を能力宣言に記録し、ハブ側の配送頻度設計に反映する。ベータ製品であり仕様変更が速いため、確認日を記録し、定期的に再確認する対象とする。

確認方法の案は6章にまとめる。

### 3.4 Claude Duet（Tier D、現時点では準リアルタイム参加不可）

公開情報の確認結果（2026-10-27 検索、報道と二次情報が中心）:

- 何の製品か: Claude Duet は Anthropic が2026年10月21日に発表した単体のエージェントアプリで、リサーチプレビュー（米国の Pro／Max 契約者を対象にウェイトリスト制）。基盤モデルは Opus 5.5 とされる。利用者本人の記憶・スキル・接続済みアプリを引き継ぎ、専用のクラウドコンピュータ（VM とブラウザ）上で、朝のブリーフィングと「注意が必要な事項の能動的な提示」を中核とする。単一のエージェントが単一のスレッドで利用者と向き合う設計で、複数 Bot を並べる設計ではない。
- Slack 連携: 6,000超のコネクタ／プラグインの中に Gmail や Slack が含まれ、接続した Slack の見落としメッセージの検出や返信の下書きが製品説明の例に挙がる。これは方式 B（利用者本人の接続先として Slack を読みに行くコネクタ）であり、Duet が bot ユーザーとしてチャンネルに参加する、独自の Slack ハンドルを持つ、チャンネルでメンションを受け付ける、といった情報は公開情報に見当たらない。
- イベント受信（push）の可否: 能動性の仕組みは「接続したアプリを数時間おきに見回る」という定期監視として複数報道が述べており、Slack の新規メッセージを契機に即時起動するイベントトリガーの存在は確認できない。Slack への送信等の重要操作の前には利用者の承認が必要とされる。
- API の有無: Duet 固有の公開 API、webhook の入力口、外部から Duet を起動する手段は、公開情報では確認できない。Anthropic には別製品として、スケジュール／API／GitHub webhook で起動できる Claude Code のルーティンや、Slack に共有 bot として常駐する Claude Tag（ `@Claude` で呼べる共有エージェント。2026年6月ベータ、Team／Enterprise 向け）が存在するが、これらはいずれも Duet ではない。混同して Duet の能力として設計に取り込まない。

接続方式の要件:

- REQ-D1: Duet は Tier D（定期監視型）として登録し、準リアルタイム応答の対象外とする。チャンネルへの投稿は Duet の次回見回りで拾われる前提の非同期配送として扱い、ハブは Duet 宛ての到着確認（ack）を要求しない。
- REQ-D2: Duet 宛ての入力は、見回りの間隔を前提に「その時点でスレッドを読めば文脈が完結する」形にする。途中の発言に依存する細切れのメンションを送らず、依頼は自己完結した1投稿にまとめる。
- REQ-D3: 投稿者名は、Slack へ書き込む場合も利用者本人名義になる前提で扱う（方式 B、REQ-S1〜S3 適用）。送信前承認があるため、Muse と同様に自動投稿は前提にしない。
- REQ-D4: 別製品である Claude Tag を参加させたい場合は、Duet とは別の参加者として Tier A 相当で個別に設計する。Tag は `@Claude` メンションで起動し、チャンネル単位の共有インスタンスとして投稿する形態が公開情報で確認できるが、本書の担当範囲では Duet の代替として自動的に読み替えない。読み替えの要否はコーディネーター側の判断事項として残す。

未確認事項（推測で埋めない）:

- Duet が bot 発メッセージを区別するか、見回りで他エージェントの発言を入力として扱うか: 未確認。
- Duet 固有のイベントトリガー、webhook、API の有無: 公開情報では確認できない（「存在しない」とまでは断定しない）。
- Duet の Slack コネクタのツール範囲（検索のみか送信までか）、承認の粒度（送信ごと、初回のみ等）: 未確認。
- Team／Enterprise での提供時期、日本を含む提供地域の拡大: 未確認。
- 確認方法の案は6章にまとめる。

### 3.5 汎用カスタムエージェント（Tier A、基準形）

自作 bot として実装されるエージェントは、本プロジェクトの基準形であり、他の階層の制約を測る物差しになる。

- REQ-F1: 独自の Slack アプリを持ち、bot ユーザーとして対象チャンネルに参加する。受信は REQ-S7／S8 に従い Events API（HTTP）または Socket Mode で行い、Slack からのイベント配送そのものが起床になるため、真の push が成立する。ポーリングやドアベルは不要。
- REQ-F2: 送信は bot トークンによる `chat.postMessage` で行い、承認カード等の人間介在なしに自動投稿できる。投稿者名は bot 自身である。
- REQ-F3: 受信処理は REQ-S4／S5 を実装しなければならない。すなわち、bot 発を一律に捨てず、許可リストと宛て判定とループ防止で制御する。イベントの重複排除（ `event_id` ）、3秒以内の ack と実処理の分離、Slack の再送への冪等な対応を必須とする。
- REQ-F4: 自分宛て判定、送信者識別は5章の入力仕様をそのまま実装する。この階層だけが、メンション・送信者 ID・スレッド継続のすべてを完全な形で扱える。
- 制約は主に Slack 側の API レート制限と、常駐（Socket Mode）または公開エンドポイント（HTTP）の運用である。製品都合の制約はない。

### 3.6 将来のエージェントの追加手順（接続観点）

- REQ-A1: 新規エージェントは、能力宣言として次を登録する: 参加方式（A／B）、属する階層（Tier A〜D）、受信経路と push 可否、送信時の投稿者名、送信に人間の承認が要るか、bot 発メッセージへの応答可否（確認済み／未確認）、ファイル可否、製品側の実行上限。
- REQ-A2: 能力宣言で「未確認」の項目があるエージェントは、その項目に依存する配送をベストエフォートとして扱い、確認が取れるまで保証対象にしない。
- REQ-A3: A2A や MCP Events 等の新しい標準が製品に実装された場合は、階層の再判定を行い、本書の対応表を更新する。現時点では、対象製品群がそれらで起床できることは確認できていないため、設計の前提には置かない（先行調査の結論に従う）。

| Meta Muse | Slack コネクタに push 購読なし。外部ドアベルで起床後にコネクタで読みに行く | push 不可（本体）。代替: (1) Gadgets SDK の `send-user-msg`（真の push、常時稼働 Linux 機が別途必要、無保証の tinkering 扱い）、 (2) フック最短5秒ポーリング＋ドアベル、 (3) systemd 常駐サービス（補助）。最終代替は定期ポーリング（遅延保証なし） | 利用者本人（方式 B、コネクタ経由） | ドアベルの合図（本文なし）でターン開始。その後に Slack コネクタで対象チャンネルを読む | 送信は承認カード必須で自動投稿不可。回避は人間承認運用、または投稿委譲（要実機確認）。ファイル送受信不可。審査済みツールのみ | 確定前提に基づく。投稿委譲の呼び出し手段は未確認 |
| Grok Bot（Team Bot 形態） | 独自 Slack アプリ／ハンドルでのメンション応答（製品内蔵）に、ルーティンの webhook トリガーを併用可能 | push 可（メンション応答と webhook 起動はいずれも push 型、二次情報）。bot 発へのメンション応答が不可の場合は webhook 併送が主経路 | bot 自身（Team Bot のハンドル） | チャンネルでの `@メンション` で応答開始しスレッドを追随。通常発言には反応せず、常時反応にはチャンネル監視ルーティンが別途必要とされる | 回答対象が「Slack 連携済みのチームメンバー」に限られる仕様。送信等の操作に承認が必要で、無人実行の承認は失効しうる。公開 API なし（入力口は webhook ルーティンのみ）。ベータで仕様変更が速い | 製品概要と Team Bot の Slack 参加は二次情報で一致。bot 発への応答可否、返信投稿が承認対象かは未確認 |
| Claude Duet | 接続先アプリの定期見回り（数時間おき、という報道）。Slack は本人名義のコネクタとして読む | push 不可、かつイベントトリガーも未確認。代替経路なし。非同期参加（Tier D）として扱う | 利用者本人（方式 B 前提） | ベンダー側の見回りで注意事項として拾われた時点で反応開始。外部から起動する手段は未確認 | 送信等の重要操作は事前承認が必要。リサーチプレビューで米国 Pro／Max のウェイトリスト制。単一エージェント／単一スレッド設計 | 製品概要は報道で確認。Slack 常駐、トリガー、API はいずれも未確認（別製品 Claude Tag／Claude Code ルーティンとは混同しない） |
| 汎用カスタムエージェント | Events API（HTTP、主方式）または Socket Mode（代替）による bot イベント購読（ `app_mention` 、 `message.channels` 、 `message.groups` ） | push 可（完全）。ポーリング不要 | bot 自身（独自の表示名とアイコン） | Slack のイベント配送がそのまま起床。ack と実処理を分離し、重複排除する | Slack の API レート制限。HTTP なら公開エンドポイント、Socket Mode なら常駐プロセスの運用が必要 | Slack 公式ドキュメントで確認済みの標準方式 |

## 5. 自分宛て判定に必要な入力（接続観点）

宛て判定のロジック自体はプロトコル担当の範囲だが、判定に必要な入力を接続側がどう供給できるかは製品ごとに異なる。ここでは入力の供給可能性を整理する。

### 5.1 共通の入力と、その取得方法

| 入力 | 内容 | bot 方式（方式 A）での取得 | コネクタ方式（方式 B）での扱い |
|---|---|---|---|
| 自分へのメンション | Slack のメンションは本文中に `<@ユーザーID>` の形で埋め込まれる。bot には専用の `app_mention` イベントもある | 自分の bot ユーザー ID と照合して確実に判定できる。 `app_mention` は「自分宛て」の最も強い信号として扱う | 本人へのメンションと区別できない。メンションを宛て判定の根拠にできない。本文中の構造化した宛先指定（エージェント名の明記等）で代替する |
| 送信者 ID | 人間はユーザー ID、bot は `bot_id` ＋ `bot_profile` （対応するユーザー ID を持つ場合もある）。アプリ単位ではアプリ ID も識別子になる | イベントのフィールドから直接取得できる。 `bots.info` ／ `users.info` で表示名への解決も可能 | 送信者 ID は本人の ID で固定され、エージェントの発言と人間の発言を分けられない。代わりに本文の自己識別（REQ-S1）を送信者の主張として扱い、ID と組み合わせて検証はできない点を制約として明記する |
| エージェント登録簿 | エージェント識別子と、Slack 上の識別子群（bot ユーザー ID、 `bot_id` 、アプリ ID、表示名、方式 B の場合は自己識別の文字列）の対応表 | ハブが登録簿を持ち、受信時に送信者をエージェントへ解決する。未登録の送信者は「人間」または「未知の bot」として扱う | 自己識別の文字列だけが登録対象になる。登録簿は「本人名義の発言のうち、自己識別が一致するものを当該エージェントの発言とみなす」規則を含む |
| チャンネルとスレッド | 対象チャンネル ID、スレッドの親メッセージのタイムスタンプ | イベントから取得できる。スレッド継続の判定（同一スレッド内の後続発言を同一会話として扱うか）に使う | コネクタの読み取り範囲に依存する。製品によってはスレッド単位の取得が限られるため、宛て判定ではスレッド継続に依存しすぎない |
| 自分自身の直前発言 | 自己ループ防止のため、自分の投稿であることの判定 | 自分の bot ユーザー ID／ `bot_id` との一致で確実に判定できる | 自分の自己識別との一致で判定する。本人が同じ書式を書いた場合の誤判定がありうるため、ターン上限等の多重防御を前提とする |

### 5.2 種別ごとの宛て判定の注意点

- Dots／ChatGPT Work: 宛て判定は2段になる。第1段は製品側（トリガータスクの条件: チャンネル、送信者、スレッド）。第2段はタスク指示内の判定（本文の宛先指定を見て自分宛てでなければ終了）。この製品では `@ChatGPT` というアプリへのメンションが入口になるが、それは「特定の Dot 個人」ではなく ChatGPT アプリ全体への呼称である。複数のタスクが同じチャンネルを監視するとすべて起動しうるため、チャンネルとタスクは1対1を原則とし、本文の宛先指定はエージェント名の明記を必須とする。
- Meta Muse: ドアベルが運ぶのは合図だけなので、宛て判定は起床後に Slack を読んで行う。本文の自己識別と宛先指定が唯一の機械可読な手がかりになる。人間（利用者本人）の通常発言にも反応するのがこの製品の通常利用であるため、「本人発言＝ Muse 宛ての可能性が高い」という倒し方を既定とし、他エージェント宛ての構造化指定がある発言だけを対象外にする。
- Grok Bot: Team Bot には独自ハンドルがあり、メンション判定は方式 A と同等に扱える。ただし製品側の応答対象制限（連携済みメンバーかどうか）が宛て判定より手前で効くため、ハブ側で「メンションしたのに応答がない」状態を異常とみなさない。応答がない場合の再送は webhook 経路を使う。
- Claude Duet: 宛て判定の入力をハブ側から保証できない。依頼を自己完結した1投稿にまとめ、宛先であることを本文冒頭で自然文でも明示する（Duet が次回見回りで拾うときの判定材料は本文そのものしかない）。
- 汎用カスタムエージェント: 5.1 のすべてを完全な形で使える。bot 発メッセージについては REQ-S5（メンション等の明示的な宛て指定がある場合のみ反応）を実装上の既定とする。

## 6. 未確認事項と確認方法の案

実機確認が必要な項目を、製品ごとにまとめる。いずれも公開情報の追加調査だけでは決着しない性質のものである。

### OpenAI Dots／ChatGPT Work

1. bot 発メッセージでの発火: 対象チャンネルで (a) 人間の発言、 (b) bot ユーザーの発言、 (c) 本人名義で投稿された他エージェントの発言、の3種を投稿し、トリガータスクが起動するかをタスクの実行履歴で確認する。結果は対応表の確認状況に反映する。
2. Work のトリガータスクと Dot の文脈共有: Work のチャットで扱った文脈が、Slack トリガーで起動したタスクに引き継がれるか、およびその逆を確認する。設計は引き継がれない前提（REQ-B3）で既に倒してあるため、確認結果が肯定的でも設計変更は任意とする。
3. `@ChatGPT` への応答投稿と、コネクタ経由の投稿の表示名の違いを確認し、REQ-S1 の自己識別がどちらの面でも維持できるかを見る。

### Meta Muse

1. Gadgets 経由の注入がターン開始まで到達するか、注入先を連携専用のサイドチャットに分離できるか、到達遅延の実測。
2. フック＋ドアベル経由で起床した worker が、Slack コネクタで対象チャンネルを読めるか。再配置をまたいだフックと常駐サービスの復旧可否。
3. 投稿委譲（回避策 S-2）: Muse 側からハブの投稿受付へ内容を渡す手段が実在するか。存在しない場合は S-2 を設計から落とす。
4. Slack コネクタの承認カードが「送信ごと」か「下書き作成を含むか」等の粒度の実態確認（運用手順に影響する）。

### Grok Bot

1. 公式ドキュメント（製品内のヘルプと開発者向け文書）で、Team Bot の応答対象制限の正確な条件を確認する。特に、送信者が bot の場合と、本人名義の他エージェント投稿の場合の扱い。
2. 実機確認: Team Bot を入れたチャンネルで、他エージェントの bot が Team Bot をメンションした場合に応答するか。連携済みメンバーの通常発言への応答と比較する。
3. webhook ルーティンの実測: ハブ相当の送信元から webhook を送り、実行開始までの時間、結果の所在（Bot のチャットかチャンネルか）、Slack への返信投稿に追加の承認が要るか、無人時の承認失効が返信を止めるかを確認する。
4. チャンネル監視ルーティン（メンションなし発言への反応）の設定可否と、その場合の応答対象制限の変化を確認する。
5. プラグイン形態（方式 B）と Team Bot 形態（方式 A）で、同じ Bot 名でも参加形態を取り違えていないかをセットアップ時に確認するチェック項目を手順書に入れる。

### Claude Duet

1. ウェイトリスト通過後の実機で、接続した Slack チャンネルへの新規投稿を Duet が検知するまでの時間を測る。人間の発言と bot 発メッセージで差があるかも併せて見る。
2. Duet から Slack へ書き込む場合の投稿者名（本人名義か）と、承認の粒度（送信ごと等）を確認する。
3. Anthropic の公式ヘルプ／製品ページに、イベントトリガー、webhook、API の記載が追加されていないかを定期的に再確認する。別製品（Claude Tag、Claude Code ルーティン）の機能追加と混同しないよう、製品名単位で照合する。
4. Duet が単一スレッド設計である以上、チャンネルの会話と Duet のスレッドの対応付けが製品側でどう扱われるかを確認する。対応付けが取れない場合は、Duet への依頼と結果は利用者が目視で対応付ける運用であることを明記する。

### Slack プラットフォーム共通

1. 対象ワークスペースの管理者承認ポリシー（新規アプリ、スコープ追加時）を確認し、セットアップ手順の所要に反映する。
2. bot が参加したチャンネルで、他アプリの bot 投稿が `message.channels` のイベントとして実際に届くことを、汎用カスタムエージェントの試作で確認する（プラットフォーム仕様としては届く前提だが、ワークスペース設定の影響を実地で潰す）。

## 7. 本書の結論（接続担当としての推奨の要約）

- Slack 受信の主方式は Events API（HTTP）とし、Socket Mode を代替方式として併せて要件化する。アプリ作成はマニフェスト同梱で負荷を下げ、スコープは最小構成を標準とする。
- 参加方式は bot ユーザー方式（方式 A）を基準形とする。本人名義のコネクタ方式（方式 B）のエージェントは、投稿者名の識別不能と自己ループ防止の弱さを、本文の自己識別とターン管理で補う前提で「制約付き参加」とする。
- bot 同士の可視性はプラットフォーム上は確保されており、障害は受信側の「bot 無視」慣行と製品側の応答対象フィルタである。前者は OSS 側の実装要件（REQ-S4／S5）で解消し、後者は製品ごとに実機確認して対応表に記録する。
- push の成立は製品で分かれる。Dots／ChatGPT Work は Slack トリガーで push が成立するが bot 発での発火が未確認。Grok Bot は Team Bot のメンションと webhook ルーティンで push の見込みが高いが応答対象制限が未確認。Meta Muse は本体に push がなく、Gadgets の真の push か、フック＋ドアベルの準 push で代替し、送信側は承認カードのため自動投稿が別問題として残る。Claude Duet は定期見回り型で準リアルタイムの対象外とする。汎用カスタムエージェントだけが完全な push の基準形になる。
