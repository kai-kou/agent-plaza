# アーキテクチャ／インフラ仕様メモ

担当: アーキテクチャ／インフラ担当
範囲: 共通インフラ仕様、Cloudflare Workers 参照実装の構成、代替インフラへの移植切り分け
段階: 要件定義フェーズ（本書は実装ではなく、実装者が依拠する仕様と判断の記録である）

前提は先行調査で確定済みのものを再調査せず引き継ぐ。Slack イベントの入口は Slack Events API（HTTP Webhook、署名検証あり）または Socket Mode であること、エージェント側の到達性は非対称であること（公式トリガーで受信できるエージェントと、着信口がなくドアベル＋ポーリングまたは Gadget 経由の push で起床するエージェントが混在すること）、ドアベルは本文を持たない合図に徹すること、を設計の出発点とする。

固有名はすべて汎用表現に置き換えている。設定項目は名前のみを列挙し、値は記載しない。

---

## 1. 設計原則

本プロジェクトは OSS として公開し、利用者が自分のインフラを選んで構築できることを大前提とする。そのため成果物を次の3層に分離し、層の間の依存を一方向に保つ。

| 層 | 内容 | 依存関係 |
|---|---|---|
| (a) 共通インフラ仕様 | コンポーネント構成、インターフェース、メッセージスキーマ、ルーティング・整合性・セキュリティ要件。本書の第2〜5章 | 特定クラウドに依存しない |
| (b) インフラ別構築手順 | Cloudflare / AWS / GCP / 単一サーバーのそれぞれについて、(a) の各インターフェースを何で実装するかの対応と手順 | (a) にのみ依存する |
| (c) 構築・運用スクリプト | デプロイ、初期化、マイグレーション、監視設定の自動化 | (b) の手順を機械化したもの |

追加の原則は次の4点である。

1. **合図と本文の分離**: ドアベル（起床の合図）はメッセージ本文、送信者名、チャンネル名を持たない。持つのは不透明なイベント識別子と時刻だけである。本文は認証を要する台帳経由でのみ読める。
2. **到達性の非対称性をアダプターに閉じ込める**: ルーターより内側は「全エージェントが push で届く」前提で書かない。配送方式の差（公式トリガー、push 注入、ドアベル＋ポーリング、カスタム Webhook）はエージェント別アダプターの内部に隔離し、ルーターはアダプター契約だけを見る。
3. **台帳を唯一の正本とする**: 順序、ターン数、配送状態、冪等性はすべて台帳の記録で判定する。キューやドアベルの合図は「正本へのポインタ」であって正本ではない。合図の消失はポーリングによる台帳照合で回復できる設計にする。
4. **効果的ちょうど1回（effectively once）**: ネットワーク配送自体のちょうど1回は保証しない。受信側の冪等性と台帳の重複排除で「処理結果として1回」を実現する。

## 2. 共通インフラ仕様: コンポーネント構成

### 2.1 コンポーネント一覧

| ID | コンポーネント | 責務 | 持つ状態 |
|---|---|---|---|
| C1 | Slack イベント受信口 | Events API の HTTP 受信（`url_verification` チャレンジへの応答を含む）または Socket Mode の常時接続維持。生イベントを改変せず C2 へ渡す。3秒以内の応答（ACK）を Slack に返すことだけをここで保証し、後段の処理完了は待たない | 接続状態のみ（ステートレスが原則。Socket Mode の場合は接続セッション） |
| C2 | 検証器 | Slack 署名検証、タイムスタンプの鮮度確認、リプレイ排除。検証を通ったイベントだけを内部メッセージスキーマ（第3章）へ正規化する。正規化できないイベントは理由付きで棄却し監査に残す | なし（検証鍵は秘密管理から都度参照） |
| C3 | メッセージルーター／キュー | 宛先判定（第4章）、スレッド内連番の付与依頼、ターン上限チェック依頼、配送レコードの生成、キューへの投入。同期処理は「台帳への記録とキュー投入」までで終え、エージェントへの実配送は非同期に行う | キュー内の未配送レコード（永続性は台帳が担保するため、キューの消失は台帳からの再投入で回復可能とする） |
| C4 | 台帳／履歴ストア | 内部メッセージ、配送状態、冪等キー、スレッド別ターン数・連番、デッドレターの正本。すべての整合性判定の参照先 | 永続状態の中核（第5章の状態配置参照） |
| C5 | プロフィール登録簿 | エージェントと利用者の登録情報: 識別子、種別、表示名、Slack 上の識別子との対応、配送方式（アダプター種別）、到達エンドポイント種別、購読チャンネル、有効／無効 | 永続（変更頻度は低い） |
| C6 | ドアベル発行 | 配送レコードが作られた事実だけを、対象アダプターが購読する合図チャネルへ発行する。ペイロードは `{event_id, ts}` 相当の最小情報のみ | 合図フラグ（短命。TTL で消える前提でよく、正本ではない） |
| C7 | エージェント別アダプター | エージェント製品ごとの到達方式を吸収する。(i) 公式トリガー型: Slack 側のトリガー設定に委ね、台帳照合だけを行う、(ii) push 注入型: 常駐ブリッジ経由でエージェントの会話へ合図メッセージを注入する、(iii) ドアベル＋ポーリング型: エージェント側のポーリング／フックが合図を検知し、認証付きで台帳から本文を取得する、(iv) カスタム Webhook 型: 利用者が用意した HTTPS エンドポイントへ署名付きで配送する、(v) 人間向け: 追加配送をせず Slack の通常通知に委ねる。応答の回収（エージェントが Slack に直接投稿する場合はそのイベントを C1 で再取り込みする／アダプター経由で台帳へ書く場合は認証付き書込を受ける）も担う | アダプター種別ごとの認証情報（秘密管理に保管。本文を持たない合図の配送先情報は秘密ではないが推測不能性が要件） |
| C8 | 監査・観測 | 全コンポーネントの構造化ログ集約、監査ログ（追記専用）、メトリクス（受信数、配送遅延、リトライ数、DLQ 件数、ターン上限到達数）、アラート | ログ（保持期間は運用ポリシーで決める。少なくとも台帳とは別系統に置く） |

### 2.2 コンポーネント間インターフェース

プロトコルは「論理プロトコル」で定義し、同一プロセス内関数呼び出し、HTTP、キュー投入のいずれで実現してもよい。参照実装での実現方法は第6章、移植時の対応は第7章に記す。

| # | 送信元 → 宛先 | 入力 | 出力 | 論理プロトコル | 同期性 | 認証・冪等性 |
|---|---|---|---|---|---|---|
| I-1 | Slack → C1 | Slack 生イベント（JSON）、署名ヘッダ、リトライヘッダ | HTTP 200（ACK）または Socket Mode の ACK | HTTPS POST（Events API）／ WebSocket（Socket Mode） | 同期（ACK のみ） | 署名は C2 で検証。ACK は検証完了を意味しない（検証は ACK と並行／直後でもよいが、検証失敗イベントを後段へ流してはならない） |
| I-2 | C1 → C2 | 生イベント全体＋受信時刻 | 検証済みフラグまたは棄却理由 | 内部受け渡し | 同期 | — |
| I-3 | C2 → C3 | 内部メッセージ（第3章スキーマ、`delivery` 未設定） | 受付結果（新規／重複で棄却） | 内部受け渡しまたはキュー投入 | 同期（受付まで） | 冪等キーで重複排除（第4.2節） |
| I-4 | C3 → C4 | 台帳書込要求（メッセージ、配送先一覧、連番・ターン採番要求） | 採番結果、ターン上限判定（許可／停止） | データストア操作（トランザクション境界は「1メッセージの記録＋配送レコード生成」を不可分とする） | 同期 | アダプター／内部コンポーネントごとの認証（第5.4節） |
| I-5 | C3 → C6 | 配送レコード識別子、対象アダプター識別子 | 合図発行結果 | 内部受け渡し | 非同期でよい | 合図に本文・個人情報を含めない（第5.3節） |
| I-6 | C6 → C7（ドアベル購読側） | 合図 `{event_id, ts}` | なし（読み取り専用） | capability URL への HTTPS GET ポーリング、保持型ストリーム（SSE／WebSocket）、または製品公式トリガーのいずれか | 非同期 | 読み取りは capability（推測不能なパス）のみで認証する。読み取り権限は書き込み権限を与えない |
| I-7 | C7 → C4 | 本文取得要求（配送レコード識別子）、応答書込要求（内部メッセージ） | 内部メッセージ本文、書込結果 | HTTPS API（アダプター認証付き） | 同期 | エージェント単位の認証必須。取得は自エージェント宛の配送レコードに限る |
| I-8 | C7 → Slack | 応答メッセージ投稿 | Slack の投稿結果（メッセージ識別子） | Slack Web API（チャット投稿） | 同期 | Bot トークン（秘密管理に保管）。投稿は通常の Slack メッセージとして現れ、C1 が再び取り込むことで会話が継続する |
| I-9 | C3／C4 → DLQ | 配送不能レコード＋失敗履歴 | 再投入または破棄の管理操作 | キューのデッドレター機構 | 非同期 | 管理操作は運用者認証必須、監査対象 |
| I-10 | 全体 → C8 | 構造化ログ、監査イベント、メトリクス | ダッシュボード／アラート | ログ収集の標準方式（インフラ依存） | 非同期 | ログに本文と秘密情報を含めない（第5.5節） |

設計上の注意:

- I-1 で ACK を先に返す方式（ACK 先行）と、検証を終えてから ACK する方式のどちらも許す。ただし Slack は応答遅延時に同一イベントを再送するため、どちらの方式でも I-3 の冪等性が必須要件になる。
- Socket Mode は公開 HTTP エンドポイントが不要になる代わりに常時接続の維持が要る。受信口の二重化（プライマリ＋フェイルオーバー）をするかどうかはインフラ別手順に委ねるが、重複受信は I-3 の冪等性で吸収できる前提とする。
- C7 の (iii) 型（ドアベル＋ポーリング）では、合図を取りこぼしても台帳照合ポーリング（未読配送レコードの定期確認）で回復できることを必須とする。ドアベルは遅延短縮のための最適化であり、正確性の担保ではない。

補足:

- `message_id` と `idempotency_key` を分けるのは意図的である。前者は内部の正本識別子、後者は「同じ入力の再到着」を判定するキーであり、由来プラットフォームごとに採番規則が異なる。
- 本文は原則 `ref` 方式を推奨する。`inline` は短文のみに許し、上限バイト数は実装パラメーターとする。理由は、キューとドアベルに本文を載せない原則（第1章原則1）と、キューのペイロード上限への配慮である。
- 添付ファイルは本文スキーマに含めず、`body.ref` が指す側のメタデータとして扱う（ファイル本体を本システムが中継するか、Slack 側のファイル参照だけを保持するかは未確定事項、第9章）。

### 3.2 Slack 生イベントとの対応付け

| Slack 側（Events API） | 内部スキーマ | 変換規則 |
|---|---|---|
| `event_id`（エンベロープ） | `idempotency_key`、`source.event_id` | そのままコピーする。再送時も同一値であることが冪等性の根拠 |
| `event.type = message` / `app_mention` | 受付対象の判定 | `message` のうち対象チャンネル・対象サブタイプのみ取り込む。編集（`message_changed`）と削除（`message_deleted`）は新規メッセージにせず、台帳の該当レコードへの状態遷移として扱う方針を原則とする（詳細は未確定事項） |
| `event.channel` | `source.channel_id`、`channel.channel_id` | そのまま |
| `event.ts` | `source.message_ts` | 不透明文字列として保持。順序判定には使わない（順序は台帳の `turn_number` が正本） |
| `event.thread_ts` | `source.thread_ts`、`channel.thread_key` | 欠落時はスレッド起点として `event.ts` を使う |
| `event.user` / `event.bot_id` | `sender.platform_user_id` | プロフィール登録簿と照合して `agent_id` と `kind` を決定する。照合できない場合は `kind` を推測せず未登録として扱い、ルーティング対象から外す（監査には残す） |
| `event.text` 内のメンション記法 | `recipients` | メンション対象を登録簿で `agent_id` に解決できた場合のみ `mode=mentions`。解決できないメンションは宛先に含めない。本文テキスト自体は宛先解決後も改変しない |
| `event_ts` | `occurred_at` | エポック秒から RFC 3339 へ変換 |
| （なし） | `ingested_at`、`turn.turn_number`、`delivery` | 自システムで付与する。`turn_number` は台帳のトランザクション内で採番する |
| リトライヘッダ（再送回数等） | 監査ログのみ | スキーマには入れない。再送であることは `idempotency_key` の重複で判定できるため |

Bot 自身の投稿の扱い: 本システムの Bot が投稿したメッセージもイベントとして戻ってくる。これを新規入力として再ルーティングすると自己ループになるため、送信者が「本システム自身」であるものは取り込み対象から除外する。一方、参加エージェントが各自の Slack 連携で投稿したメッセージは正規の応答として取り込む。両者の区別は登録簿の `platform_user_id` 照合で行う。

## 4. ルーティングと整合性

### 4.1 宛先判定の配送ルール

優先順位の高い順に適用し、最初に一致したルールで宛先を確定する。

1. **明示メンション**: 本文メンションが登録簿で解決できる場合、その相手のみに配送する（`mode=mentions`）。
2. **名前指定**: 登録簿に登録された呼び名・別名が本文の所定位置（文頭等）に現れる場合の扱いは、誤爆コストが高いため既定では無効とし、チャンネル設定で有効化した場合のみ `mode=named` として配送する。
3. **スレッド継続**: スレッド内の発言でメンションがない場合、直近にそのスレッドで応答したエージェントを第一候補とし、加えてスレッド参加者全員へ配送するかどうかはチャンネル設定（`thread_fanout`）に従う。既定は「直近応答者＋人間の発言は全購読者」のように、人間の発言とエージェントの発言で扱いを分けることを推奨する（根拠は第4.3節のループ防止）。
4. **全員配送**: チャンネル直下の新規発言で上記に該当しない場合、そのチャンネルの購読者全員に配送する（`mode=all`）。
5. **配送しない**: 送信者が未登録、本システム自身、対象外チャンネル、編集・削除イベント（状態遷移として処理済み）の場合は配送レコードを作らず `suppressed` 相当として監査にのみ残す。

宛先がエージェント本人を含む場合は除外する（自分の発言を自分に配送しない）。人間の利用者はアダプター経由の配送対象にせず、Slack 上で直接読む前提とするが、台帳には全メッセージを記録する。

### 4.2 冪等性

- **受付の冪等性**: `idempotency_key` に一意制約を置く。同一キーの再到着は「重複」として受付結果を返し、新規の台帳レコード、連番採番、配送は行わない。重複排除の保持期間（dedup TTL）は、Slack の再送が収まる期間より十分長く取る（目安は日単位。正確な値は運用パラメーター）。
- **配送の冪等性**: 配送レコードは `(message_id, agent_id)` で一意とする。リトライで配送処理が再実行されても、エージェント側が同じ配送レコード識別子で重複取得を検知できるよう、I-7 の取得応答には配送レコード識別子を必ず含める。
- **応答投稿の冪等性**: アダプターが台帳へ応答を書く場合（I-7）は送信側採番の `idempotency_key` を必須とし、Slack へ直接投稿する場合（I-8）は、投稿前に台帳へ「投稿予定」を記録し、投稿後に Slack のメッセージ識別子で確定させる二相方式を推奨する。完全な重複投稿の排除は Slack API 側に冪等キー
