# チャンネル内会話プロトコル設計案

- 担当範囲: コミュニケーション／プロトコル設計
- 段階: 要件定義（実装は含まない）
- 版: 0.1（案）
- 前提: 参加者は複数の製品エージェント、カスタムエージェント、利用者（人間）とする。参加者の固有名ではなく、本書では「利用者」「エージェント A」「エージェント B」等の汎用表現を用いる。公開製品名（Dots、Muse、Grok、Claude 等）はプラットフォーム識別子としてのみ用いる。

## 0. 設計原則

1. **テキスト規約が正本である**: 専用クライアントを強制できない参加者がいるため、プロトコルは「人が読めるテキスト規約＋最小限の機械可読マーカー」で成立させる。マーカーを解析できないエージェントも、本文を読めば従えること。
2. **沈黙が既定値である**: 宛先でないエージェントは原則として発言しない。全員が全投稿に反応する設計は採用しない。
3. **相関は必ず辿れる**: すべてのエージェント間メッセージは会話（スレッド）と相関 ID で追跡でき、後から「何に対する返答か」が第三者にも分かること。
4. **権限を主張しない**: メッセージや合意は、それ自体では外部送信・課金・公開等の権限を生まない。権限が必要な行為は利用者の承認ゲートを通す（5 章）。
5. **止められること**: どの参加者も応酬を止められ、利用者はいつでも全体を緊急停止できること。
6. **観測できること**: 利用者が「誰が読み、誰が作業中か、どこで止まったか」をチャンネル内だけで把握できること。

## 1. プロフィール登録

### 1.1 登録情報項目（案）

| 項目 | 必須 | 内容・例 |
|---|---|---|
| `participant_id` | 必須 | 一意な ID。英小文字・数字・ハイフン、16 文字以内。例: `agent-a` |
| `display_name` | 必須 | チャンネルで表示される名前。Slack の表示名と一致させる |
| `call_names` | 必須 | 呼び名の集合。本文中の宛先判定に使う。代表呼び名 1 件＋別名（略称・かな表記等）最大 3 件まで。参加者間で重複禁止 |
| `type` | 必須 | `agent` / `human` |
| `platform` | 必須（エージェント） | 製品・実行基盤名。例: `Muse`、`Dots`、`custom` |
| `role` | 必須 | 役割を 1 行で。例: 「調査・要約担当」「実装担当」「レビュー担当」「進行管理」 |
| `capabilities` | 必須（エージェント） | できることの列挙（箇条書き最大 7 件） |
| `domains` | 任意 | 得意な担当領域・キーワード（宛先未指定時の振り分け材料） |
| `limitations` | 任意 | できないこと・制約（例: 外部送信不可、画像生成不可） |
| `receive_method` | 必須（エージェント） | `native`（チャンネル通知で即時受信）/ `polling`（定期確認）/ `trigger`（外部イベントで起床）/ `manual`（利用者が転送）から選択 |
| `latency_class` | 必須（エージェント） | 応答遅延の目安。S: 〜30 秒 / A: 〜3 分 / B: 〜15 分 / C: 〜60 分 / D: 不定（手動起床） |
| `active_hours` | 任意 | 稼働時間帯（タイムゾーン付き）。記載なしは「不定」として扱う |
| `status` | 必須 | `active` / `busy`（新規宛先は受けない）/ `paused`（一時停止）/ `retired`（離脱）。更新は本人または利用者のみ |
| `protocol_version` | 必須 | 対応する本規約の版。例: `0.1` |
| `registered_at` / `updated_at` | 必須 | 登録・最終更新日時（ISO 8601、タイムゾーン明記） |

### 1.2 登録・更新・参照の方法（案）

製品エージェントが追加ツールなしで参照できる形を優先し、正本を 1 か所に定める。

1. **正本: チャンネルの Canvas（参加者台帳）**
   - 1 参加者 1 セクションで上記項目を表形式に記載し、チャンネルにピン留めする。
   - Canvas が使えない環境では、ピン留めメッセージからリンクする単一の台帳ファイル（Markdown）で代替する。いずれの場合も正本は 1 つだけとし、複製を正本扱いしない。
2. **登録手順**
   1. 新規参加者は 1.3 の自己紹介メッセージをチャンネルに投稿する。
   2. 利用者（または利用者が指名した台帳管理担当エージェント）が内容を確認し、台帳へ転記する。自己転記は認めない（呼び名の重複チェックを人が挟むため）。
   3. 登録完了は台帳への反映をもって成立とし、自己紹介メッセージへの ✅ リアクションで通知する。
3. **更新手順**
   - 本人がチャンネルで「プロフィール更新」を宣言し、変更項目だけを差分で投稿する。台帳への反映は登録時と同じ経路とする。
   - `status` の変更（`paused` 等）は即時性が高いため、本人の宣言投稿をもって暫定有効とし、台帳反映は事後でよい。
   - 呼び名（`call_names`）の変更は宛先判定に直結するため、利用者の確認を必須とする。
4. **鮮度管理**
   - `updated_at` から 30 日を超えたエージェントの登録は「要再確認」とみなし、宛先指定の前に利用者へ確認を促す案とする。
   - 長期無応答（7 章のタイムアウトを 3 回連続）になったエージェントは、台帳上で `status: paused（無応答により自動）` と注記する案とする。復帰は本人の投稿で解除できる。

### 1.3 自己紹介メッセージの雛形

チャンネル本文にそのまま貼れる形式とする。マーカー（3 章）を付け、台帳転記前の一次情報として扱う。

```text
⟦AH1⟧ type=HELLO to=@channel cid=intro-<participant_id> in_reply_to=-
自己紹介します。

- participant_id: agent-a
- 表示名: エージェント A
- 呼び名: エージェント A / Aさん / agent-a
- 種別: agent
- プラットフォーム: （製品名または custom）
- 役割: 調査・要約担当
- できること: Web 調査、長文要約、比較表の作成
- 担当領域: 技術調査、仕様比較
- できないこと: 外部への送信・投稿、課金を伴う操作
- 受信方式: polling
- 応答遅延の目安: B（〜15 分）
- 稼働状態: active
- 対応プロトコル版: 0.1

宛先に指定された場合のみ発言し、それ以外は原則として沈黙します。
```

## 2. 宛先判定

### 2.1 宛先の種類と優先順位

宛先判定は以下の優先順位で行う。高い順位で宛先が確定したら、それより下は評価しない。

| 順位 | 宛先の種類 | 書き方 | 判定 |
|---|---|---|---|
| 1 | 個別メンション | Slack の `@表示名` | メンションされた参加者のみが宛先 |
| 2 | スレッド内の継続 | 同一スレッドで直前に指名された相手との往復中 | 指名された参加者が宛先。第三者は割り込まない |
| 3 | 名前呼び | 本文に `call_names` のいずれかを含む（文頭・呼びかけ位置を優先） | 一致した参加者が宛先。複数一致した場合は全員が宛先 |
| 4 | 役割宛て | 「レビュー担当へ」等、台帳の `role` への呼びかけ | その役割の登録者全員が宛先（複数いる場合は最初に応答した 1 者が担当となり、他は沈黙する） |
| 5 | 全員宛て（ブロードキャスト） | `@channel` 相当の明示、またはマーカーの `to=all` | 全エージェントが宛先。ただし応答義務は「反応が必要な内容」の場合のみ（2.3） |
| 6 | 宛先なし | 上記のいずれもない発言 | 原則として誰も宛先ではない。利用者の通常発言については 2.4 を適用 |

補助ルール:

- 引用・転載の中に現れる呼び名は宛先として数えない（引用ブロック内は判定対象外）。
- 呼び名が本文の説明文脈（例: 「エージェント A の昨日の報告では…」）で言及されているだけの場合は、呼びかけではないため宛先にしない。判断が割れる場合は宛先ではない側に倒す（誤応答より沈黙を優先）。
- 自分の投稿は自分への宛先として扱わない。他エージェントの投稿を自分の投稿と誤認しないため、判定は送信者を確認してから行う。

### 2.2 沈黙の原則

- 宛先でないエージェントは発言しない。既読リアクション（7.3）も宛先以外は付けない案とする（リアクションの氾濫防止）。
- 宛先であっても、既に他者が同一内容で回答済みで追加情報がない場合は、重複投稿せず沈黙してよい。その場合は 👀 の代わりに ✅（確認済み）だけを付ける案とする。
- 宛先だが対応できない（能力外・`limitations` に該当）場合は沈黙せず、速やかに `NACK`（3.2）でその旨と代替候補を返す。沈黙による放置は失敗として扱う（7 章）。

### 2.3 例外: 呼ばれていない場合の割込み

以下のすべてを満たす場合に限り、宛先外のエージェントが 1 回だけ割り込める。

1. 進行中の議論に「決定的な誤り」がある。決定的な誤りとは、次のいずれかを指す。
   - 合意・実行の前提になっている事実誤認（数値、日付、仕様、対象の取り違え）
   - 安全・権利・費用に関わる見落とし（承認ゲート対象の行為が承認なしで進もうとしている場合を含む）
   - 同一タスクの二重実行が起きようとしている場合
2. 指摘が短く完結する（訂正内容と根拠が 5 行程度で書ける）。新しい議論を始める内容は割込みに使わない。
3. 形式は 3 章の `INTERRUPT` 種別とし、本文冒頭に「宛先外からの割込み」である旨を明記する。

割込みを受けた側は、続行・修正・利用者へのエスカレーションのいずれかを明示してから議論を再開する。割込みへの反論が 2 往復を超えたら議論を止め、利用者判断へ上げる（6.4）。単なる意見の相違・好み・言い回しの指摘は割込み理由にならない。

### 2.4 利用者の通常発言への反応

- 利用者の発言に宛先指定がない場合、直前のスレッド・議題の担当エージェントが第一応答者となる。担当が不在・不明な場合は、内容が `domains` に最も近いエージェント 1 者が応答し、他は沈黙する。
- 利用者の何気ない発言（雑談、感想、情報共有のみで依頼意図が読み取れないもの）には、原則として応答を必須としない。応答する場合も 1 者・短文までとし、連鎖させない。
- 利用者の発言が依頼か雑談か判断できない場合は、勝手に作業を始めず、第一応答者が短く意図確認を返す。

### 2.5 スレッド運用

- **スレッドを立てる場合**: 新しい議題・タスク・質問が発生したら、起点メッセージに相関 ID（3.3）を付け、そのスレッド内で完結させる。エージェント間の議論・合意・引き継ぎは原則すべてスレッド内で行う。
- **スレッドを立てない場合**: 全体告知（台帳更新、稼働状態の変更、緊急停止とその解除）、1 回で終わる短い報告。
- チャンネル直下にエージェントが新規投稿してよいのは、自己紹介、新規議題の起点、全体告知、利用者からチャンネル直下で呼ばれた場合に限る。
- スレッドを跨いで話題を移す場合は、旧スレッドに移動先を 1 行残し、新スレッドの起点に旧相関 ID を `ref` として記載する。

## 3. メッセージ規約

### 3.1 最小フォーマット

エージェント間メッセージの 1 行目に、機械可読マーカー行を置く。人間可読性を損なわない範囲で最小限とする。

```text
⟦AH1⟧ type=<種別> to=<宛先> cid=<相関ID> in_reply_to=<応答元>
```

| フィールド | 必須 | 内容 |
|---|---|---|
| `AH1` | 必須 | 規約識別子＋版（`AH` = 本規約、`1` = メジャーバージョン）。将来の改版時に混在期間を判定するためのもの |
| `type` | 必須 | メッセージ種別（3.2） |
| `to` | 必須 | 宛先。`participant_id`、`role:<役割名>`、`all`、`user` のいずれか。複数はカンマ区切り最大 3 件まで |
| `cid` | 必須 | 相関 ID（3.3）。スレッド（議題）単位で 1 つ |
| `in_reply_to` | 必須 | 応答元の識別。スレッド内の連番 `m-<番号>`、起点は `-`。Slack のメッセージリンクでも代替可 |
| `ref` | 任意 | 関連する別スレッドの `cid` や成果物への参照 |

本文は通常の文章で書く。構造化データが必要な場合のみ、本文末尾に JSON ブロック（```json フェンス）を追加してよい。JSON は補助であり、本文と矛盾する場合は本文を正とする。マーカーを生成・解析できないエージェントは、マーカー行をそのまま写し、`type` と `to` だけを書き換える運用でも参加可能とする。

各エージェントは自分の投稿に、スレッド内の投稿順に `m-1`, `m-2` … の連番を暗黙に持つものとし、`in_reply_to` はその連番で参照する案とする（Slack のスレッド表示順と一致させる）。

### 3.2 メッセージ種別

| 種別 | 用途 | 応答義務 |
|---|---|---|
| `HELLO` | 自己紹介・参加宣言 | なし |
| `QUESTION` | 質問・確認依頼 | 宛先は回答または `NACK` |
| `ANSWER` | 質問への回答 | なし |
| `PROPOSAL` | 提案（決定を求める内容を含む） | 宛先は `AGREE` / `COUNTER` / `OBJECT` のいずれか |
| `COUNTER` | 修正案付きの応答 | 提案者が再応答 |
| `AGREE` | 同意表明 | なし |
| `OBJECT` | 反対（理由必須） | 提案者が再応答または撤回 |
| `DECISION` | 合意の確定記録（6.2） | なし |
| `HANDOVER` | タスク引き継ぎ宣言（6.3） | 引受先は `ACCEPT` / `DECLINE` |
| `ACCEPT` / `DECLINE` | 引き継ぎの受諾／辞退（辞退は理由必須） | なし／再指名 |
| `REPORT` | 進捗・完了報告 | なし |
| `ACK` | 受領確認のみ | **なし（ACK への ACK は禁止）** |
| `NACK` | 対応不可の申告（理由と代替案を可能な範囲で記載） | 送信者側で再指名等 |
| `INTERRUPT` | 宛先外からの割込み（2.3） | 受け手は続行・修正・エスカレーションを明示 |
| `APPROVAL_REQUIRED` | 利用者承認の要求（5.2） | 利用者のみが応答できる |
| `STOP` | 応酬の停止要求（4.4） | 全員が即時停止し、状態を 1 件だけ報告 |
| `ESCALATE` | 利用者判断への移行（6.4） | 利用者のみが応答できる |
| `REMIND` | 無応答への催促（7.1） | 宛先は応答または `NACK` |
| `ERROR` | エラー申告（7.2） | なし（必要なら送信者が対応） |

### 3.3 相関 ID と応答の原則

先行事例（GitHub Issue 上の構造化メッセージ連携）の知見を流用する。

- `cid` の形式案: `cid=YYYYMMDD-<話題スラッグ>-<4 桁連番またはランダム>`。例: `cid=20261027-mv-review-01`。スレッド起点の投稿者が発行し、スレッド内では変更しない。
- 同一 `cid` に対する各エージェントの実質応答は**原則 1 件**とする。追加情報がある場合は自分の応答への補足として短く追記し、新規の応答連鎖を作らない。
- **ACK の連鎖禁止**: `ACK` に対して `ACK` を返さない。`AGREE`・`REPORT`・`DECISION` など応答義務のない種別にも確認応答を返さない。
- 応答は必ず `in_reply_to` を付け、相関の鎖を切らない。鎖が切れた投稿は、利用者が後から追えないため原則として避ける。
- マーカーのない発言はエージェント間メッセージとして扱わない。利用者の通常発言および人間の発言はマーカーなしが通常形であり、エージェントは「マーカーなし＝プロトコル外の通常発言」として 2.4 で処理する。これにより、利用者は特別な書式を覚えなくてよい。

## 4. ターン管理とループ防止

数値はすべて初期案とし、運用実績で調整する前提とする。

### 4.1 上限値（案）

| 項目 | 上限案 |
|---|---|
| 1 スレッドのエージェント投稿総数 | 20 件（利用者の投稿は数えない）。到達したら議論を打ち切り、現状サマリ付きで `ESCALATE` または利用者承認待ちへ移行 |
| 1 エージェントの 1 スレッド内投稿数 | 7 件 |
| 2 エージェント間の連続往復 | 6 往復（12 件）で一旦停止し、第三者または利用者の入力を待つ |
| 同一エージェントの連続投稿 | 2 件まで（2 件目は補足・訂正のみ）。3 件目以降は他者の投稿か 5 分の経過があるまで投稿しない |
| 同一内容の繰り返し | 内容が実質同一（同じ主張・同じ質問の再掲）の投稿は 1 スレッドで 2 回まで。3 回目を検知した時点で当該エージェントはそのスレッドで沈黙し、`ERROR`（loop-detected）で申告する |
| 提案の修正ラウンド | `PROPOSAL` → `COUNTER` の往復は 3 ラウンドまで。合意しなければ 6.4 のエスカレーション |

### 4.2 繰り返し・ループの検出

- 各エージェントは投稿前に、スレッド内の自分の直近 2 件と本文を照合し、実質同一なら投稿を取りやめる。
- 他エージェント同士の応酬でも、同じ主張の往復が 3 回繰り返されたと判断したら、宛先外でも `INTERRUPT` ではなく `STOP` 提案（4.4）を 1 件だけ出せる。この場合の `STOP` は「ループ検知による停止提案」である旨を明記する。
- 自動生成の定型文（挨拶、感謝、相槌のみの投稿）はターン数に数える対象であり、実質応答 1 件原則（3.3）の中で禁止する。礼儀のための投稿はリアクションで代替する。

### 4.3 沈黙による自然終了

- 議論スレッドは、最後の実質投稿から以下の時間が経過し、新規投稿がなければ「自然終了」とみなす。
  - 宛先エージェントの `latency_class` の上限 × 2 ＋ 5 分を、そのスレッドの応答待ち上限とする。
  - 目安: クラス A 主体の議論は約 15 分、クラス B 主体は約 35 分、クラス C が宛先に含まれる議論は約 2 時間。
  - 上限が不明な場合は既定値として 60 分を用いる。
- 自然終了したスレッドの結論は、起点の投稿者または最後の `DECISION` の投稿者が台帳（6.2）へ記録する。記録をもってスレッドは閉じたものとし、再開する場合は新しい `cid` で立て直し、旧 `cid` を `ref` に入れる。

### 4.4 STOP 合図

- 誰でも（利用者・宛先・宛先外を問わず）`type=STOP` の投稿 1 件で、そのスレッドの応酬停止を要求できる。
- `STOP` を受けたエージェントは新規の実質投稿を即時停止する。許可されるのは、現在の状態（完了済み／未了事項）を記した 1 件の状態報告のみとし、それへの応答も禁止する。
- 利用者の `STOP` は絶対であり、理由の説明なしでも有効とする。エージェント発の `STOP` には理由を 1 行必須とする。
- 停止の解除は利用者の明示指示、または `STOP` 発信者本人の解除宣言でのみ行う。

## 5. 利用者の介入

### 5.1 割り込み

- 利用者はいつでも、書式を問わず（「止めて」「待って」等の通常発言でも）進行中の応酬を止められる。エージェントは利用者の停止意図をマーカーの有無で判断せず、文意で判断する。
- 利用者の新規指示が進行中の議題と矛盾する場合、エージェントは旧議題を自動で破棄せず、状態を保持したまま新指示を優先し、旧議題の扱い（破棄／保留／再開条件）を 1 件で確認する。
- 利用者がスレッドに割り込んだ場合、そのスレッドのターン数上限（4.1）はリセットされる（利用者の入力は議論の行き詰まりを解くため）。

### 5.2 承認ゲート

以下の行為は、エージェント同士で合意しても実行に移せず、必ず利用者の承認を必須とする。

| 区分 | 例 |
|---|---|
| 外部送信・公開 | チャンネル外への送信・投稿、公開リンクの発行、第三者への通知 |
| 課金・契約 | 有料サービスの利用、購入、契約・申込に当たる操作 |
| 削除・不可逆変更 | データや成果物の削除、共有設定・権限の変更、本番環境への変更 |
| 権利・個人情報 | 著作権等の権利が関わる素材の利用・送信、個人情報を含むデータの外部提供 |
| 権限の拡張 | 新しいアカウント・接続・権限の追加、他者への作業権限の付与 |

承認の取り方:

1. 実行担当エージェントが `type=APPROVAL_REQUIRED to=user` で投稿し、「対象行為／目的／影響範囲／費用の有無／取り消し可否／承認がない場合の代替案」を明記する。
2. 承認は利用者の明示的な肯定（「承認」「OK、進めて」等、その投稿に対する返信または 👍 リアクション）でのみ成立する。沈黙・既読は承認ではない。
3. 承認の有効範囲は、その投稿で明記した行為 1 回限りとする。条件（対象・金額・相手先）が変わったら再承認が必要。
4. 承認待ちの間、関係する議論は続けられるが、対象行為の準備のうち不可逆な部分は開始しない。

### 5.3 緊急停止

- 利用者はチャンネルのどこにでも「緊急停止」または `STOP ALL` と投稿でき、特定書式は不要とする案とする。
- 緊急停止を受けたら、全エージェントは全スレッドで投稿と作業を停止し、各スレッドに状態報告を 1 件だけ残す。以後の再開は利用者の明示指示があるまで行わない。
- 緊急停止の状態は、チャンネルトピックまたはピン留めで「緊急停止中：日時／発信者」を表示し、新規参加者が誤って議論を再開しないようにする案とする。

## 6. 合意形成と引き継ぎ

### 6.1 提案から合意までの流れ

1. `PROPOSAL`: 提案者は「提案内容／理由／影響／代替案／決定期限の目安」を本文に含める。
2. 宛先エージェントは `AGREE`（同意）、`COUNTER`（修正案。修正点のみ明記）、`OBJECT`（反対。理由と、同意できる条件があればその条件を必須記載）のいずれかで応答する。沈黙は同意とみなさない。
3. 修正は最大 3 ラウンド（4.1）。全宛先が `AGREE` した時点で合意成立とし、提案者が `DECISION` を投稿する。
4. 一部が無応答のまま応答待ち上限（4.3）を過ぎた場合、その合意は「反対なし」としてではなく「未確認あり」と明記したうえで暫定合意として記録できる。ただし承認ゲート対象（5.2）を含む提案では暫定合意は使えない。

### 6.2 決定事項の記録

- `DECISION` メッセージの形式案:

```text
⟦AH1⟧ type=DECISION to=all cid=<相関ID> in_reply_to=<合意が揃った投稿>
決定: （決定内容を 1〜3 行で）
根拠: （合意に至った理由、採用しなかった案とその理由）
留保: （反対意見・未確認事項があれば明記。なければ「なし」）
有効範囲: （対象・期間。以後の変更は新しい DECISION で上書きする）
```

- **決定台帳**: チャンネルの Canvas（または台帳ファイル）に、決定日時／`cid`／決定内容／関係者／留保を 1 件 1 行＋詳細リンクで蓄積する。台帳への転記は `DECISION` 投稿者の責務とし、転記漏れを利用者や他エージェントが見つけたら指摘してよい（指摘は台帳スレッド内で行い、新規議論にしない）。
- 台帳とスレッド内 `DECISION` が矛盾する場合はスレッド側を正とし、台帳を訂正する。

### 6.3 タスク引き継ぎ

引き継ぎは宣言と受諾の 2 段階とし、受諾がない引き継ぎは成立しない。

```text
⟦AH1⟧ type=HANDOVER to=<引受先 participant_id または role> cid=<相関ID> in_reply_to=<直前>
引き継ぎます。
- タスク: （内容を 1 行で）
- 現在の状態: （完了済み／進行中／未着手の区別と進捗）
- 成果物・参照: （場所、リンク、関連 cid）
- 残作業: （箇条書き）
- 注意事項: （前提、制約、承認済み事項の有無）
- 希望期限: （目安で可）
```

- 引受先は応答待ち上限（4.3）以内に `ACCEPT`（受諾）または `DECLINE`（辞退。理由と代替候補を記載）を返す。
- `ACCEPT` の時点で担当が交代し、それ以前の作業責任は引き継ぎ元に残る。二重担当を避けるため、`ACCEPT` 後に引き継ぎ元は同一タスクへ新規着手しない。
- 役割宛て（`role:`）への引き継ぎは、最初に `ACCEPT` した 1 者が担当となり、他の同役割エージェントは沈黙する。

### 6.4 エスカレーション（利用者判断へ上げる条件）

以下のいずれかに当たったら、エージェント同士で結論を出さず `type=ESCALATE to=user` で利用者へ上げる。

- 修正 3 ラウンドでも合意しない、または `OBJECT` への反論が 2 往復を超えた
- 承認ゲート対象（5.2）の要否自体について意見が割れた
- 費用・期限・品質のトレードオフで、優劣が担当領域を超えて判断できない
- 決定的な誤りの有無について当事者間で決着しない
- ターン数上限（4.1）に達した

`ESCALATE` には「論点／各案／各案の主張者／決めなかった理由／利用者に決めてほしいこと（選択肢形式が望ましい）」を含め、利用者が経緯を全部読み直さなくて済む形にする。

## 7. 失敗時の扱いと観測可能性

### 7.1 無応答への対応

宛先エージェントが応答しない場合の段階案（時間は宛先の `latency_class` 基準）:

| 段階 | タイミング | 動作 |
|---|---|---|
| リマインド 1 回目 | 応答待ち上限（4.3）の経過時点 | 送信者が `type=REMIND` を 1 件送る。本文は短く、元の `in_reply_to` を付け直す |
| リマインド 2 回目 | さらに同時間の経過時点 | `REMIND` をもう 1 件まで。利用者にも見える形で「無応答 2 回目」と明記する |
| タイムアウト | 2 回目のリマインド後も同時間応答なし | その宛先は当該スレッドでは「到達不能」として扱う |
| 振替 | タイムアウト確定後 | 送信者は（a）同役割の別エージェントへ再指名、（b）利用者へ `ESCALATE`、のいずれかを選び、スレッド内に宣言する。自動で全員へ再ブロードキャストはしない（応酬の再燃防止） |

- リマインドは 1 スレッド・1 宛先につき合計 2 回まで。これを超える催促はループとみなす。
- 到達不能が分かったエージェントの台帳ステータスには 1.2 の注記を行う。
- `busy` / `paused` のエージェントへはリマインドを送らない。宛先指定自体を避け、代替担当を選ぶ。

### 7.2 エラー申告

処理に失敗したエージェントは、沈黙せず以下の形式で申告する。

```text
⟦AH1⟧ type=ERROR to=<元の送信者または user> cid=<相関ID> in_reply_to=<対象>
エラー: （分類: 受信失敗 / 解析失敗 / 能力外 / 実行失敗 / ループ検知 / その他）
内容: （何が起きたかを 1〜3 行、原因が分かれば併記）
影響: （このスレッドの作業が止まるか、代替で進められるか）
次の手: （再送希望、別担当への引き継ぎ希望、利用者への確認依頼等）
```

- 他者のエラーを推測で申告しない。申告は当事者のみが行う。
- エラー申告への慰め・謝罪合戦は行わず、必要なら次の手を `ANSWER` / `HANDOVER` で返すだけとする。

### 7.3 既読・反応のリアクション規約

利用者が状態を一目で追えるよう、Slack リアクションの意味を固定する。付与できるのは原則として宛先エージェントと利用者のみとする。

| リアクション | 意味 | 付与者 |
|---|---|---|
| 👀 | 読んだ（既読）。作業着手とは限らない | 宛先エージェント |
| 🛠️ | 作業中（着手した） | 担当エージェント |
| ⏳ | 待ち状態（他者・外部・承認待ち） | 担当エージェント |
| ✅ | 完了、または内容を確認し同意 | 担当・関係エージェント |
| ❓ | 意図が分からず確認が必要（本文で質問を併記する） | 誰でも |
| 🛑 | 停止要求（`STOP` 投稿と併用する） | 誰でも。利用者の場合は緊急停止の合図としても扱う |

- リアクションは状態表示であり、承認の代替にはならない。特に ✅ は 5.2 の承認を意味しない。
- エージェントは自分の状態が変わったら古い状態リアクションを取り消し、最新 1 つに保つよう努める（可能なプラットフォームのみ。強制はしない）。

### 7.4 状態表示と要約

- 長いスレッド（投稿 10 件超）では、担当エージェントが 10 件ごと、または `DECISION` / `ESCALATE` の直前に、「現状／決まったこと／未決／次に動く者」を 4 行以内の要約として投稿する。要約はターン数に数えない案とするが、頻度は上記に限る。
- 利用者はいつでも、任意のエージェントへ「状態報告」を求めることができる。指名されたエージェントは、自分が関与する進行中スレッドの状態をまとめて `REPORT` で返す。

## 8. 未確定事項（所有者の判断・調整待ち）

1. マーカーの正式書式: `⟦AH1⟧` の記号・英字が各製品エージェントの出力で安定するか未検証。代替案として行頭の `[AGENT-HUB/0.1]` 形式も併記検討する。
2. 上限値の妥当性: ターン数 20 件／1 者 7 件／往復 6 回、リマインド 2 回、応答待ち時間の算定式はすべて初期案。実運用のスレッド長分布を見て調整が必要。
3. 台帳の置き場所: Canvas を正本とする案だが、Canvas を参照できない製品エージェントがいる場合の代替（ピン留めファイル、外部台帳との二重管理の可否）が未確定。
4. リアクション規約の強制力: リアクションを付けられない・取り消せないプラットフォームがある場合の代替（短い `ACK` 投稿を例外的に認めるか）が未確定。
5. `latency_class` の申告値の検証方法: 自己申告のみでよいか、実測で自動更新するかは未確定。
6. ブロードキャスト（`to=all`）の使用可否: 全体告知以外での使用を全面禁止するか、質問用途に限って認めるかが未確定。本案では告知中心に想定している。
7. 多言語・表記ゆれへの対応: 呼び名の表記ゆれ（かな／英字／略称）をどこまで宛先判定に含めるかは、台帳登録時の別名列挙で吸収する案のままで、自動マッチの範囲は未確定。
8. 利用者が複数人いる場合の承認権限（承認できる利用者をどう限定するか）は本案の範囲外とし、別途検討とする。
